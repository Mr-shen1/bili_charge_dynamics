# UP 主动态与评论查看页面：软件需求规格说明书（SRS）

- 状态：已由用户确认需求，作为本期实现与验收基线。
- 上游依据：[可行性分析报告（FSR）](FSR.md)。
- 本期交付：模拟数据驱动的、兼容桌面与手机的可交互前端页面。
- 当前文档任务不包含页面开发、云资源配置或部署；需求状态不代表实现状态。

## 1. 文档职责与需求边界

### 1.1 与 FSR 的关系

FSR 记录可行性、技术取舍、资源约束和工作量估算。本文件细化用户可观察行为、展示数据语义、状态变化及验收条件，不重复进行技术论证。

本次确认新增了分页数值、文字折叠、排序并列规则、图片网格、浏览恢复和异常处理细节；明确取消 UP 主简介，时间精确到秒。这些是对 FSR 的细化，不改变本期范围。后续若需改变已确认行为，应先更新需求并获得用户确认，不由实现阶段静默扩大范围。

编号前缀：`FR` 为功能需求，`DR` 为数据要求，`NFR` 为非功能要求，`AC` 为验收场景。同一规则以其需求条目为准；验收场景引用规则并给出可验证结果。

### 1.2 目标用户与系统范围

面向个人自用，展示一个固定 UP 主的图文动态及其评论。核心流程是浏览列表、查看详情与图片、阅读评论和回复，再返回继续浏览。

页面统一处理普通“动态”。上游内容在 B站属于充电动态，不影响本系统的内容模型；本期没有充电标识、购买、解锁或会员体系。

本期使用虚构身份、模拟动态、模拟评论和合法可用的项目内演示图片。未来后端返回用户自有阿里云 OSS 的图片 URL，浏览器直接请求 OSS；应用服务器不代理图片。

### 1.3 范围排除

- 爬虫、B站接口、数据库、真实后端、账号与权限系统。
- 多 UP 主切换、UP 主搜索或添加、动态搜索、复杂筛选和统计分析。
- UP 主简介、粉丝数、关注入口和独立个人主页。
- 视频、转发动态、评论图片、复杂表情包和 B站专用富文本解析。
- 真实点赞、发评论、转发、图片下载及自由缩放或双指缩放。
- 深色模式、主题设置、离线功能和持久化阅读历史。
- OSS 上传及配置、CDN 配置、实际云部署、大型压测与具体容量承诺。

## 2. 术语与用户流程

| 术语 | 本文含义 |
| --- | --- |
| 动态 | 固定 UP 主发布的一条图文内容；可以只有文字或只有图片 |
| 一级评论 | 直接归属于某条动态的评论 |
| 回复 / 楼中楼 | 归属于某条一级评论的回复；用回复目标表达对话关系，界面不递归嵌套 |
| 动态评论总数 | 该动态的一级评论与所有楼中楼回复数量之和 |
| 回复数 | 某条一级评论下的回复总数 |
| 当前会话 | 当前标签页在不刷新、不关闭的情况下进行的站内浏览；不承诺跨标签页或重启后的状态恢复 |
| 主动进入 | 点击“查看详情”或“评论数”等入口打开详情，而非通过历史导航返回 |
| 历史导航 | 浏览器前进/后退，或详情页返回到其站内列表来源 |

主要用户流程：

1. 打开列表，阅读并按需展开动态正文、加载后续动态。
2. 通过“查看详情”阅读完整动态，或通过“评论数”直接阅读评论。
3. 在列表或详情点击图片进行预览，然后回到原位置。
4. 切换一级评论排序、加载评论、展开或收起楼中楼。
5. 返回列表，保留已加载内容与原浏览位置。

## 3. 页面与内容需求

### FR-01 页面结构与身份展示

- 列表顶部显示固定 UP 主的头像和昵称，下方为居中的动态内容主栏；不展示简介，也不保留简介占位。
- 桌面不增加复杂的两侧导航；手机使用单列布局。
- 每张动态卡片显示头像、昵称、发布时间、正文、图片及评论数。
- 详情使用独立页面，包含返回入口、完整动态内容、图片及评论区，不以多层弹窗承载详情和评论。
- 评论和回复显示作者头像、昵称、发布时间、正文及点赞数；作者为该 UP 主时展示 UP 主标识。
- 头像和昵称仅用于展示，不跳转其他页面。点赞数只读，不呈现可实际点赞的交互。
- 全站采用浅色、简化布局，参考 B站信息层级，不要求像素级复刻。

### FR-02 导航入口与有效地址

- 动态卡片不整体绑定详情跳转，选择或展开正文不触发导航。
- “查看详情”进入对应详情页顶部；“评论数”进入同一详情页并定位评论区。
- 点击图片直接打开该动态的图片预览，不要求先进入详情。
- 每条动态拥有可直接访问和刷新的详情地址；具体 URL 路径在实施阶段确定。
- 详情返回按钮有站内列表来源时返回该列表；无站内列表来源时回到列表首页，而非将用户带离本站。
- 无效地址与请求失败分别按 FR-13 处理；状态恢复及定位优先级按 FR-10 处理。

### FR-03 文字阅读

- 动态列表正文、一级评论正文和回复正文在当前布局下超过 6 个渲染行时，初始折叠至 6 行，并提供展开/收起操作。
- 未超过 6 行时不显示多余的展开入口；详情中的动态正文始终完整展示。
- 展开与收起只改变对应文本，不触发页面导航或改变其他评论的状态。
- 保留原有换行，正常显示普通文字和 emoji；长单词及长 URL 可换行，不能撑宽页面。
- URL、话题和 `@用户` 均按普通文本展示，不自动变成外链、用户跳转或话题入口。
- 楼中楼“回复 @某人”用于表达关系，不提供真实回复操作。

### FR-04 时间与计数

- 有效时间按北京时间（`Asia/Shanghai`）显示为 `YYYY-MM-DD HH:mm:ss`，不随浏览设备时区变化，也不替换为相对时间。
- 计数显示完整非负整数，可添加千位分隔符，不缩写为“万”等单位。
- 动态评论数使用动态评论总数，不用已加载评论数量代替；每条一级评论另显示其回复数。
- 时间、计数缺失与真实零值必须区分，兜底规则见 FR-12。

### FR-05 动态列表排序与分批加载

- 动态按发布时间倒序，每批最多 10 条，通过“加载更多”追加，不使用无限滚动。
- 相同时间的记录以稳定标识进一步确定顺序；具体比较方式可在实现中固定，但每次读取必须一致。
- “加载更多”保留已有动态及交互状态，不重置为首批，不无故跳回顶部。
- 无后续数据时明确显示已加载完毕，不再允许发起下一批加载。
- 列表加载中、空态和失败处理遵守 FR-11。

### FR-06 一级评论排序与分页

- 进入尚无会话状态的详情时默认选择“最热”；每批最多 20 条一级评论。
- “最热”：点赞数降序，同点赞数按发布时间降序；仍相同则以稳定标识确定顺序。
- “最新”：发布时间降序，相同时间以稳定标识确定顺序。
- 排序作用于该动态的完整模拟一级评论集合，再进行分批读取，不只排序已展示的一批。
- 一级评论的排序不改变楼中楼的时间正序。
- 切换排序后定位评论区顶部，重置为目标排序的首批，并重置评论文字和回复的展开状态；不沿用旧排序的分页进度。
- 切换时保留上方动态，显示目标排序正在加载。切换失败仍停留在目标排序的错误状态并可重试，不能把旧排序结果冒充为新排序。
- 连续切换以最后一次选择为准，较早返回的数据不得覆盖新选择；加载更多也不得把旧排序批次追加到新排序。

### FR-07 楼中楼回复

- 每条一级评论按时间正序预览最早的最多 3 条回复；相同时间以稳定标识确定顺序。
- 存在更多回复时可展开，每次最多追加 10 条，直到全部展示。
- 回复列表采用扁平结构，显示可用的回复目标，不增加无限嵌套层级。
- 展开更多后提供“收起回复”，收回最初最多 3 条；同一排序与会话状态下，再次展开恢复此前已加载的回复，不重复请求已有内容。
- 回复数为零时不显示展开入口；全部加载后不再显示可继续加载的操作。
- 切换一级评论排序时，按 FR-06 重置回复展示状态；某条回复列表失败不影响其他评论。

## 4. 图片与浏览状态需求

### FR-08 页面内图片布局

- 单图按比例展示，限制列表内展示高度；超长图通过预览阅读。
- 多图网格：4 张时两列，其他多图场景三列；网格不能造成页面横向溢出。
- 列表最多展示 9 个缩略图位置；超过 9 张时，在最后一格叠加未显示图片的数量，预览仍能访问全部图片。
- 详情展示全部图片缩略图，不把全部原图直接铺开；9 个位置不是数据图片数量上限。
- 预览顺序与数据中的图片顺序一致；点击缩略图打开对应图片。
- 图片加载策略见 NFR-03，失败处理见 FR-11。

### FR-09 图片预览

- 可从列表或详情打开预览，默认保持比例、完整显示当前图片，不裁切；显示当前张数与总张数。
- 提供上一张、下一张和关闭操作；第一张不能继续向前，最后一张不能继续向后，不循环切图。
- 只有一张图片时隐藏切换按钮。
- 手机支持左右滑动切图，桌面支持左右方向键切图、`Esc` 关闭。
- 对长图提供“适应宽度 / 完整显示”切换；适应宽度时允许在预览内纵向滚动阅读，不增加自由缩放。
- 切换图片时重置长图的纵向阅读位置；纵向阅读不应误触发横向切图，也不应带动底层页面滚动。
- 手机浏览器返回操作优先关闭当前预览，保留底层页面，而非直接离开列表或详情。
- 关闭后恢复触发预览的页面位置和操作焦点；失败图片仍允许关闭或切换其他图片。

### FR-10 会话内浏览恢复

| 情境 | 要求 |
| --- | --- |
| 从详情返回有来源的列表 | 恢复已加载动态、正文展开状态及滚动位置 |
| 历史导航返回已访问详情 | 恢复该详情的评论排序、已加载评论、回复展开状态及阅读位置 |
| 主动点击“查看详情” | 可以复用已有会话数据和交互状态，但必须定位详情顶部 |
| 主动点击“评论数” | 可以复用已有会话数据和交互状态，但必须定位评论区 |
| 关闭图片预览 | 恢复触发预览的底层页面位置，遵守 FR-09 的关闭与焦点规则 |
| 直接打开详情且无列表来源 | 正常加载该动态；页面返回按钮回到列表首页 |
| 刷新、关闭后重开 | 允许重置加载进度、排序和展开状态；无需持久化阅读历史，但有效详情地址仍可访问 |

入口指定的位置优先于旧滚动位置；历史导航则恢复历史阅读位置。列表数据必须先具备恢复条件，再恢复滚动，避免只保存坐标而丢失前面已加载的内容。

## 5. 加载、空态与异常需求

### FR-11 局部状态与重试

每个可独立读取的区域应区分加载中、成功有内容、成功无内容和失败。分页区域还需区分有更多与已加载完毕。成功无内容不是请求失败。

| 区域或操作 | 加载、空态与失败行为 |
| --- | --- |
| 列表首次加载 | 显示加载状态；无动态显示空列表；失败提供错误提示与重试 |
| 详情首次加载 | 显示加载状态；请求失败提供错误提示、重试和返回列表 |
| 评论首次加载或排序切换 | 只更新评论区；无评论显示无评论状态；失败在评论区重试，保留动态正文与图片 |
| 动态或一级评论加载更多 | 保留已展示内容；失败在原加载位置重试，不回到第一页 |
| 单条一级评论的回复加载 | 只改变对应回复区域；失败保留此前内容并在该区域重试 |
| 内容图片加载 | 加载失败显示占位和重试入口；不阻止其他图片查看及预览切换 |

- 请求进行中禁用对应的重复加载操作，避免相同批次被重复追加；不同区域的操作不应被无关请求全局锁定。
- 重试针对失败操作；成功后按稳定标识保证展示无重复，且不跳过失败批次的数据。
- 错误提示应说明受影响区域并提供可执行操作，不以技术堆栈替代用户提示。
- 头像加载失败使用 FR-12 的默认头像，无需占用内容图片的错误界面。

### FR-12 缺失字段兜底

| 缺失或无效内容 | 展示规则 |
| --- | --- |
| 头像缺失或加载失败 | 使用默认头像 |
| 昵称缺失 | 显示“未知用户” |
| 动态无正文但有图片 | 正常展示图片，不强行补正文 |
| 动态无图片但有正文 | 正常展示正文，不保留空图片区域 |
| 动态正文与图片均为空 | 显示“暂无内容”，不推断为已删除 |
| 评论或回复正文为空 | 显示“暂无评论内容” |
| 回复目标缺失 | 不拼接错误的 `@用户`，保留回复本身 |
| 时间缺失或无效 | 显示“时间未知” |
| 计数缺失 | 显示“—”，不伪装成零；有效的零仍显示 `0` |

本规则只约束展示，不要求实现数据清洗。模拟数据中用于正常排序的样例需具备有效排序字段；缺失字段样例的读取顺序应确定、可重复，不允许因展示兜底值导致随机顺序。

### FR-13 无效地址与内容不可用

- 对合法详情路径中的不存在动态 ID，显示“动态不存在或不可用”和返回列表入口，不将其表现为无限加载或普通网络重试。
- 对未知页面路径显示未找到页面状态，并提供回到列表的入口。
- 请求失败使用 FR-11 的可重试状态，不断言内容已删除或 ID 不存在。
- 部署后的页面入口回退与静态资源错误必须区分，见 NFR-05。

## 6. 数据与外部边界

### DR-01 展示数据语义

本表描述页面需要的信息，不指定 TypeScript 字段名、数据库表结构或 HTTP 协议。

| 数据对象 | 所需语义 |
| --- | --- |
| UP 主 / 评论作者 | 稳定用户标识、昵称、头像 URL；通过标识判断是否为固定 UP 主，不以昵称相同作为判断依据 |
| 动态 | 稳定动态标识、作者、发布时间、正文、按顺序排列的图片、动态评论总数 |
| 图片 | 可供缩略展示与预览使用的 URL；保留顺序，不要求前端从文件路径推断来源 |
| 一级评论 | 稳定评论标识、所属动态、作者、发布时间、正文、点赞数和回复总数 |
| 回复 | 稳定回复标识、所属一级评论、作者、发布时间、正文、点赞数及可缺失的回复目标 |
| 分批读取结果 | 本批数据及是否还有后续数据；可准确区分读取失败与成功空结果 |

稳定标识不能用分页位置或当前数组下标替代。时间数据必须足以确定其对应时刻，避免通过无时区字符串猜测时间；展示格式遵守 FR-04。

本期有效模拟数据的总数、回复数与完整数据集一致。未来真实数据可能只采集到部分内容，届时总数语义需通过数据接口明确；前端不得用当前已加载条数覆盖来源提供的总数。

### DR-02 模拟数据与可替换读取接口

- 展示层通过统一读取接口获取动态列表、详情、一级评论和回复，本期接入模拟实现。
- 排序、分页、空结果与失败均可通过该接口表达，展示组件不直接依赖模拟文件的组织方式。
- 未来可替换为 API 数据实现，不要求重写页面浏览规则；本期不制定真实 API 路径、数据库和爬虫方案。
- 本期素材不得依赖真实充电内容或 B站外链；开发与测试的失败触发方式必须确定、可重复。

### DR-03 图片 URL 边界

- 组件接收可直接用于展示的图片 URL，不自行拼接 B站域名、OSS 桶地址或本地目录。
- 本期可使用项目内图片 URL；未来由后端返回 OSS 图片 URL，浏览器直接请求，不经应用服务器转发。
- 缩略图和预览图可使用不同 URL；是否生成尺寸变体、使用 OSS 图片处理、缓存或 CDN 均留到实际接入阶段决定。
- 公开读或签名 URL 尚未选定；若未来采用签名 URL，其过期刷新需在接入阶段设计，不由本期静态页面代替。

## 7. 非功能需求与约束

### NFR-01 响应式与浏览器

- 检查 360px、390px、768px、1280px 视口宽度，页面不得横向溢出；长昵称、正文及图片不能撑坏布局。
- 面向现代 Chrome、Edge、Safari，手机重点覆盖 Android Chrome 和 iOS Safari；不承诺老旧浏览器或 B站 App 内置浏览器兼容。
- 验收记录实际浏览器版本、设备或模拟方式。桌面模拟、自动化浏览器与真机结果分别标明，不能互相冒充。

### NFR-02 可操作性与焦点

- 主要触控按钮提供约 44px 的点击区域；桌面交互支持键盘访问及可辨识的焦点。
- 图片预览的关闭、切换和长图显示方式操作应可通过键盘完成；预览打开时焦点应位于预览内，关闭时返回触发处。
- 图片失败、空态及加载状态有可理解的文字提示，不只依靠颜色或失效的图片表达。
- 手机横向切图、长图纵向阅读与底层页面滚动相互区分，遵守 FR-09。

### NFR-03 加载与资源

- 采用 FR-05 至 FR-07 的分批展示规则，不在页面打开时一次渲染全部动态和评论。
- 列表缩略图懒加载，预览图或原图按需加载；打开一张预览不要求预先下载该动态全部原图。
- 图片应预留合理展示空间，避免加载完成后严重扰动阅读与位置恢复；具体尺寸和实现方式在开发阶段确定。
- 懒加载不等于压缩，使用 OSS 也不保证图片性能。本期不设置未经基准测试的加载时间、并发或内存指标。

### NFR-04 文本安全与范围隔离

- 正文、昵称、评论及回复作为文本安全渲染，不将输入中的标签或脚本作为可信 HTML 执行。
- 正常展示不发起真实 B站请求，不依赖真实后端、数据库或 OSS 凭据。
- 本期公开静态产物只包含模拟内容；未来真实内容的合法获取、站点与 OSS 访问保护按 FSR 的接入门槛另行处理，不能靠前端隐藏替代授权。
- 失败样例通过开发/测试入口触发，正常用户页面不增加故障控制面板。

### NFR-05 技术与构建交付

- 遵循 FSR 已确认方案：React + TypeScript + Vite + React Router，不引入大型全站 UI 框架；Node.js 使用 nvm 管理，依赖和脚本使用 pnpm。
- 构建在本地或 CI 完成，生成可由 Nginx 托管的静态产物；生产页面不依赖常驻 Node.js 应用或 SSR。
- 部署目标是阿里云 2 核 2GB；后续后端、数据库及爬虫的资源评估不属于本期容量承诺。
- 本期开发交付源码、模拟数据与演示素材、关键交互测试、可复现构建方式与产物，以及静态部署说明，不实际配置云服务器。
- 部署说明必须区分 SPA 页面路由与静态资源：直接访问或刷新详情能进入应用；缺失资源返回资源错误，不能错误地返回入口 HTML。

## 8. 验收数据集

以下为最小验收样例要求，不代表产品数据上限或服务器性能指标。正常数据集与故障/缺失字段场景可以分开维护。

| 样例 | 最低覆盖要求 |
| --- | --- |
| 动态分页 | 至少 25 条，验证首批、连续追加与最终加载完毕 |
| 一级评论分页 | 至少一条动态有 45 条一级评论，验证分页完整性及两种排序 |
| 回复分页 | 至少一条一级评论有 25 条回复，验证预览、连续追加、收起与恢复 |
| 图片 | 纯文字、单图、4 图、9 图、超过 9 图、超长图及单张失败图片 |
| 文本 | 超过 6 行、长昵称、长 URL、换行、emoji，以及包含 HTML/脚本文本的安全展示样例 |
| 排序 | 不同点赞数、相同点赞数、相同时间，以及并列时需通过稳定标识区分的记录 |
| 时间和计数 | 可验证秒值与时区转换的时间、有效零值和缺失值 |
| 身份和回复 | UP 主本人评论/回复、普通用户、回复目标存在与缺失 |
| 空态和路由 | 空列表、无评论、无回复、正文和图片均为空、不存在动态 ID、未知路径 |
| 故障 | FR-11 所列各局部失败与重试；排序请求按逆序返回，以验证最后一次选择生效 |
