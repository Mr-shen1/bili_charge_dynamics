业务规则以[飞书通知需求与设计](../../design/feishu-notifications.md)为准，本文只写实现契约。锁定的模块接口：

| 模块 | 职责 |
| --- | --- |
| `backend/bili_monitor/notifications/config.py` | 读取路由配置、本站基址与可选签名密钥；单条目写错只让该目标等待配置；`repr`、日志、队列都不复制 webhook 与密钥 |

| `notifications/outbox.py` | 事务发件箱：阶段与评论起点、正文写领取、版本与（动态、所属根、评论）身份去重、候选、事件、目标投递、领取/回写、心跳时段与有效期、告警节流与登记 |

| `notifications/heartbeat.py` | 北京时间时段身份、有效期与本机可观察状态 |
| `backend/bili_monitor/notifier.py` | 进程入口、单实例锁、信号退出 |

## 1. 进程

```sh
export BILI_DATABASE_PATH=/srv/bili-monitor/monitor.sqlite
export BILI_NOTIFICATION_CONFIG=/srv/bili-monitor/credentials/notifications.json
exec .venv/bin/python -m backend.bili_monitor.notifier
# 只处理一轮到期记录并退出（运维排查用；不登记心跳）：
.venv/bin/python -m backend.bili_monitor.notifier --once
```

- 独立进程，与 API、collector 使用同一 SQLite；API 与 collector 不内嵌通知定时器，只读 HTTP 不产生事件。
- 启动时取得数据库旁 `.notifier.lock` 排他锁，重复启动直接失败（`Notifier already running`）；崩溃后锁由内核释放。
- 启动时执行 `Store.migrate`（当前 schema v23），并重新核验“等待配置”的待投递记录，使修复后的配置无需等待复检周期（`--once` 只跑一轮到期记录，不做这次复检，也不做告警扫描）。
- 默认每 **1 秒**领取一轮，单轮有限批量（8）；网络等待、限流与退避都在数据库事务之外。
- 每轮轮询先读一次持久总开关（§1.1，关闭即直接进入下一轮），再按当前时间登记本小时心跳（见 §3.1），然后投递到期记录，最后按 §3.3 扫描“持续投递失败”事实并登记告警；心跳与告警都不单独起时钟进程，也不进 API。
- 单轮领取/回写失败（如 SQLite 写锁竞争）只记录固定分类并继续下一轮，不停掉投递进程；心跳登记失败与告警扫描失败同理（`heartbeat_cycle_failed`／`alert_cycle_failed`），不连带停掉业务投递。
- 等待配置的记录每 60 秒复检一次，每次回写都会累加 `attempts`；心跳在系统群未配置时也会这样累积。这只是“未配置”的诊断计数，**不是**投递失败次数。真实失败次数另记在 `failures`/`last_failed_at`（见 §4），告警阈值只读它们（见 §3.3），不能拿 `attempts`。心跳过期后该记录转为 `expired`，不再增长。
- 同一数据库只允许一个投递实例（`.notifier.lock`）；第二个进程启动即以固定错误退出，崩溃后锁由内核释放，不靠租约猜活。
- 统一托管入口（`python -m backend.bili_monitor.service`）已支持三个进程：先等 API 完成迁移并监听，再启动独立 collector，最后启动通知进程；设置 `BILI_NOTIFICATION_CONFIG` 时才有第三个进程，未设置时保持原两进程形态（不投递飞书）。任一子进程退出都会停止其余进程并以固定错误退出；TERM 按“通知 → 采集 → API”反向顺序逐个等待退出。启动顺序、迁移顺序、启停与路由修复步骤见[部署手册](../../../deploy-v2/README.md)（安装第 4/7 步、选配第 8 步）；systemd unit 与 env 模板见 `deploy-v2/assets/bili-monitor.service`、`deploy-v2/assets/bili-monitor.env.example`。API 仍不内嵌任何通知定时器。

## 1.1 发送状态（管理页三态，票据 14 起、票据 15 改造）

- 语义：通知进程**不停止**（照常持有 `flock`、照常跑轮询），状态是**一个持久枚举**，同时决定登记与发送哪一类消息：

  | 状态 | 业务消息（动态变化 / 一级评论 / 楼中楼） | 系统消息（心跳 / 告警） |
  | --- | --- | --- |
  | `all` 全部通知 | 登记 + 投递 | 登记 + 投递 |
  | `system_only` 仅心跳与告警 | 不登记、不投递 | 登记 + 投递 |
  | `off` 全部关闭 | 不登记、不投递 | 不登记、不投递 |

- 与 `BILI_NOTIFICATION_CONFIG` 的分层不变：环境变量决定**是否启动通知进程**，本状态决定**进程发什么**。
- 持久化：状态存 SQLite（随库走，重启服务、重新部署与机器重启后保持），**默认 `off`**；v22 → v23 迁移把布尔闸门换成三态表，既有库升级后同样是 `off`（新语义下“默认不发”比“默认全发”安全：升级瞬间不会突然开始投递没预期的消息）。
- 非 `all` 状态：采集、归档、API 全部照常，但**业务事件不登记**（登记发生在采集写事务里，因此闸门也装在登记侧）；`off` 下心跳与告警同样不登记——等价于“错过不补”，与 `:40` 窗口规则一致。
- 状态切换时同步收敛队列（`outbox.discard_queue`）：进入 `off` 作废全部 `pending`/`waiting_config` 记录，进入 `system_only` 只作废业务角色的未投递记录；正在发送中的 `inflight` 无法撤回，由那一轮投递自行收尾。
- 切回 `all`（**票据 15 裁决，替换票据 14 的“方案 A 保留并补发”**）：就地前移业务起点（`outbox.realign`）——每个未封存且仍在入选的阶段把 `comment_started_at` 置为切换时刻、`baseline_version` 对齐当前已归档的可信版本（与 `activate` 同口径），阶段本身延续、去重种子不清。因此关闭或仅系统期间发生的变化与评论**永远不补发**，只通知切换之后的新变化。
- 可观测：状态切换与“因关闭而跳过”都是 `notifier_event` 的固定分类字段，不含 webhook、密钥或 URL。`off` 期间每轮都跳过，但只在**状态变化时**记一条（`delivery_skipped reason=switch_off` / `notification_switch_opened`），不每秒刷日志。进程启动按实际状态计，因此正常启动不伪造一次切换日志；启动时状态就是 `off`，则第一条就是 `delivery_skipped`。管理页切换记 `notification_switch_changed state=<all|system_only|off>`，幂等重复写同一状态不产生这条日志。
- 读不到状态（如本地存储异常、状态表缺失）按 `off` 处理：不领取、不发 HTTP，采集侧也不登记。`delivery_cycle_failed reason=storage_error` **只在首次进入该状态时记一条**，恢复后记一条 `notification_switch_opened` 再继续投递；宁可停发也不误发，但不会每秒刷日志。登记侧读失败只让这次不登记，绝不让归档事务回滚。
- 管理端契约见 [management-api.md](management-api.md) 的“通知状态”一节。

实现约定（`notifications/outbox.py` 的 `read_state`/`write_state`/`_registration_open`/`discard_queue`/`realign`/`pending_count`，`delivery.py` 的 `_allowed`/`_switch_enabled`）：

- 状态是 SQLite 单行表 `notification_gate(id=1, state)`（v23 迁移，缺行按 `off`，重放迁移不重置已选状态）。
- `tick` 与 `run_once` 都以同一入口读状态：`tick` 先读状态再登记心跳、再投递、最后扫描告警；`--once` 走 `run_once`，同样受状态约束，因此“`off` 后一条都不发”对运维排查入口也成立。
- 状态切换不改变单实例锁、租约、领取凭证与失败事实：`off` 期间没有领取，因此不会出现“关闸时被领取、切回后重复发送”。

## 2. 配置

配置文件只存在于服务端仓库外，格式：

```json
{
  "base_url": "https://archive.example.invalid",
  "ups": {"900719925474099312345": {"up": "up-room", "all": "all-room"}},
  "dynamics": {"123": {"up": "up-room-123"}},
  "system": "system-room",
  "destinations": {
    "up-room": {"webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/<fictional-token>"},
    "all-room": {"webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/<fictional-token>",
                 "secret": "<fictional-signing-secret>"},
    "system-room": {"webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/<fictional-token>"}
  }
}
```

`secret` 可选：机器人在飞书侧开启“签名校验”时才需要。它只在发送时参与组装 `timestamp`/`sign`，不写入发件箱、消息快照、错误或日志。

- 业务角色是 `up`（UP 群）与 `all`（全员群），两者都按“动态覆盖 → 所属 UP 默认值”解析；某个角色缺失就只为该角色进入“等待配置”，**不跨角色补位**（不会把全员群或系统群当 UP 群，也不会反过来用 UP 群顶全员群）。
- 系统群是顶层 `system` 单独配置的目标角色：心跳与后续告警只发这一个角色，不按 UP 或动态覆盖解析。`system` 缺失时心跳保留待配置记录，不转投 UP 群或全员群。
- `base_url` 只接受无凭据、无查询串的 `http(s)` 地址（服务器配置，不从请求头推导）；链接为 `{base_url}/dynamics/{id}`。
- 目的地只保存引用标识；发件箱、日志、错误与消息快照都不含 webhook 或签名密钥。队列只记录目标角色（`up`/`all`/`system`），实际地址与密钥在发送时由服务端配置解析——不把凭据副本写进队列。
- 单条目写错（`webhook` 不是 `http(s)` 地址、`secret` 不是非空字符串、条目不是对象）只把该目的地标成不可用：对应目标进入 `waiting_config` 且错误码为 `route_invalid`，其他群照常投递。引用指向不存在的目的地同样是 `route_invalid`；角色本身没配置才是 `route_missing`。
- 整份文件不可解析、`base_url` 非法或路由表结构非法仍按启动错误处理（通知进程直接退出，不自动降级）。此时没有可用告警通道（见 §3.3），属票据 10 的运行边界。
- 修复流程：编辑配置文件 → 重启通知进程。记录保留（`waiting_config` 在启动时立即复检，不用等 60 秒）、阶段与基线不重设、历史不补发、已成功目标不重发。没有热更新：运行中改文件不会生效，也不需要为修复另做 UI。
- 新增目标角色只在同一 `ups`/`dynamics` 角色表里加键，不新增第二套凭据入口；系统群仍是唯一顶层例外。

## 3. 事件资格与去重

- 只有**可信任的新版本正文实际成功归档**（`Store.finish_archive` 的 success 分支内）才登记动态变化事件；计数、定位、聚合 revision、未知/失败/受限信号都不单独产生事件。
- 首次取得正文只建立基线；已有归档首次启用通知时，用已有可信版本作基线，不补发旧版本。
- 正文事件按 `(dynamic_id, 已成功取得的可信版本)` 去重，跨重启、重复扫描与重新入选有效；同一版本重复提交不重复登记。
- **受限（`MAJOR_TYPE_BLOCKED`）也要可见**：受限不是成功归档，因此不建基线、不推进版本；但会登记一条 `dynamic_restricted` 事件（同一阶段内按阶段令牌去重，重复的每 60 秒页面检查不会刷屏），路由与「发生变化」相同（只发 UP 群）。受限只影响正文：它下面的新评论照常按评论规则登记与投递。恢复可读后按正常规则发「发生变化」。
- 通知阶段是自有身份，**不等于入选令牌**：`refresh_selections(reset=True)` 会轮换全部入选令牌（recent_n/模式变化），持续入选的目标沿用原阶段与原基线。
- 目标真正离开入选时封存阶段；重新入选建立新阶段，以恢复后第一份可信正文重建基线。停用后在途执行仍可保存内容，但因领取时绑定的阶段已封存而不产生事件。
- 消息快照在登记事件时冻结（动态 ID 与标题）；投递与重试不读取最新归档，标题缺失或仅空白回退动态 ID。

## 3.1 一级评论（04）

- 接入位置是根评论的实际写事务（`Store._change_roots`，逐页提交）：评论内容、合格事件或候选、逐群投递记录在同一事务提交或回滚。因此**单条评论就绪即可投递**，不等整轮分页结束，也不等媒体完成；后页失败不收回已提交页的资格，也不宣称本轮评论集合完整（`root_comments_error` 仍如实记录）。
- **评论起点独立于正文基线**（`notification_phases.comment_started_at`）：新阶段在建立时与 `started_at` 同一时刻写下评论起点。接入本能力时升级已有库，01 建立的旧阶段以**升级时刻**作为评论起点，而不是复用 01 早就写下的 `started_at`——否则升级瞬间会把 01 部署以来的历史评论判成“起点之后”批量补发。裁决：升级前已归档、以及 01 之后 04 之前发表但未接入评论通知的评论**静默**（它们从未属于评论通知阶段），升级后发表的评论照常通知。
- 资格比较使用来源发表时间（`published_at`，`+08:00` 秒精度）与评论起点，比较前都解析成时间戳；**起点按秒取整**，与起点同一秒发表的评论属于“起点及之后”。不用采集时间或首次见到时间补造资格。首屏置顶/热评 extras 可能是很早的历史评论，因此只靠起点过滤，不靠“首次插入”直接通知。
- 作者 UID 或发表时间缺失时，内容照常归档，并在同一事务里写入 `notification_candidates`（记录**原阶段**）；同一评论补齐字段后按候选原阶段的评论起点原子转成事件，转换失败随内容一起回滚。已结束（封存/退选）阶段的候选作废，不借新阶段生成通知。补字段、纯编辑、重复扫描都不是新增，只有候选补齐才走转换。
- 路由按评论作者 UID 与该动态所属 UP 的 UID（`archives.uid`）**字符串相等**判定：相等 → `up` 与 `all` 两个目标；否则 → 仅 `all`。昵称、是否“另一个受监控 UP”都不参与判断；系统群不在业务角色里，因此不会收到评论正文。
- 事件身份是 `(kind='root_comment', dynamic_id, root_id, comment_id)`，一级评论的 `root_id` 就是自身；回复（05）将用所属根作 `root_id`，因此同一源评论 ID 属于不同根时不会撞键。跨重启、重复扫描与重新入选都不重复登记。
- 快照在登记事件时冻结：动态 ID 与标题、作者 UID 与昵称、发表时间、正文、是否已知有图。投递与重试不读取最新归档；归档随后被编辑只改归档，不改已入队消息。链接基址与 01 一致，在发送时从 `base_url` 读取（改基址会影响尚未发出的消息，这是既有裁决）。

## 3.2 楼中楼回复（05）

- 接入位置是回复的实际写事务（`Store._change_replies`，逐楼逐页提交）：回复内容、合格事件或候选、逐群投递记录在同一事务提交或回滚。**单条就绪即可投递**，不等其他楼层、后续页或媒体完成；某楼后页失败不收回已提交页的资格，也不宣称整轮回复集合完整（`replies_error` 如实保留 `REPLIES_FAILED`）。
- 阶段、评论起点、候选与路由与 3.1 完全一致，不复用第二套身份规则或通知时钟：作者 UID 与该动态所属 UP 的 UID 字符串相等 → `up` + `all`，否则仅 `all`；被回复者身份、昵称与其他受监控 UP 都不参与判定。
- 事件身份是 `(kind='reply_comment', dynamic_id, root_id, comment_id)`：`root_id` 是**所属根评论**，`comment_id` 是目标回复，因此同一源评论 ID 属于不同根时不会撞键。一级评论与回复共用同一唯一索引，去重跨重启、重复分页、补字段与纯编辑有效。
- 可定位条件由归档本身保证：回复只能指向已归档的所属根（`replies` 外键），回复与根的 ID 都是本站可用的十进制身份。因此“根或站点不可定位”只表现为回复无法合法归档（分页失败、`REPLIES_FAILED`），本契约不为通知放宽外键或来源校验，也不伪造字段。
- 候选身份是 `(dynamic_id, root_id, comment_id)`（一级评论的 `root_id` 就是自身），回复候选带上所属根；补齐后按候选原阶段的评论起点原子转事件，已结束阶段的候选作废，不越阶段生成通知。
- 消息沿用 3.1 的新增评论模板，链接换成该条回复的精确入口 `{base_url}/dynamics/{dynamicId}/comments/{rootId}/replies/{replyId}/locate`；不剥除来源“回复 @某人”前缀、不附加父评论全文、不扩大回复图片采集或飞书上传范围。空正文的回复按 §6 的纯图占位规则处理：只依据来源响应已给出的图片存在性（归档只存布尔 `has_pictures`，不保存 URL、不下载上传、不新增上游请求），未知不当成无图，也不反向扩大前端或采集侧的回复图片范围。
- 阶段有效性在提交处按**领取时绑定的阶段**核验（`notification_body_claims` 的 generation → phase），正文、一级评论与回复共用同一绑定。停用后重新启用的旧在途执行即使写代次仍是当前值，也无法把迟到内容算进新阶段——只按“当前未封存阶段”推导会违反[设计 §3.4](../../design/feishu-notifications.md)“旧执行不能借新阶段生成通知”。

## 3.3 小时心跳（09）

- 时段身份是**北京时间的 `YYYY-MM-DDTHH`**（`Asia/Shanghai`，用现有 `BEIJING` 常量做绝对时区换算，不受服务器 `TZ` 影响），**只在第 40 分钟这一分钟内成立**：`moment.replace(minute=40, second=0) <= now < 该时刻 + 1 分钟`，即 `:40:00`–`:40:59`。整分钟窗口是为了让 1 秒轮询不需要精确命中某秒；`:40` 之前不提前生成，`:41` 起（包括进程首次启动）返回 `None`，本小时不再有生成入口。
- 时段身份持久写入 `notification_heartbeats`（主键即时段）：同一小时的重复轮询、进程重启、重开数据库都不会重复生成，不靠进程内标记。时段已存在的那一轮只做一次只读判重，不抢写锁。
- 停机错过的时段**不追赶**：没有“生成非当前时段”的入口；窗口关闭（`:41` 起）后首次启动也不为本小时补一笔，因此进程在 `10:41` 或 `10:55` 冷启动不会补发 `10:40`，恢复后只处理当前小时（且未到窗口就什么都不生成），不会一次补发几条旧心跳。
- **窗口只限制生成，不限制投递**：已生成的待发/重试心跳仍按退避重试到 `expires_at`，窗口关闭不等于放弃这条消息；业务消息同样不读窗口。
- 有效期 `expires_at` 为下一个时段开始（下一个 `:40`，即本时段开始后一小时），写入事件对应的投递记录；有效期不跨时段。
- 心跳只发系统群（`role=system`）：系统群未配置时留 `waiting_config` 与脱敏错误 `route_missing`，不转投 UP 群/全员群；系统群发送失败按原任务退避重试，过期后停止。
- 心跳文本只陈述本地已记录事实，不把通知进程存活写成采集成功：

```text
心跳【2026-10-09 13:40】通知进程存活
采集观察：纳管 3 个目标，已检查 3 个，最近检查 2026-10-09 13:39:50
最近一次检查：失败 1 个，正文待同步 2 个
仅报告本地已记录状态，进程存活不等于采集成功
```

  “纳管”与“已检查”不等时（如刚启用、采集滞后）如实显示；无任何检查记录时显示 `已检查 0 个，最近检查 无记录`；无纳管目标时显示 `暂无纳管目标`。不出现“正常/全部正常”之类断言。
- 只读产品表（`targets`/`recent_discoveries`/`target_checks`）汇总状态，不访问上游、不写检查或归档，因此不能凭心跳推断内容已归档。
- 时段去重与心跳投递不读写任何“故障节流”状态；告警的 30 分钟节流见 §3.3（状态在 `notification_alerts`），两者只共享队列基础设施。

## 3.3 系统告警（08／09）

五类运行故障与三个风控生命周期事实只发系统群（`role=system`），与业务群严格分开；不为业务故障发恢复消息，也没有飞书图片上传降级消息。

| 类别 `category` | 触发事实（全部来自真实代码路径，不解析日志文本） | 对象 `object` | 固定原因 `reason` |
| --- | --- | --- | --- |
| `credential` | 来源业务码 **`-101`** 且本次启动**确实配置了来源凭据**（`BILI_COOKIE_FILE` 读到非空 Cookie） | `source_credential` | `credential_rejected` |
| `collection` | 目标检查失败（页面/详情/计数读取）、同步阶段真实失败（正文读取失败、根／回复分页失败、执行异常）、近期发现失败 | `{uid}:{dynamic_id}`；发现用 `{uid}` | 采集固定分类，如 `timeout`／`network_error`／`http_status`／`source_rejected`／`body_failed`／`comments_failed`／`source_unavailable`；匿名 `-101` 为 `login_required`。**分页一致性校验（`pagination_*`、`comment_count_decreased`、`reply_count_decreased`）只留 WARNING，不登记告警** |
| `loop` | 主循环捕获到的运行异常（`collector_loop_failed`） | `collector_loop` | 固定分类（多为 `internal_error`） |
| `delivery` | 业务目标**持续投递失败**：`notification_deliveries.failures >= 3` 且 `state='pending'`；心跳、告警自身与系统角色不计 | `{role}:{kind}`（如 `up:root_comment`） | 最近一次失败分类，如 `timeout`／`http_error`／`platform_rejected`／`rate_limited` |
| `route` | 业务目标路由缺失或目的地不可用（`route_missing`／`route_invalid`） | `{role}:{uid}:{dynamic_id}` | `route_missing`｜`route_invalid` |
| `risk_triggered` | 真实风控状态转移：`normal`／`observing` 收到 HTTP 412／429 进入冷却（第六档后直接转人工的一次转移只登记 `risk_manual`） | `source_risk` | `risk_cooldown` |
| `risk_manual` | 真实风控状态转移进入人工态：第六档探测失败，或观察期第六档之后再触发 | `source_risk` | `risk_manual_wait` |
| `risk_recovered` | 风控观察期按“确有成功业务请求的活跃采集时间”满 10 分钟后回到 `normal`（探测刚通过、尚未稳定不算） | `source_risk` | `risk_stable` |

判定边界：

- **可信凭据失效只有一条路径**：上游业务码 `-101`（账号未登录）**且**本次进程启动时读到来源凭据。`-111/-352/-401/-403/-412/-799` 等风控／频控／权限码、HTTP 401/403、超时与网络异常一律保持原分类，不冒充登录失效；未配置凭据时的 `-101` 归 `login_required`（采集异常，属本地匿名配置问题）。不新增 `nav` 或其他上游探针，也不用空页启发式推断登录态。
- **正常业务活动不告警**：计数增长、采集期间的新评论、普通“待同步／媒体待完成”都不产生故障告警；只有显式失败事实（检查失败、正文读取失败、根／回复分页失败、执行异常）才登记。**可重试收敛的分页一致性校验除外**：页内计数基准因来源删除／插入漂移时，下一次尝试会重新定位锚点并刷新基准，因此只记 `collector_failure` 的 WARNING 与持久错误事实（可续采），不登记告警；`value_invalid` 这类未登记的校验失败仍按采集异常提醒。
- **不递归**：系统角色（`system`）自身的缺配置、投递失败、心跳失败与告警投递失败一律只留本地脱敏诊断与 `failures` 事实，不再生成新告警，也不转投业务群。
- **登记与失败事实同事务**：检查结果（`record_check`）、工作回写（`finish_check_work`）、发现结果（`finish_discovery`）与投递回写（`_finish`）在同一事务里登记告警；每条告警用 `SAVEPOINT` 单独隔离，写不进一条告警只丢该告警并记 `alert_registration_failed`，不让采集/投递主链跟着回滚。主循环异常用**独立新建连接的短事务**在退出前登记；该连接或整库不可写时只留脱敏日志，不承诺即时外发（进程被强杀、整机离线同样无法登记）。
- **节流与合并**：同一 `(category, object)` 首次立即提醒，此后每 **30 分钟**最多一条；节流状态持久在 `notification_alerts`，跨重启保留。若上一条同类提醒**仍未投递完成**（`state` 不是 `sent`／`expired`），新的同类故障合并到它、不再新建事件，因此系统群长期失败时不会按故障次数或采集轮次堆积。不同对象、不同类别分别判定。
- **告警不套用心跳有效期**：告警投递记录 `expires_at` 为空，不会因为跨过整点被判过期；反之告警节流也不读写 `notification_heartbeats`，两者互不抑制。
- **风控生命周期告警只认状态转移**：三个类别在风控状态机的对应短事务里登记（`_record_trigger` 的首次触发／冷却升级、`_finish_probe` 的末档失败转人工、`_observing_tick` 的稳定恢复），与状态事实同事务提交，不解析日志文本、不做全表扫描。每档等待、每类探测结果、每页 412 与重复的迟到响应只进结构化日志，不刷群；人工态重复登记、轮次接管、进程重启都不产生新告警。对象是唯一的全局保护状态 `source_risk`，三个事实各占一个类别，因此恢复消息不会被分钟级的触发提醒节流吞掉。
- **票据 10 组合复验**：真实 API＋独立采集＋独立通知三进程共享临时 SQLite、飞书 HTTP 替身的隔离回放确认，六档冷却与人工探测只投递触发／转人工／稳定恢复三类系统消息，探测与观察期间业务群为 0；恢复后新一级评论仍按既有通知起点与资格投递，系统群不混入评论正文。证据见[10 多进程组合与性能验收](../../../.scratch/bilibili-risk-control/evidence/10-integrated-performance-verification.md)。
- **通知关闭即不登记**：`off` 时风控告警与其他系统消息一样不登记、不排队、不补发，风控也不改动通知开关；`system_only` 只收这类系统消息，`all` 行为不变。告警写不进时只丢该条告警并留 `alert_registration_failed`，状态转移照常提交——通知失败不能变成风控旁路。
- **风控告警消息只有固定字段**：类别、对象、发生时间与固定原因；不带正文、完整 URL／query、Cookie、凭据，也不带 owner／探测轮次令牌。逐接口资源定位信息留在采集日志。

配置整体不可解析、`base_url` 非法或路由表结构非法时通知进程仍按启动错误退出（见 §2），此时**没有可用告警通道**：这类故障只能由进程托管与日志发现，不由本能力外发。

## 3.4 生命周期：停用、移出、删除、模式切换与重启（07）

本节把“何时结束通知阶段、何时开始新阶段、什么只是重启”写成实现契约；矩阵与逐项证据见[票据 07 证据](../../../.scratch/feishu-notifications/evidence/07-notification-lifecycle.md)。

- **结束阶段（五种真实入口）**：停用 UP（`enabled=0`）、近期窗口重发后目标移出、删除指定目标、删除监控配置、模式切换后不再入选，都由 `selection.refresh_selections` 的“真正离开入选”集合调用 `outbox.retire`，把该目标当前未封存阶段置 `sealed = 1`。`reset=True`（启用开关、模式、`recent_n` 变化）只轮换入选令牌，**持续入选的目标沿用原阶段、原起点与原基线**。
- **封存只结束通知阶段**：归档正文/评论/回复、`archives.generation`、分项 checkpoint 与目标入选令牌都不因此被删除或回退；只读归档 HTTP 仍可读。
- **提交处核验领取时绑定的阶段**：`notification_body_claims` 在 `claim_archive` 时写入 generation → phase，`outbox._active_phase` 同时要求“同一写代次 + 绑定阶段未封存 + 目标此刻仍入选”。正文、一级评论、回复共用这一判定，因此停用/删除后迟到的在途提交**可以保存内容，但不生成事件、不写候选**；旧阶段封存后即使重新入选，旧执行也拿不到新阶段。
- **候选不是队列**：`notification_candidates` 只在原阶段未封存时原子转事件，阶段结束即作废（补齐时被消费，不进投递）；旧候选不因当前已重新入选而生成新阶段通知。
- **已入队不随监控配置级联**：`notification_events`/`notification_deliveries` 不引用 `monitors`/`targets`。停用、删除目标或删除配置后，`waiting_config`、退避中的 `pending`、已领取的 `inflight` 记录继续按 §5 规则投递，成功目标不重发；投递结果只改该目标行，不回写阶段起点、评论起点、正文基线或归档 checkpoint。
- **重新启用/重新入选建立新阶段**：新的 `started_at` 与 `comment_started_at`，`baseline_version = NULL`，以恢复后第一份可信正文重建基线（不追补暂停期间编辑）；评论按新起点过滤（不补暂停期间发表的评论），新起点同秒发表的一级评论/回复仍属“起点及之后”（`math.floor(comment_started_at)` 比较）。新阶段初始化期间（如 `POST /api/sync/initial`）发表的新评论同样有资格；过滤只用来源发表时间，不用采集/扫描时间。
- **普通重启不是新阶段**：`Store.migrate`、新的 API/采集/通知进程实例都不触碰阶段、起点、基线与队列；只有 `refresh_selections` 的真实增删才开/封阶段。未完成领取的恢复按 §5 租约与采集侧恢复规则处理，不重建启用时间。
- **重复保存等价配置 / 重复发布相同窗口**：不轮换入选令牌、不重设起点；真实移出再入选才建立新阶段（令牌、起点都变）。

## 4. 持久状态

| 表 | 语义 |
| --- | --- |
| `notification_phases` | UP、动态、阶段令牌、开始时间、评论起点、当前基线版本、是否封存 |
| `notification_body_claims` | 每次正文领取绑定的写代次与阶段，用于提交时核验 |
| `notification_versions` | 已取得的可信版本，事件去重 |
| `notification_events` | 稳定事件身份：正文按 `(kind, dynamic_id, version)`，评论按 `(kind, dynamic_id, root_id, comment_id)`；所属 UP、消息快照、生成时间；心跳事件的 `dynamic_id`/`version` 就是小时时段身份，`uid` 为空 |
| `notification_candidates` | 待补身份/时间的评论：动态、**所属根**、评论、**原阶段令牌**、发现时间；补齐后原子转事件，阶段结束即作废 |
| `notification_deliveries` | 每目标状态 `waiting_config`/`pending`/`inflight`/`sent`/`expired`、重试时间、领取凭证与租约、脱敏错误、成功时间、`expires_at`（只有心跳写入）、`failures`（真实投递失败次数）与 `last_failed_at` |
| `notification_heartbeats` | 心跳时段身份、生成时间、有效期与对应事件；主键即“每小时最多一条” |
| `notification_alerts` | 告警节流状态：`(category, object)` 主键、最近提醒时间、最近事件；只存固定类别/对象身份，不存凭据或正文 |

- 正文、事件与 UP 群投递记录在**同一事务**提交或回滚；正文失败或未知信号只保留待同步状态。
- 根评论／回复、评论事件/候选与逐群投递记录同样**同一事务**提交或回滚；一处失败整体回滚，内容与通知不会只留一半。
- 心跳时段、心跳事件与系统群投递记录同样**同一事务**提交或回滚：时段已存在则什么都不写。
- 投递结果不回写归档成功 checkpoint；已入队记录不随监控配置删除而级联（新表不引用 `monitors`/`targets`）。
- 到期领取走 `(state, due_at)` 索引，过期租约走 `(state, lease_until)` 索引：业务到期、系统角色到期、过期租约三条查询各自命中索引后再合并排序、限批量（`DUE_QUERY`/`SYSTEM_DUE_QUERY`/`LEASE_QUERY`）；业务与系统分两条查询是为了让心跳/告警不排在业务积压后面（合并后按「系统角色优先，再按到期时间与 id」排序）；不扫描评论表推断新增。
- 过期扫描的已知成本：`expire_overdue` 按 `expires_at IS NOT NULL AND expires_at <= now` 更新，该列没有独立索引，因此这一条会成为每轮领取的额外扫描成本。当前记录规模（每动态每角色一条 + 每类告警一条）不足以要求容量治理，本期不新增索引、**不**因此自动丢弃业务消息（业务记录 `expires_at` 永远为空）；若未来队列长期积压，应先评估索引或归档而不是放宽过期范围。
- 事务样板集中在一处：**本轮改造覆盖的范围**——通知投递的领取/回写/路由复检/心跳登记/告警扫描、检查状态写入（`record_check`/`claim_check_work`/`finish_check_work`/`recover_check_work`），以及采集主循环故障登记——都走 `bili_monitor/transaction.py` 的 `write(store)`（`BEGIN IMMEDIATE` → 提交，异常回滚后原样抛出）；网络请求、退避与日志不在事务内。归档/发现等既有模块仍有自己的 `BEGIN IMMEDIATE` 写法（行为不变，未在本轮合并），不应把本条理解为全仓储已统一。
- 告警以有名字段穿行：`outbox.Alert(category, object_key, reason)`。`object_key` 对应既有的 `notification_alerts.object` 列与消息快照的 `object` 字段（列名与载荷形状不迁移），`object` 不再作为 Python 位置参数名覆盖内建。
- 路由只解析一次：`NotificationConfig.resolve(uid, dynamic_id, role)` 同时给出错误码、地址与可选签名密钥，投递侧用它取代“先查错误、再查地址、再查密钥”三次查询；返回的 `Route` 的 `repr` 不复制地址或密钥（与整份配置一致），队列、日志与快照仍不保存凭据。
- `attempts` 每次**投递结果**回写都 +1（含等待配置复检、过期、租约恢复后的回写），只用于诊断；限速顺延是例外，见 §5.2（顺延不算投递结果，不消耗 `attempts`）。`failures`/`last_failed_at` 只在外部投递真的失败时增长（网络异常、超时、HTTP/业务失败、限流、缺模板），并与 `state`/`error` 一起构成票据 08 的持久可判定事实：`outbox.delivery_failures(connection)` 只读返回 `role`/`kind`/`uid`/`dynamic_id`/`state`/`error`/`failures`/`last_failed_at`，不含地址、密钥或快照。成功不抹掉历史失败事实，等待配置复检不会伪造失败。
- 每条领取事务先丢弃已过有效期的心跳（置 `expired`、错误 `expired`），再领到期记录；`expires_at IS NULL` 的业务记录不受影响，因此共用队列不会误删待发业务消息，也没有过期心跳积压。告警记录的 `expires_at` 永远为空，只按退避重试，不被过期规则丢弃。
- 告警事件身份是 `kind=alert`，`dynamic_id` 为对象身份，`version` 为“类别 + 节流窗口序号”（例如 `collection:16800000`），因此同一对象同一窗口重复登记会被唯一约束兜住；消息快照只含 `category`/`object`/`occurred_at`/`reason` 四个固定字段。

### 5.2 主动限速（票据 13，已交付）

| 参数 | 约定值 | 说明 |
| --- | --- | --- |
| 限速键 | 目的地（实际 webhook） | 同一群共用一份额度；不同群互不占用 |
| 单键额度 | 5 次/秒、100 次/分钟 | 对应飞书自定义机器人官方额度，不再额外加全局层 |
| 系统角色 | 独立额度键 | 心跳与告警不排在业务积压后面，避免被挤到 `expires_at` 之后 |
| 超预算处理 | 顺延 `due_at`（约 1 秒步长） | 记录留在 `pending`；**不算失败**：不动 `failures`/`error`，也不消耗 `attempts`（否则会无端放大后续退避） |
| 与 429 的关系 | 主动限速 + 被动退让并存 | 主动限速降低但不消除 429；`x-ogw-ratelimit-reset` 处理保留 |

实现约定（`notifications/ratelimit.py`、`outbox.defer_delivery`）：

- 记账发生在**请求之前**：占用额度的是外发尝试（含失败与超时），不是成功响应。检查与记账都是内存里的同步操作，因此同一轮并发投递不会超卖同一份额度。
- 超预算只改 `due_at` 并放回 `pending`（`state` 不变）：不消耗 `attempts`、不写 `error`、不增长 `failures`，所以退避与 08 的“持续投递失败”判定不会被限速噪声放大。顺延步长固定 1 秒（与默认轮询间隔相同，但不随 `poll_seconds` 覆盖变化）。
- 代价：每条被顺延的记录多一次短写事务，并占掉本轮批量里的一个名额（本轮不发送）。批量与轮询节拍的既有语义不变。
- 限速在**领取之后的请求之前、事务之外**完成；写回顺延结果是独立短事务。不持有 SQLite 写事务，也不阻塞其他目的地。
- 领取时系统角色（`role = system`）优先于业务记录，并使用独立限速键：心跳（1 条/小时）与告警不会因业务积压被挤到 `expires_at` 之后。独立键意味着**系统群应与业务群使用不同的机器人/群**：如果运维把 `system` 指向与某个业务群相同的 webhook，该目的地会同时持有两份额度（业务 5 次/秒 + 系统 5 次/秒），合计可能超过单机器人额度——这是裁决 4 的已知取舍，不做合并。
- 可计算上界：单次顺延最多一个分钟窗口加一步（61 秒），失败退避上限 300 秒，两者不累加；同键积压按 5 次/秒摊开，`N` 条同群积压的最坏等待约 `ceil(N/5)` 秒（受批量 8 限制时再加少量轮次），队列按 `due_at` 顺序推进，不会出现“永远轮不到”。
- 调参入口：`BILI_NOTIFIER_SENDS_PER_SECOND` 与 `BILI_NOTIFIER_SENDS_PER_MINUTE` 只接受正整数，且**只能调小**（默认值就是平台额度，环境写大不会放宽）；两者互相矛盾时拒绝启动。这只为隔离测试与保守运维准备，不是提速旋钮。
- 日志：超预算只记 `delivery_deferred role=… kind=… reason=rate_limited`，沿用 `notifier_event` 的安全字段约定，不含 webhook、密钥或 URL。
- 边界：窗口状态在进程内存里。单实例 `flock` 保证同一库只有一个投递进程，但**重启会丢失窗口历史**，重启瞬间可能有一小段超额；主动限速也不消除 429（极端积压、多机器人共享额度、平台侧策略变化仍可能被限流），因此 5.2 与 06 的被动退避是并存关系。

## 6. 飞书协议（已核验官方文档，未做真实投递）

- 载荷：`POST {webhook}`，`{"msg_type": "post", "content": {"post": {"zh_cn": {"content": [[...]]}}}}`；只使用 `text` 与 `a` 节点，不使用 `at`/`img` 标签，来源文本不会变成提及或图片。
- 动态变化：两段文本 + `{"tag": "a", "text": "查看动态", "href": {base}/dynamics/{id}}`。
- 新增评论（一级评论与楼中楼回复共用同一模板）：`动态：{标题或动态 ID}` / `评论人：【{昵称或作者 UID}】` / `时间：{北京时间到秒}` / `内容：{原文，按来源换行分段}` / `链接：查看该条评论`。一级评论的链接是 `{base}/dynamics/{id}/comments/{rootId}/locate`（与 02 交付的精确入口一致，不是楼中楼页）；回复的链接是 `{base}/dynamics/{id}/comments/{rootId}/replies/{replyId}/locate`（与 03 交付的精确入口一致，携带所属根与目标回复）。正文为空但有已知媒体时显示 `【图片评论，点击链接查看】`：一级评论看归档媒体；楼中楼回复只看来源响应已给出的图片存在性（归档只存布尔值，不保存图片 URL、不下载上传、不新增上游请求），来源未给或未知时不冒充无图、也不凭空占位。不附父评论全文、不上传图片，回复也不扩大图片采集范围。
- 成功判定：HTTP 200 **且**响应体业务码 `code == 0`（旧版 webhook 兼容 `StatusCode == 0`）；`{"code": 9499}`、非 JSON、HTTP 500 都算失败并保留重试。HTTP 200 也可能只是限流（`11232`/`11233`/`230020`/`99991400`）或签名不匹配（`19021`），都不标成功。
- 可选签名：`timestamp`（秒）与密钥拼成 `"{timestamp}\n{secret}"` 作为 HMAC-SHA256 的 key，对空字符串计算后 Base64；`timestamp`/`sign` 加在请求体外层，消息结构不变。时间戳需距发送时不超过 1 小时，因此每次重试都重新计算。
- 限流：优先使用响应头 `x-ogw-ratelimit-reset`（秒），缺失时退避 60 秒；官方频控为单租户单机器人 100 次/分钟、5 次/秒，超限返回 HTTP 429 或 `11232` 等业务码。
- 告警：不带链接，只有五行固定文本——`告警【{类别}】`、`对象：{对象}`、`发生时间：{北京时间到秒}`、`原因：{固定原因短语}`、`同类同对象 30 分钟内最多提醒一次`。类别与原因都是白名单，未知值退化为 `运行故障`／`未分类`；对象只接受 `[A-Za-z0-9_:.-]`（最长 80 字符），其余退化为 `unknown`，因此消息里不存在自由文本入口。
- 载荷上限：自定义机器人请求体 20 KB，按序列化后的 UTF-8 长度计算，标题与昵称等字段都计入预算。超限时评论先只裁正文并追加 `……内容过长，点击链接查看全文`，仍超限才依次收窄昵称与标题；链接与时间不被截掉，也不拆多条消息。裁掉的只是展示值，不回写归档原文。
