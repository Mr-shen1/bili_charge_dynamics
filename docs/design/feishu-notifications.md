## 2. 消息与路由

### 2.1 消息模板

**动态变化**：

```text
动态【{动态标题或动态ID}】发生变化
链接：查看动态
```

**新增评论**（一级评论与楼中楼使用同一模板，一条评论一条消息）：

```text
动态：{动态标题或动态ID}
评论人：【{昵称或作者UID}】
时间：{YYYY-MM-DD HH:mm:ss}
内容：{评论正文}
链接：查看该条评论
```

规则：

- 使用已归档的真实标题；缺失、空字符串或仅空白时回退动态 ID，不用正文截取伪造标题。
- 时间是评论发表时间，按 `Asia/Shanghai` 显示到秒，不用采集时间或投递时间替代。
- 保留评论正文、换行和“回复 @某人”等上下文；正文、昵称按不可信文本转义，不执行 HTML，不触发任意提及。
- 只有昵称缺失时可显示作者 UID。作者 UID 或有效发表时间缺失则暂缓判定，后续合法补齐后再评估；不猜测是否 UP 本人。
- 已知无文字但有图片的评论显示 `【图片评论，点击链接查看】`。不上传图片到飞书、不附加动态全文或父评论全文；此兜底不扩大现有回复图片采集范围，也不保证尚未归档的图片可见。
- 普通评论完整显示。超过飞书单条消息载荷限制时截断正文，保留其他字段和链接，并追加 `……内容过长，点击链接查看全文`，不拆多条。实现时须按实际消息格式核验官方限制和序列化后的载荷大小，为标题、昵称等字段做安全预算；不得以截断后的文本覆盖归档原文。
- “查看动态”“查看该条评论”必须是真正可点击的链接。消息格式选用支持文本和显式链接的机器人载荷即可，不要求飞书应用或图片上传凭据；具体协议在实施时核验。
- 事件生成时冻结标题、作者、发表时间、正文等消息快照；发送重试不因归档随后更新而改写原事件。信息不全的候选在获得发送资格时才形成完整快照。

### 2.2 路由矩阵

| 事件 | UP 群 | 全员群 | 系统群 |
| --- | --- | --- | --- |
| 动态变化 | 发送 | 不发送 | 不发送 |
| 动态所属 UP 本人的新增评论 | 发送 | 发送 | 不发送 |
| 其他人的新增评论 | 不发送 | 发送 | 不发送 |
| 告警、心跳 | 不发送 | 不发送 | 发送 |

按评论作者 UID 与该动态所属 UP 的 UID 相等判断本人，使用字符串身份，不按昵称或“是否为其他受监控 UP”判断。

服务器配置文件保存每个 UP 的默认 UP 群、全员群及个别动态的路由覆盖，优先采用该动态对应目标角色的覆盖，否则使用所属 UP 的默认值；系统群单独配置。不得把缺失的全员群替换成 UP 群或系统群。

应发送的目标未配置或配置错误时，保留该目标的待投递记录，等待修复后补发，并产生系统告警；其他有效目标照常发送。补配路由不重置通知起点、不触发历史回填。投递记录区分目标角色与实际目的地，成功目标不能因另一群失败而再次发送。

Webhook 及其签名等凭据只在服务端、仓库之外保存，不进入浏览器、业务 API、日志或消息快照；发件箱引用路由身份而不是复制密钥。本站基址由服务端配置，不从不可信请求头推导；链接不包含管理凭据，沿用现有代理访问保护。

## 3. 发送资格、基线与生命周期

### 3.1 动态变化

1. 沿用现有默认 **58～62 秒**页面检查间隔及可信编辑信号判定，不增加正文/图片差异比较。
2. 首次取得正文仅建立通知版本基线；首次发现新动态不发送发布或变化通知。已有归档启用飞书时，以已有可信归档版本作为基线。
3. 确认版本变化后，只有对应新版本正文成功归档，才登记可投递事件；不在仅观察到变化时立即发送。
4. 不等待评论、动态图或评论图全部完成。正文失败保留待同步状态，成功重试后再产生事件。
5. 正文受限、读取失败、计数变化、locator 变化或聚合 `revision` 增加不等于动态内容版本变化。没有正文成功归档时不能借“目标 complete”发送内容变化消息。

保留分钟精度编辑信号的漏检限制；58～62 秒是采样间隔，不是送达承诺，也不保证捕捉每个中间编辑版本。事件对应已成功取得的版本，点击普通动态详情可能看到之后更新的版本，不承诺链接固定历史快照。

### 3.2 新增评论

来源评论计数变化仅触发采集，不直接发送计数消息。找到符合资格的新评论后，在该条评论成功保存、本站可读取且能够定位时允许投递；不等待整轮分页或其他评论成功，不等待媒体完成。

- 总数 10→12 且取得两条新评论：分别登记两条事件。
- 总数下降但未发现新评论：没有新增评论事件，不推断具体评论被删除。
- 已保存的合法评论可以通知，即使随后其他分页失败；这不代表本轮评论集合完整。
- 同一评论的重复采集、补字段或纯编辑不重复产生新增事件。先前因身份/时间不全而暂缓的候选补齐后可以首次产生事件。
- 楼中楼须具备已归档的所属根评论和完整定位身份；暂时无法定位时保留等待状态，满足后再投递，不假装已经可读。
- 不通过扩大采集策略弥补总数抵消、纯评论编辑等既有漏检；通知只能覆盖实际发现且满足资格的条目。

### 3.3 首次启用

持久保存每条动态的通知起点与通知基线，独立于归档完成状态。已有记录在启用时静默建立基线；首次采到的评论须按来源发表时间与起点比较，起点之前的历史评论不通知，起点及之后的新评论保留通知资格。

例：10:00 启用；09:59 发表、10:02 才采到的评论静默；10:01 发表、10:02 归档的评论应通知。不能等首次全量采集结束才设起点，否则会漏掉初始化期间的新评论。

时间缺失的合法归档不能用“首次见到时间”通过此门槛；保存待判定身份与原通知阶段，后续补齐时仍按该阶段起点判断，不重新制造启用时间。来源时间的秒精度不扩大为更精细的先后保证。

### 3.4 停用、重纳入与进程重启

| 场景 | 新事件 | 已入队事件 |
| --- | --- | --- |
| 停用、移出窗口、删除目标或配置、模式切换后不再入选 | 该通知阶段结束；此后在途采集可保存内容，但不再产生该阶段新通知 | 继续投递，不随监控配置级联删除 |
| 重新启用或重新入选 | 建立新通知起点；以恢复后取得的最新状态重建版本基线，不追补暂停期间编辑；评论按新起点过滤 | 旧队列继续，不重复生成已登记事件 |
| 普通采集/通知进程重启 | 保留原起点、基线和去重记录，恢复后按原规则处理 | 恢复领取与重试 |
| 群路由缺失、错误或后续补配 | 不重置起点和版本基线 | 对应目标等待配置并补发 |

事务提交时核验有效通知阶段及目标入选代次；仅在任务启动时检查一次不足以阻止停用后的在途事件。重新入选不能让旧执行以新阶段名义产生通知。恢复时第一份可信当前正文用作重建基线，这个间隙不保证逐次捕捉编辑。

## 4. 事务发件箱与独立投递

### 4.1 提交边界

```text
检查来源信号 → 采集正文 / 评论
    ↓
SQLite 短事务：
  校验归档 owner、版本及通知阶段
  保存对应正文 / 评论
  更新通知基线或待判定候选
  对符合资格的事件去重并写入发件箱及目标记录
    ↓ 同时提交或同时回滚
独立通知进程：领取到期记录 → 事务外请求飞书 → 短事务回写结果
```

资格已满足时，内容保存与事件登记必须同事务成功或回滚。信息待补齐、根评论待就绪等情况，也必须在内容事务中可靠保存候选，后续完成判定与事件登记采用原子转换，避免“内容已存但事件永久遗漏”。

通知进程只扫描有状态/到期索引的候选及发件箱，不反复扫描整张评论表推断新增。采集侧只依赖小接口登记持久事实，不知道飞书请求、限流与模板实现；通知模块封装路由、消息格式、领取、重试和告警。API 的归档写入入口也须遵守相同事务约束；只读 API 与前端不产生通知。

可复用的代码位置（实施时核对活文件，不把当前行号或 schema 版本写死为实施契约）：

| 现有位置 | 接入责任 |
| --- | --- |
| `backend/bili_monitor/storage.py`：`Store.finish_archive` | 正文实际成功提交与版本事件原子关联 |
| 同文件：`save_roots` / `_change_roots` | 页内新根评论、补字段与候选事件原子保存 |
| 同文件：`save_replies` / `_change_replies` | 页内新回复、根关系及候选事件原子保存 |
| `backend/bili_monitor/checks.py`、目标入选代次 | 复用并核验有效阶段；不把观察 revision 当正文通知版本 |
| `frontend/src/app/router.ts` 及评论读取模块 | 新增按 ID 直达定位；保留既有分页和历史阅读行为 |

### 4.2 最小持久模型与不变量

| 记录 | 必须表达的事实 |
| --- | --- |
| 通知阶段/基线 | UP、动态、阶段标识、起点、有效性、初始及已处理的正文版本 |
| 待判定候选 | 评论稳定身份、所属原阶段、缺失条件；可恢复而非只在内存等待 |
| 通知事件 | 稳定事件身份、类型、动态/根/评论身份、内容版本、消息快照、生成时间 |
| 目标投递 | 事件、目标角色/路由引用、待配置/待投递/已领取/成功等状态、重试时间、领取凭证与有效期、脱敏错误 |
| 系统消息状态 | 告警去重与节流时间、心跳时段身份和有效期 |

这是一组语义要求，不预定 SQL 表名、列名或迁移编号。正文事件按动态和已取得的可信内容版本去重；评论事件按动态与评论稳定身份（回复包含所属根身份）去重，不使用计数值或轮次当事件键。跨重启、重扫和重纳入不得重复生成同一已登记事件。

一个事件可以有多个目标投递结果；成功状态单调保持。消息快照、目标状态和重试结果不得反向修改归档成功 checkpoint。队列是持久数据，不是无限容量保证；本期不新增自动丢弃业务消息、备份或存储治理功能。

### 4.3 通知进程

- 独立于 API 和 collector 运行，默认每 **1 秒**轮询到期任务，通过索引、有限批量和短事务领取；只有一个正式投递实例，仍以领取凭证防止失效执行回写。
- 飞书 HTTP、等待与退避均在数据库事务之外。租约过期或进程崩溃可恢复未完成领取；不同目标的失败相互隔离。
- 失败自动退避重试，保存下次尝试时间；平台限流按响应处理。无路由的任务等待配置，不能每秒执行无效 HTTP。具体批量、退避参数和锁参数留实施核验，不更改采集节拍。
- 无积压、无异常、无平台限流时，通常在提交后一个轮询周期内开始投递；实际延迟还含采集、队列、限流与网络耗时，不承诺一秒送达，也不承诺跨群严格同时或全局按发表时间排序。
- 必须核验飞书业务成功响应，不能仅凭 HTTP 200 标成功。失败保留记录而非只写日志。
- 可靠性目标是持久可重试而非飞书端绝对一次：飞书收到但客户端没收到成功响应时，重试可能产生重复；用户已接受此不确定性。内部事件及每目标状态仍须幂等。

### 4.4 为什么不直接接 Kafka 或扫描评论表

直接调用飞书会把外部延迟耦合进采集；“保存数据库后直接发布 Kafka”仍有双写中断窗口，不能单靠中间件解决。扫描评论表推断新增会混淆历史初始化、补采、补字段与已通知状态。事务发件箱利用现有 SQLite 同事务保存内容与投递事实，并以独立进程隔离网络故障，代价是新增队列状态、写入竞争和恢复测试。

未来确有多个消费者或吞吐需求时，可由发件箱转发到中间件；本期不预建通用消息总线或多种投递渠道。

## 5. 本站精确链接

动态消息打开本站动态详情；评论消息必须携带足够的动态、根评论和目标评论身份，自动取得所需归档、展开对应区域、定位并高亮当条评论。一级评论在后续批、回复在后续页、窄屏独立楼中楼及直接打开/刷新都必须可用，不能依赖用户之前浏览过该动态。

现有 `/dynamics/:dynamicId` 和 `/dynamics/:dynamicId/comments/:rootId` 是基础路由，后者本身不能精确定位任意回复。具体参数和读取接口在实施规格中定义，要求按归档身份可靠读取，不能只对当前 DOM 调用滚动而忽略未加载目标；也不能为了定位一次渲染所有评论。

- 精确链接属于主动入口；目标定位完成后，普通阅读、返回与历史恢复仍按既有规则工作，不持续抢占用户滚动。
- 目标确实不存在或归档已清理时，明确提示并提供返回对应动态的入口；不能静默落到评论列表顶部伪装定位成功。临时读取失败与不存在分开，允许重试。
- 前端及只读定位接口只访问本地归档，不借打开链接触发 B 站采集。
- 保留现有代理鉴权；深链接不绕过鉴权，不把凭据嵌入 URL。基址需对实际群成员可达。
- 上线前新增飞书内置浏览器、手机打开与刷新验证，记录实际客户端/设备版本；现有 Linux Chrome、iPhone Safari 的历史证据不替代此次验证。

## 6. 告警与心跳

### 6.1 告警

沿用参考脚本的系统群隔离，保留以下类别：

| 类别 | 边界 |
| --- | --- |
| 凭据失效 | 依据可信失败信号；普通网络失败不冒充登录失效 |
| 采集异常 | 目标检查/同步等真实失败；正常计数变动、采集期间新增评论不是故障 |
| 主循环异常 | 捕获到的运行失败可持久登记；进程被强杀或整机离线时不承诺即时外发 |
| 飞书投递持续失败 | 按持久目标失败状态提醒，不因每次重试无限制造告警 |
| 路由缺失或错误 | 标识受影响目标角色，不回显 Webhook 或签名 |

同一对象、同类持续故障首次发送，此后每 30 分钟最多提醒一次；节流状态跨重启保留，未投递的同类提醒不得堆积成告警风暴。告警采用简洁的类别、对象、发生时间及固定脱敏原因，不包含凭据、来源响应正文或异常原文。不新增故障恢复通知，也不保留飞书图片上传降级告警。

系统群投递失败留本地脱敏日志并按原任务重试，不能递归生成“系统群发送失败”的飞书告警。告警重试与采集重试分别管理，通知退避不改变采集的固定节拍。

### 6.2 心跳

北京时间每小时第 **40 分钟**向系统群生成一次心跳，不受告警的 30 分钟节流影响。同一小时重启不重复生成；错过的心跳时段不追赶，过期心跳不补发，有效期不跨越下一个心跳时段。

心跳报告当前可观察运行状态，不把通知进程存活表述为采集全部正常；不能承诺整机停机时仍能发送心跳或告警。动态变化和评论消息不适用心跳的过期丢弃规则。
