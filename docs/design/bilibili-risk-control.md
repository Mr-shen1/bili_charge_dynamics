## 1. 目标与边界

### 必须保持

- 当前入选动态的**全部可获取一级评论和楼中楼回复**均需归档；不采用“只抓最近 N 条评论／回复”。近期 N 条动态仍只决定目标集合。
- 正文、评论、回复、媒体分别保留真实状态；已得内容不因失败、停止或来源消失而删除。未知、受限及失败不冒充成功空。
- 正常采集以参考脚本的同等工作量为速度基准，先消除额外并发和重复扫描，不以数小时等待作为初始化方案。
- 浏览器归档读取继续只读本地数据；通知基线不代表全量归档成功，沿用[领域词汇](../../GLOSSARY.md)。

### 本次新增

1. 一路重型采集、分页轮转、可验证的持久续采。
2. 楼中楼每次分页请求后至少等待 0.1 秒。
3. HTTP **412／429** 触发跨进程全局暂停、持久冷却、按接口类型探测及人工恢复。
4. 可串联执行过程、包含动态与评论 ID 的结构化日志。

### 非目标

- 不扩大业务错误码分类；业务码 `-352`、`-412` 不因名称相似而自动触发本设计。
- 不顺带修改凭据失效、普通超时／网络／5xx、内容受限／删除的现有处理；不引入新的登录探针、验证码绕过、换 IP 或 Cookie 自动续期。
- 不新增风控页面、前端风控面板或采集按钮；允许为既有操作补充固定的“暂不可用”错误映射。
- 不改通知资格、业务群路由、归档阅读协议、评论检测信号或既有校准策略。
- 不授权生产压测、真实上游复现、代码提交、部署或重启。

本设计是 SRS FR-16 固定节拍及 FR-18“不默认引入退避”的**已确认风控例外**：正常调度保留原信号和节拍，风控期间暂停发送、错过的槽不补发。除该例外及本文的调度／续采变更外，其他策略保持原状。

## 3. 正常采集：串行、轮转、续采

### 3.1 请求调度

使用一个统一的请求协调模块管理发送许可、等待和风控状态，覆盖 HTTPX、Requests、媒体下载及 API 进程入口。调用方只提交接口类型、工作类型和资源上下文，报告响应结果；不各自实现一套熔断或 sleep。

- 全局只推进一路重型归档；调度片是一个可提交的分页／下载步骤，不是整条动态或整栋楼。不同目标在步骤结束后轮转。
- B 站源请求统一排队发送，按参考脚本的串行方向控制在途请求；轻量计数、到期页面检查和必要发现可在分页间穿插，不与后台全量扫描叠加成多路洪峰。
- 同目标重复检查／同步合并，继续遵守忙时跳槽、不积压、不补发。轻量工作不能无限占满队列，历史分页同样须持续推进；有可运行分页时，每轮轻量任务只处理有限批次，再让出一次分页机会。
- API 手动初始化／媒体重试也进入同一许可和目标互斥机制；不能靠另一个进程绕过串行。未风控时保留现有同步入口及统计含义，不顺带改成“返回已登记即成功”。
- 网络、等待、解析和 OSS 上传均在 SQLite 写事务外；事务仅用于领取、更新状态和提交分片。

### 3.2 等待规则

| 请求／处理 | 规则 |
| --- | --- |
| 动态发现 feed | 保留现有每次发送前 0.8–1.5 秒等待，由共享调度执行 |
| 一级评论分页 | 保留现有每次发送前 0.3–0.4 秒等待，包含首屏和空尾确认 |
| 楼中楼分页 | **每次真实分页请求结束后，异步等待至少 0.1 秒**；覆盖首次、增量、重试、尾页确认及探测 |
| 每楼等待 | 对齐参考脚本，只在实际展开楼中楼后保留相应等待；没有发出请求或整楼跳过时，不额外缴纳每楼等待 |
| 会话预热、其他信号 | 不借此次变更增加大幅等待；保留已有缓存和正常间隔，所有真实发送仍经过统一许可 |

0.1 秒不是每个 worker 的独立延时：统一约束楼中楼请求，不能用多任务交错绕过。在等待期间可让出执行权，但不能提前发送下一次楼中楼请求。首次请求前不额外增加这 0.1 秒，最后一页请求后仍执行。若进入冷却，后续等待和发送服从风控状态。

### 3.3 持久续采与完成语义

续采进度与“最新观察是否全部完成”分开持久化：

- 保存目标、locator／内容代次、阶段、分页方向、已处理 ID／页锚点、下一步位置及必要来源计数；复用已有楼级成功记录，不把 UI 阅读 cursor 当成上游续采游标。
- 每页归档数据和对应进度在同一短事务提交。请求失败、风控或崩溃后，保留已提交页，从可验证的断点继续。
- 上游页码不是稳定快照。恢复需校验 locator、页锚点与必要重叠页；漂移时重定位受影响区段，不能仅保存 `pn + 1` 后盲跳，也不能默认全目标重新开始。
- 归档期间的新计数／revision 只登记后续待处理工作，不撤销已确认数据。旧执行仍不得覆盖新观察或清除较新工作；不通过简单放宽 revision 比较来伪造完成。
- 只有对应根页集合及必要楼中楼均得到确认，才推进相应 checkpoint；最新工作未清空时保持 pending／部分完成，状态读取和日志明确表达仍在追赶，不新增前端状态机。
- 本地条数与来源数不强制相等；保留现有不可见／已删除回复的口径处理，不能因两者有差额而无限重扫。
- 入选令牌、领取令牌、归档 generation 和媒体 attempt 的旧执行隔离继续有效。风控暂停优先于“已领取整条链允许结束”：已取得内容可提交，但下一次 B 站发送必须停下。普通停用语义不在本次扩改。

## 4. 风控状态机

### 4.1 状态与持久数据

| 状态 | 普通 B 站请求 | 允许行为 |
| --- | --- | --- |
| `normal` | 按统一调度发送 | 正常采集 |
| `cooldown` | 禁止 | 等待持久截止时间 |
| `probing` | 禁止 | 唯一探测 owner 按接口类型逐一探测 |
| `observing` | 恢复正常调度 | 保留退避档位，累计正常运行观察期 |
| `manual` | 禁止 | 等待执行者通过管理接口发起一轮受控探测 |

SQLite 持久保存全局状态、状态代次、退避档位、进入时间、下次探测时间、最近触发接口／HTTP 状态、探测轮次与结果、owner 租约。采集进程与 API 共用，不按 UP 或动态拆成独立开关。

发送前原子核验状态和许可，响应层在调用方吞掉异常前报告 412／429；预热“忽略异常”也不能忽略风控。探测请求不自动补做尚未获准的预热，避免一次接口探测暗中触发其他网络请求。多个并发迟到响应只推进同一状态代次一次，不能一波 412 连跳多档。发出后无法撤回的请求允许安全收尾，结果仍受原提交校验；不得继续重定向、翻页、预热或重试。

重启保留冷却期限、档位和人工态。进程崩溃后只能在 owner 租约失效后接管，不能同时探测或直接放行；探测途中崩溃需重新确认本轮接口。持久时间用带时区 UTC，进程内等待用单调时钟；不能因时钟异常自动绕过保护。停机时间不算正常运行观察期，重启后观察期重新累计、档位保留。状态存取失败时禁止新发送，返回存储错误，不降级成放行。

### 4.2 冷却阶梯

首次在 `normal` 遇到 HTTP 412／429，进入第 1 档；**每档等待结束都必须执行一轮探测**：

| 档位 | 等待时长 | 到期探测未通过 |
| --- | --- | --- |
| 1 | 1 分钟 | 转第 2 档 |
| 2 | 2 分钟 | 转第 3 档 |
| 3 | 4 分钟 | 转第 4 档 |
| 4 | 8 分钟 | 转第 5 档 |
| 5 | 15 分钟 | 转第 6 档 |
| 6 | 30 分钟 | 转 `manual`，停止自动探测 |

一轮只推进一档，不按 URL／失败页数量累计。HTTP 429 如带合法 `Retry-After`，等待不得短于服务端要求；仍使用相同阶梯和次数，不增加一套 429 恢复机制。

任一轮全部通过 → `observing`，恢复串行、按页轮转的正常调度，不补发冷却期间错过的检查。连续正常采集 10 分钟且确有成功业务请求后 → `normal` 并清零档位；不能以空闲或停机时间证明恢复。观察期间再遇 412／429，进入当前档的下一档；第 6 档后再次触发则转人工，避免无限回到 1 分钟。

`manual` 的人工探测通过后同样进入观察期；失败保持人工态。没有“强行清除风控并直接发送”入口。

### 4.3 探测流程

1. 冻结本轮需要验证的接口集合：**本次触发接口 ∪ 当前待执行任务需要的接口类型**。无关功能不为凑探测而发请求。
2. 使用当前有效凭据和已知有效资源，为每类选择一个最小有效 GET；正常业务与探测走同一解析、许可和等待规则。不能用匿名请求或另一套代理证明正式请求已恢复。
3. 按类型逐一串行发送，不为每个动态 ID、根 ID、页码分别探测。任一未通过立即结束本轮，其余接口不再请求。
4. 通过必须满足该接口现有的成功及资源校验，不能只看 HTTP 200；一类成功不能代替另一类。非 412／429 的探测失败表示“未确认恢复”，不是新识别出的风控类型，但本轮仍不放行并按阶梯处理；普通业务中的其他错误策略不变。
5. 当前样本失效时只允许从本地选择其他已知有效样本，不能在线无限寻找或把 404 当接口恢复。没有可验证样本则本轮未通过，记录固定原因。
6. 探测只验证可用性，不推进归档／评论 checkpoint、工作成功时间或通知基线，不登记业务通知。随后正常采集继续使用原断点与独立提交校验。

### 4.4 接口类型与样本

类型按主机和路径模板划分，query 中不同资源／页码不产生新类型；CDN 分片子域按受信图片域族归类。

| 类型 | 路径／来源 | 最小有效样本 |
| --- | --- | --- |
| 评论计数 | `api.bilibili.com/x/v2/reply/count` | 已存可信 locator 的计数请求 |
| 一级评论 | `api.bilibili.com/x/v2/reply` | 已知目标的一个有效根页 |
| 楼中楼 | `api.bilibili.com/x/v2/reply/reply` | 已知有回复根的一页，不用空根代替验证 |
| 动态发现 | `api.bilibili.com/x/polymer/web-dynamic/v1/feed/space` | 当前 recent UP 的首批，不继续翻页 |
| 动态详情 | `api.bilibili.com/x/polymer/web-dynamic/v1/detail` | 已知动态详情，仍校验目标及作者 |
| 动态网页 | `www.bilibili.com/opus/{id}` | 已知动态的 HTML 请求，使用原解析 |
| UP 资料 | `api.bilibili.com/x/web-interface/card` | 已存 UP 的资料请求 |
| 首页预热 | `www.bilibili.com/` | 原预热 GET，不解释为登录校验 |
| 空间预热 | `space.bilibili.com/{uid}/dynamic` | 已知 UP 的原预热 GET |
| 图片 CDN | `hdslb.com`、`biliimg.com` 受信域族 | 已存有效来源图，验证实际 GET 的状态／媒体响应；沿用下载校验和超时约束，不用 HEAD 代替 GET |

图片域族若分别需要使用则分别验证。需要 detail、网页或图片时不能因成本或曾被拦截就跳过，以计数／资料接口代替。继续遵守现有主机白名单、重定向和 Cookie 隔离；不新增 nav 探针。

## 5. 管理接口与运行反馈

以下为**新增契约**；其中 `GET /api/manage/risk`、`503 SOURCE_RISK_PAUSED` 与按接口探测摘要已由票据 03／04 实施，观察期清零与 `POST /api/manage/risk/probe` 由票据 05 实施（现行契约见[采集契约](../backend/api/collector-api.md#跨进程风控暂停03)、[六档冷却与按接口探测](../backend/api/collector-api.md#六档冷却与按接口探测04)与[恢复观察期与人工探测](../backend/api/collector-api.md#恢复观察期与人工探测05)）：

- `GET /api/manage/risk`（已实施）：只读 SQLite，返回全局 `state`、`since`、`backoff_step`、`next_probe_at`、`observing_since`、`last_trigger` 及最近一轮各类型的 `pending|passed|failed` 探测摘要。不返回凭据、完整 URL、内部 owner／领取令牌，不触发探测。
- `POST /api/manage/risk/probe`（已实施）：仅在 `manual` 请求登记一轮探测，由正式 collector 领取；返回 `202` 表示已登记，**不代表探测成功或已恢复**。同一人工态代次的重复登记幂等，不排多轮；collector 未运行时保持已登记，不由 API 绕过领取直接发送。冷却未到期不提前探测，正在探测不叠加，普通／观察态不把此入口当采集触发器；不适用状态返回固定 `409 RISK_PROBE_NOT_ALLOWED`。沿用现有管理入口的部署鉴权；两个新增入口都不接受 query 或可写状态字段，POST 不允许借请求体清零状态或修改截止时间。
- 普通业务在需要访问 B 站但被保护状态阻止时，返回 `503 SOURCE_RISK_PAUSED`，固定安全提示及当前状态／可空 `next_probe_at`；有未来截止时间时附相应 `Retry-After`。新增 UP 和目标校验不创建半成品、不挂起等待；手动初始化和媒体重试不谎报正常零成功。已经提交的分片保留。
- 纯本地管理、归档读取、已下载数据提交与 OSS 上传继续可用；只阻止下一次 B 站源请求。源图片 URL 不作前端回退，浏览器已有头像策略也不在本次改造。

后台因闸门暂停的工作是“被保护暂停”，不是每个节拍都制造新的来源失败。保留 pending、断点和已有失败事实，不伪造检查／成功时间；现有只读状态可附加保护摘要，前端不新增风控面板。

系统群告警复用既有事务发件箱、去重／节流、路由和通知三态开关。记录首次触发、进入人工态及恢复稳定等生命周期；逐页和逐接口细节留日志，不重复刷群。通知为 `off` 时不得偷偷发送，也不为风控改变通知开关。三类事实已在风控状态转移的同一短事务登记（`risk_triggered`／`risk_manual`／`risk_recovered`），详见[采集契约](../backend/api/collector-api.md#风控生命周期系统告警09)与[通知契约](../backend/api/notification-process.md#33-系统告警0809)。

## 6. 结构化日志

日志沿用现有标准输出／错误输出 → systemd-journald 链路，不新增应用独立 `.log` 文件或文件轮转器。生产机已核实持久落盘，当前没有固定按天保留规则，历史可见范围受全机 journal 容量及可用磁盘约束；不承诺永久保存，也不能将单文件轮转周期当成保留天数。本次只扩展日志内容，若需固定保留期，应另行确定运维配置与容量预算。

本节**有意扩展**现行“日志不含身份／动态／评论 ID”的限制：只放行已校验的业务标识，其他保密约束保留。ID 均以字符串记录，不经浮点数转换。

### 事件与字段

INFO 记录流程边界及每页摘要；WARNING 记录风控触发／探测未通过及原有失败；DEBUG 可补充条目级差异，不以 DEBUG 代替生产必要定位信息。

| 字段 | 规则 |
| --- | --- |
| `event`、`stage`、`result` | 固定事件／枚举，不拼接上游原文 |
| `run_id`、`attempt`、`probe_round_id` | 独立诊断关联号；不得复用内部领取令牌；跨进程／重启后不混淆 |
| `uid`、`dynamic_id`、`root_id`、`reply_ids`／`comment_ids` | 阶段可得时记录；每页打印该页全部已校验 ID，失败至少定位所属动态／楼层 |
| `endpoint_type`、`page`、`direction` | 类型而非完整 URL；页码与正序／倒序／尾页复查分别明确 |
| `fetched`、`new`、`updated`、`skipped` | 区分返回数、新增数、更新数与跳过数，不把重复 ID 算新增 |
| `http_status`、`reason`、`elapsed_ms`、`wait_ms` | 状态经过范围校验，原因固定脱敏；耗时与等待分别记录 |
| `risk_state`、`backoff_step`、`next_probe_at`、`checkpoint_result` | 仅在对应阶段记录，能解释为何暂停、从何处续采、为何未完成 |

流程至少覆盖：发现开始／完成 → 检查信号 → 领取／合并／跳过 → 正文 → 根页 → 楼中楼页 → 分片提交／续采 → 媒体下载／上传 → 分项与整轮结果；以及风控触发 → 冷却 → 每类探测 → 观察／再次冷却／人工态 → 稳定恢复。

每页 ID 批量记一条，不为每条回复刷一行；若单条事件触及日志长度上限，按同一关联号分块，不能静默丢弃定位 ID。没有回复而跳过的楼只记必要摘要。暂停期间不每 2.7 秒重复打印相同警告，状态转移、探测开始／结束和低频汇总足以解释执行流。

示例（虚构 ID）：

```text
INFO event=reply_page_saved run_id=run-demo uid="202" dynamic_id="10001" root_id="20001" page=2 reply_ids=["30021","30022"] fetched=2 new=2 updated=0 elapsed_ms=85 wait_ms=100
WARNING event=source_risk_triggered run_id=run-demo endpoint_type=replies dynamic_id="10001" root_id="20001" http_status=412 backoff_step=1 risk_state=cooldown
INFO event=risk_probe_finished probe_round_id=probe-demo endpoint_type=replies result=passed http_status=200
```

统一禁止新增 Cookie、Authorization、密钥、SDK 凭据、完整 URL／query、请求／响应正文、评论文本、昵称、未审核异常原文或内部领取令牌。原有资料诊断的已审核固定消息目录维持原限制，不借此扩大记录范围。原始 HTTP 调试日志继续关闭。

## 7. 验收标准

以下均是实施后的完成条件，**当前尚未执行**。时钟、传输和随机等待应可注入；使用真实临时 SQLite 验证跨进程／重开行为，禁止为验收在生产诱发风控。

| 编号 | 必须验证的结果 |
| --- | --- |
| RC-01 | 包含 8 目标和万条楼中楼回复的固定样本最终完整归档；没有最近 N 条裁剪，轻量检查与所有可运行分页均有进展 |
| RC-02 | collector、API 初始化、资料／作者校验、预热、图片下载全部经过同一全局许可；重型归档不多路并发，按页轮转且不补发错过检查 |
| RC-03 | 每次楼中楼真实请求后等待至少 100ms，覆盖首次、增量、重试、尾页与探测；整楼跳过不增加无效等待，任务间不能绕过 |
| RC-04 | 采集中断／重启／风控恢复后复用已验证分片；计数持续变化不无条件重扫全部根页；页移动／locator 变化不导致盲跳、假完成或数据丢失 |
| RC-05 | 任一入口 HTTP 412／429 原子触发暂停；迟到响应不连跳档，下一次上游发送被阻止；其他状态和业务错误码不扩大触发分类 |
| RC-06 | 六档等待逐一到期探测，任一接口失败整轮只推进一档，最后失败转人工；真实时间边界、合法 Retry-After、重启剩余时间及租约接管均正确 |
| RC-07 | count 通过而根页／楼中楼／其他必需类型失败时不恢复；按类型而非每个完整 URL 探测；没有样本或非风控失败不冒充通过；探测无归档／业务通知副作用 |
| RC-08 | 全部通过才进入观察；正常采集满 10 分钟才清零，空闲／停机不抵扣；观察期再拦截沿用下一档，人工入口不能提前解除冷却 |
| RC-09 | 保护状态下相关管理操作明确返回暂不可用且不产生半成品；本地读取、管理停用／删除、既有内容提交及 OSS 上传仍正常 |
| RC-10 | 仅用 INFO／WARNING 日志能追踪目标、楼层、分页、断点、等待和每轮探测；每页 ID 完整，凭据、正文、完整 URL 与内部令牌泄漏测试通过 |
| RC-11 | 风控告警遵守既有系统群路由、三态开关与去重；未扩大业务通知资格，未新增风控页面 |
| RC-12 | 报告正常无风控的同负载性能对照与逐类请求数量差异；下述公式仅作非硬性参考目标，未达标或无法建立等价基线不阻塞交付，不以重复请求美化预算 |

### 性能对照口径

用户最新确认的非硬性性能参考目标（取代此前的耗时硬上限）：

```text
T_new <= 1.2 * T_reference + 0.1s * P_replies
```

- `P_replies` 是无故障固定样本中实际必需的楼中楼请求页次数，包含协议要求的尾页确认；不得增加无用重复请求来放宽上限。
- 对照固定目标集合、全部评论／回复、分页大小、来源变化序列、模拟网络延迟、随机种子、运行环境与结果完整性。分别报告总耗时、每类请求数、显式等待耗时、重复读取和最终归档量。
- 参考侧必须处理相同全量工作，不能以“通知基线已建立”替代完整归档。项目独有工作须在对照两侧等量计入；不能等量计入时，只能单列其成本并报告可比链路结果，不能据此宣称整体初始化耗时达标。
- 原始 `script_demo` 文件维持 ignored，不执行、导入或强制纳入版本。基线依据静态核对构造隔离参考 Adapter，记录来源版本／摘要和适配项；该结果是受控回放，不是原脚本生产实测。无法证明工作量等价时，明确标注整体性能未验收并报告可比范围，不阻塞票据或整体交付。
- 该公式不是硬性验收或回归门槛，不保证真实网络耗时，也不是 B 站安全频率。保留一次有界的对照与开销分析，不为达到公式反复调参或陷入优化循环；未达参考目标如实披露，不因此阻塞交付。全量完整性、正确性与 100ms 等安全等待要求不变。真实来源验证须另行授权，不以压测平台上限作为交付门槛。
