# #34：用户浏览器成功响应与服务端拒绝的对照

## 用户提供的证据

用户提供浏览器直接访问同一授权 UID 的 card URL 截图。截图可见顶层整数 `code: 0`、`message: "OK"`，以及 `data.card` 中匹配目标的字符串 mid、非空 name、HTTPS face；不在此复制身份、昵称、头像 URL、签名或原截图。

这份字段结构符合当前生产资料解析约束。若后端得到相同状态正常的 JSON，不应因上述字段结构而返回 PROFILE_UNAVAILABLE；此前服务端的实际失败发生在收到 HTTP 412、进入 JSON 解析之前。

截图证明浏览器在其请求上下文中获得了可读资料，**不能把服务端失败泛化成接口整体不可用或目标 UID 无效**。截图本身没有浏览器 Network 状态、缓存/时刻、请求 headers、登录/站点会话或网络出口证据，不推断这些信息。

## 与服务端证据并存

[私有留样](private-response-capture-2026-10-21.md)来自新的短时 18446 诊断实例，使用同一生产 app 与真实出站客户端；其 412 HTML 明确声明安全风控拒绝。该新客户端没有复制浏览器或 18444 已有客户端的会话状态，不能宣称两侧请求上下文相同。

[协议调查](profile-412-investigation.md)只确认服务端默认 HTTPX 请求、无显式 headers 和 trust_env=False；SDK 的 headers 差异不是根因证明，也不是擅自伪装浏览器的授权。

## 用户补充的环境事实

用户确认浏览器与后端同一台机器，浏览器已登录 B站；使用系统代理，但 B站不走 VPN。这是用户说明，不是本次主动抓取的网络出口/headers 证据；不因此声称已测得两端完全相同的网络栈或出口。

当前生产实现没有 B站登录 Cookie/token 配置入口，也不会从浏览器读取会话；card 查询只显式传 `mid`，没有设置登录 Authorization/access token 或 WBI 签名。HTTPX 客户端可能自动保存来源响应设置的匿名 Cookie，不等于拥有浏览器登录态；本次全新取样客户端没有导入浏览器 Cookie。没有读取、请求或回显用户凭据，也没有据此认定缺登录态就是 412 的具体原因。

## 下一步：先问非敏感事实，不新增请求

优先区分以下差异，暂不认定哪项为原因：

1. 浏览器与服务端是否同一机器、同一正常网络出口；浏览器是否使用系统/扩展代理或 VPN。后端 trust_env=False 不会自动使用环境代理。
2. 浏览器是否已登录 B站，以及可能存在站点会话；未登录不代表没有匿名站点 Cookie。
3. 浏览器与 HTTPX 的正常请求协议/默认 headers、连接实现及采样时刻/缓存是否相同。

仅询问是/否与部署位置，不索要 Cookie、认证头、完整 HAR、Copy as cURL、代理口令或密钥。没有要求用户刷新/开无痕页制造新请求，也没有自行请求 B站、切换身份、代理、UA 或来源接口。本条只记录截图对照，不修改业务代码，不宣称真实新增已经修复。
