# 07：会话直达、刷新与返回阅读位置

Status: resolved
Blocked by: 05, 06

依据：[实施规格](../spec.md)。覆盖 UI-11、UI-15 的会话导航与精确入口组合。

## 交付内容

用户从热度或时间排序的回复第 N 页进入会话后，返回能恢复原排序、页码和位置；新会话地址直达/刷新也能独立读取，无来源时安全回到所属回复详情。

## 验收条件

> 全部条件已按本票范围实现并取证：`pnpm check`（typecheck + **30 文件 / 336 passed**）、`pnpm check:dist`、`pnpm test:e2e:location`（**13 passed**，API 4178 / web 4325）、`pnpm test:e2e`（**224 passed / 15 skipped**，临时配置副本 4426/4427/4428；定位/楼中楼子集在最后改动后复跑 61 passed）、`pnpm test:delivery`（本机 Nginx 三阶段全绿）、`pnpm test:nginx-parity` 均通过。未验证项（视觉基准与黄金图、真机、真实上游、目标机部署交付）见证据 §6；后端未改动，未重跑后端全量。

- [x] 新阅读身份包含动态、根评论及入口回复，使用 conversation 命名，与应用 session 状态明确区分；不以页码或昵称充当身份。
- [x] 有效来源保存回复访问的排序、页码、阅读位置与恢复所需内容；点击 `‹ 会话列表` 或浏览器返回恢复该次访问，不能只恢复坐标却先显示第 1 页。
- [x] 从热度页进入并返回不调用时间定位去覆盖原热度页码；主动通知定位仍使用既有时间序，两种意图明确分离。
- [x] 直达或刷新会话可仅依赖 URL 和只读接口获得内容；无有效来源时 replace 到所属回复详情的时间序第 1 页，不回错动态、不退出本站、不构成返回循环。
- [x] 新主动进入会话从起点和第 1 页开始；入口回复在后续页时不自动跳过前文。历史前进/后退不串用另一根、另一动态或另一访问的快照。
- [x] 初始读取、局部错误、缺失上下文与重试可分别理解；读取失败不丢失已有来源快照或把对话不存在伪装为永久加载。
- [x] 新恢复仅限当前有效浏览访问；未改变的独立回复直达/刷新首屏语义和图片历史优先关闭规则继续成立。
- [x] 实际 API＋隔离 SQLite 的生产浏览器覆盖跨页分支、热度返回、按钮/浏览器返回、刷新、复制 URL 直达、无来源和受控迟到响应；另覆盖“通知定位页的时间序第N页/目标锚点→查看对话→返回”，恢复该次定位访问与位置，而非重置第1页或重复主动定位。
- [x] 更新导航/静态路由回退覆盖与接口客户端说明，不把纯 mock 页面通过当作直达协议已验收。

## 依赖理由

05 提供真实热度页码和定位兼容，06 提供真实会话身份与页面。只有两者都存在，才能验收“从热度后续页进入会话再恢复”的完整用户路径。

## Answer

- **结论**：会话往返恢复已交付并取证。**不改任何归档 HTTP 契约**（无新接口、无新表、无迁移、无索引、无采集），只在客户端补“会话来源的回复访问快照”与导航语义。
- **定稿语义**（[客户端契约](../../../docs/backend/api/archive-api-client.md#阅读改版-07-增量会话往返恢复回复访问)）：
  - 会话身份仍是 `dynamicId + rootId + replyId`（URL、`conversation` 命名），与应用 session 状态无关；会话页不存快照，永远从第 1 页/起点开始。
  - `ReplyVisitSnapshot` 属于独立回复访问（窄屏楼中楼页与窄屏回复精确入口），按历史记录（`pageEntryId`）存在导航协调器的内存访问表：区域身份（动态 + 根评论）、排序、页码、已读批次与失败原因、定位意图、阅读位置；不跨重启/跨标签页。
  - `‹ 会话列表`、浏览器返回与前进恢复该次访问：先按快照的排序、页码与内容渲染再按锚点落点，不重读第 1 页、不重新定位；热度第 N 页返回仍是热度第 N 页；通知定位访问返回仍是那次时间序定位页与高亮。
  - 无来源时 `replace` 到所属回复详情的时间序第 1 页；新访问（直达/刷新/再次进入同一地址）从第 1 页与页面顶部开始。
  - 区域身份不符的快照一律不采纳，互不串用；恢复时的失败保留内容与局部重试。
- **实现位置**：`frontend/src/app/snapshots.ts`（`ReplyVisitSnapshot`／`replyVisitRegion`／`adoptReplyVisitSnapshot`）、`frontend/src/app/navigation.ts`（`saveReplyVisitSnapshot`、`replyVisitSnapshot`、`isReplyVisitPath`、`openConversation`／`returnFromConversation`）、`frontend/src/dynamics/useReplyPage.ts`（`restored` 初始状态）、`frontend/src/pages/CommentThreadPage.vue`（采纳/保存、恢复不重新定位）、`frontend/src/pages/ThreadPage.vue` + `router.ts`（按访问标识重建楼中楼页）、三个交付脚本的回退清单、`tests/unit/conversation-navigation.test.ts`、`tests/e2e-location/conversation.spec.ts`、`tests/support/app.ts`、`tests/e2e/thread.spec.ts`。

## Comments

- 快照放在导航协调器的访问表而不是组件里：历史记录只写轻量访问标识，前进/后退回到同一 `pageEntryId` 才能取回同一份快照；组件内状态在路由卸载时就没了，无法区分“同一次访问”与“同一地址的新访问”。
- 快照以“动态 + 根评论”为区域身份，而不是只用 `pageEntryId`：路径与访问标识已经能隔离，身份再挡一层，避免将来复用同一访问记录时把另一根的排序和页码带过去。
- 恢复时不重读，与详情/列表快照同策略：先看到的就是离开时的内容，代价是归档在此期间变化时内容可能略旧；翻页或重试即取最新。只有上次没读完（`loading`／`cancelled`）的访问才补读同一页。
- 恢复不 `arm()` 定位，但保留 `locating` 标记：通知直达的目标返回后仍高亮（`data-located`），但不会重新滚动抢视口；显式点“重试”且当前没有内容时才重发定位。
- 楼中楼路由加了按 `pageEntryId` 重建的外壳 `ThreadPage`：不加时，同一路由记录换参数会被 Vue 复用实例，状态会从另一根/另一访问串过来。
- 静态回退清单补会话页时发现两处与本票无关的陈旧断言（01 改文案后的 `UP 123 归档`、管理页 401 提示变多条后的严格模式选择器）；只做覆盖修复，没有改变任何被测行为，理由写在证据 §7。
