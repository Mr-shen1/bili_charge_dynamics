    # B 站限流／风控保护与全量归档续采实施规格

## 问题陈述

首次初始化动态时，用户遇到 B 站 HTTP 412 拦截。初始化产生大量评论及楼中楼请求，多个同步与检查、发现叠加；拦截发生后，其他目标及失败重试仍可能继续请求。用户既无法及时获得完整归档，也无法仅凭现有日志准确知道哪条动态、哪个楼层、哪一页正在执行或反复失败。

参考脚本由用户报告可长期在线运行，但当前实现不等价于它的串行调度和跨轮推进。直接显著降低频率、让初始化拖至数小时，不是用户接受的解决方式；只抓最近若干条评论也不满足全量归档要求。需要消除并发及重复扫描造成的请求放大，并在真实遇到限流后统一暂停、逐接口验证恢复，而不是继续冲击上游。

## 解决方案

保持当前入选动态全部可获取的正文、一级评论、楼中楼回复及既定媒体归档范围。重型采集改为一路、按分页步骤在目标间轮转；轻量检查可穿插，历史归档也持续推进。保留可验证的持久分片进度，使热帖新增、分页失败、风控和重启不再无条件推翻已完成工作。楼中楼每次实际分页请求后新增至少 0.1 秒等待。

仅以 HTTP 412／429 触发跨进程统一保护，覆盖采集与管理入口、会话预热及 B 站图片下载。按 1、2、4、8、15、30 分钟逐档等待，每次到期均按当前所需接口类型串行探测；全部通过后才恢复，一轮任意失败则继续下一档，最后失败转人工。恢复后连续正常采集 10 分钟才清零档位。

使用结构化日志记录完整流程、业务 ID、每页结果、断点和探测状态；通过现有系统告警和管理接口反馈，不新增风控页面。冷却时需要访问 B 站的既有操作明确返回暂不可用，本地归档阅读、纯本地管理、已下载数据提交和 OSS 上传继续工作。

## 用户故事

### 全量归档与正常运行

1. 作为监控使用者，我希望已选动态现有及后续可获取的一级评论都能归档，以便不因启用较晚而丢掉历史讨论。
2. 作为监控使用者，我希望每栋楼中全部可获取回复都能归档，以便三条预览或最近若干条不会被误认为完整内容。
3. 作为监控使用者，我希望“近期 N 条”只限制动态目标集合，以便不会暗中变成评论或回复条数上限。
4. 作为监控使用者，我希望正常初始化对齐参考脚本同等全量工作量的速度，以便保护措施不会把正常采集拖慢一个数量级。
5. 作为监控使用者，我希望正文、根评论、回复和媒体分别表达实际完成情况，以便一项成功不会掩盖其他未完成项。
6. 作为归档阅读者，我希望来源失败、删除或停止监控不清除已取得内容，以便已有归档仍能阅读。
7. 作为监控使用者，我希望不同动态按分页轮转，以便一条有上万回复的动态不会挡住其他目标。
8. 作为监控使用者，我希望同一时间只有一路重型归档，以便多条动态初始化不会叠加成请求洪峰。
9. 作为监控使用者，我希望轻量检查能在分页间获得机会，以便耗时归档不阻止发现后续变化。
10. 作为监控使用者，我希望持续到来的轻量检查也不能饿死历史分页，以便全量归档最终能够推进。
11. 作为运维者，我希望忙碌或冷却期间跳过的检查槽不积压补发，以便恢复时不形成新的瞬间流量。
12. 作为运维者，我希望手动初始化、媒体重试与后台采集遵守同一发送许可，以便 API 进程不能绕过正常采集约束。

### 分页等待、续采与一致性

13. 作为监控使用者，我希望楼中楼每次真实分页请求后至少等待 0.1 秒，以便连续翻页不再无间隔请求。
14. 作为运维者，我希望首次、增量、失败重试、空尾确认及探测都遵守这项等待，以便替代路径不能绕过保护。
15. 作为监控使用者，我希望没有请求回复页或整楼跳过时不额外等待，以便保护不会在无网络工作的楼层上浪费时间。
16. 作为监控使用者，我希望每页数据与进度一起保存，以便中断后不会反复下载已提交的全部内容。
17. 作为监控使用者，我希望根评论和楼中楼都能从可验证断点续采，以便大目标不因一个失败页重新全扫。
18. 作为监控使用者，我希望热帖持续新增时保留既有进度并登记后续增量，以便归档不会因观察版本不断变化而无法收敛。
19. 作为监控使用者，我希望上游页移动时先校验锚点和重叠页，以便续采不会盲目跳页导致缺失。
20. 作为监控使用者，我希望评论定位资源改变时旧断点得到识别，以便不同资源的数据不会被错误拼接。
21. 作为监控使用者，我希望旧执行不能清除新观察或覆盖新领取，以便并发检查及迟到响应不会制造假完成。
22. 作为监控使用者，我希望仍在追赶最新变化时保留未完成状态，以便部分归档不会被误标为全量完成。
23. 作为监控使用者，我希望来源数与本地数的已知口径差异被如实记录，以便不可见或已删除回复不会导致无限追赶。
24. 作为运维者，我希望进程退出后仍能继续已保存的工作，以便重启不等于重新初始化。

### 统一风控保护

25. 作为运维者，我希望任一 B 站源请求遇到 HTTP 412／429 都能触发全局暂停，以便其他任务不再继续冲击上游。
26. 作为运维者，我希望暂停同时覆盖发现、计数、正文、详情、评论和回复，以便只暂停报错动态不会留下其他请求入口。
27. 作为运维者，我希望首页／空间预热及图片 CDN 下载也遵守暂停，以便隐藏的辅助请求不会破坏冷却。
28. 作为运维者，我希望 API 与 collector 共享保护状态，以便不同进程不会各自继续发送。
29. 作为运维者，我希望一波迟到的 412 不会连续推进多档冷却，以便并发响应不会迅速耗尽恢复机会。
30. 作为监控使用者，我希望已开始请求取得的内容仍能安全保存，以便风控不抹去刚取得的有效数据。
31. 作为运维者，我希望出现风控后不再自动翻下一页、重定向或补做预热，以便已领取的整条链不会继续请求。
32. 作为运维者，我希望暂不扩大其他业务码、网络故障和受限内容的分类，以便本次修复不改变其他既有行为。

### 冷却、按接口探测与恢复

33. 作为运维者，我希望依次等待 1、2、4、8、15、30 分钟，以便恢复节奏明确且逐步保守。
34. 作为运维者，我希望每档等待结束都执行一轮探测，以便系统不会只等时间到就直接恢复正常流量。
35. 作为运维者，我希望按接口类型而非每个带不同 ID／页码的完整 URL 探测，以便覆盖不同拦截范围又不制造探测洪峰。
36. 作为运维者，我希望计数接口成功不能代替根评论、楼中楼、详情或图片接口成功，以便局部恢复不会被误判为整体恢复。
37. 作为运维者，我希望只验证触发接口与当前待执行工作实际需要的类型，以便无关功能不会增加额外请求。
38. 作为运维者，我希望探测使用当前正式凭据、代理策略和有效资源，以便探测结果能代表后续真实采集。
39. 作为运维者，我希望探测串行执行并在任一类型未通过后立即停止，以便仍被拦截时不继续尝试其余接口。
40. 作为运维者，我希望业务解析与资源校验也通过才算探测成功，以便 HTTP 200 的验证页或错误数据不会导致误恢复。
41. 作为运维者，我希望没有有效样本或暂时无法验证时保持暂停，以便系统不会把未知情况当成恢复。
42. 作为监控使用者，我希望探测不推进归档成功状态、通知基线或业务通知，以便恢复检查不会伪造成内容已采集。
43. 作为运维者，我希望每轮失败只推进一档，最后一档仍失败则等待人工，以便系统不会无限自动探测。
44. 作为运维者，我希望全部必需接口通过后才进入正常采集观察期，以便恢复有明确的整体条件。
45. 作为运维者，我希望连续正常采集 10 分钟后才清零档位，以便刚恢复又被拦截时不会反复从 1 分钟开始。
46. 作为运维者，我希望观察期间再次触发时沿用下一档，以便短暂恢复不会掩盖持续风险。
47. 作为运维者，我希望冷却期限、档位和人工态持久化，以便重新部署、重启或崩溃都不能绕过保护。
48. 作为运维者，我希望探测拥有唯一可接管的 owner，以便进程故障后不会出现多路探测或无人恢复。
49. 作为运维者，我希望停机和无请求的空闲不抵扣正常观察期，以便系统不会凭时间流逝就宣称恢复稳定。

### 管理操作与可用性

50. 作为管理使用者，我希望冷却时新增 UP 或校验指定动态明确返回暂不可用，以便操作不会静默请求、长时间挂起或生成半成品。
51. 作为运维者，我希望被暂停的手动初始化或媒体重试不返回伪成功统计，以便能判断本次操作实际未执行完成。
52. 作为管理使用者，我希望停止、删除、读取等纯本地操作仍可用，以便风控不会阻止我控制系统。
53. 作为归档阅读者，我希望风控期间已有动态、评论和回复仍可阅读，以便源站不可用不会变成本站不可用。
54. 作为运维者，我希望已下载数据能落库并继续 OSS 上传，以便不依赖 B 站的工作不被无谓暂停。
55. 作为运维者，我希望通过只读管理接口查看保护状态、截止时间及各接口结果，以便无需新增页面就能排查运行状态。
56. 作为运维者，我希望人工态能登记一轮受控探测，以便处理完外部问题后有明确恢复入口。
57. 作为运维者，我希望重复点击或重复请求不会登记多轮探测，以便人工操作也不能形成并发冲击。
58. 作为运维者，我希望没有强制跳过校验的恢复入口，以便手动操作不会意外绕过保护。

### 流程日志、告警与验收

59. 作为运维者，我希望生产日志串起发现、检查、归档各分项、分片提交、媒体和整轮结果，以便大体还原完整执行流程。
60. 作为运维者，我希望日志包含 UP UID、动态 ID、根评论 ID 及每页回复 ID，以便能定位到真实资源而不只看到流水号。
61. 作为运维者，我希望每页批量记录全部已校验 ID，而不是每条回复刷一行，以便既可定位又不产生无意义日志洪峰。
62. 作为运维者，我希望请求、等待、分页方向、数量变化和续采结果分别记录，以便能区分慢请求、主动等待和重复扫描。
63. 作为运维者，我希望冷却、每类探测、再次退避和稳定恢复都有关联日志，以便跨进程和重启后仍能理解执行过程。
64. 作为系统使用者，我希望日志不包含 Cookie、密钥、正文、完整 URL 或内部领取令牌，以便增加定位信息不等于泄漏敏感数据。
65. 作为运维者，我希望告警复用系统群、去重及现有通知开关，以便既能感知风险又不会刷群或越过关闭通知的选择。
66. 作为系统使用者，我希望本次修改不改变动态变化、新增评论的通知资格和通知起点，以便保护恢复不会补发或重复通知历史内容。
67. 作为维护者，我希望迁移保留归档、成功媒体、有效阅读 cursor 和未完成工作，以便升级保护机制不会损坏已有数据。
68. 作为维护者，我希望在隔离环境复现跨进程暂停、重启和热帖变化，以便无需再次请求真实 B 站来验证修复。
69. 作为维护者，我希望性能按同等全量工作量比较，并单独核算新增 0.1 秒等待，以便保护开销透明而不是通过改换基准隐藏。
70. 作为维护者，我希望没有等价基线时明确标为未验收，以便普通冒烟通过或通知基线日志不会被误当成速度达标。

## 实施决策

1. **统一请求协调模块**：集中封装发送许可、等待、接口分类、风控状态和响应报告。HTTPX、Requests、图片下载及 API 来源访问都经过同一 Interface；业务调用方不分别实现熔断。优先复用既有来源传输 seam，只在确有不同传输实现处提供 Adapter。
2. **串行与公平性**：全局一路重型归档，按可独立提交的分页／下载步骤轮转目标；B 站源请求统一排队、串行方向控制发送。轻量检查与发现穿插且批次有限；正常节拍保留忙时跳槽、不积压和不补发语义，不把所有目标处理完才开始下轮。
3. **正常等待**：feed 发送前维持 0.8—1.5 秒，根评论每次发送前维持 0.3—0.4 秒。每次真实楼中楼分页请求结束后异步等待至少 100ms，覆盖所有模式和探测，第一请求前不加该等待、最后一页后也执行。等待统一协调，其他任务不能交错绕过；没有展开请求或整楼跳过时不加每楼等待，实际展开后的楼级等待对齐参考策略。
4. **分片提交**：逐页保存归档数据及对应续采进度，使用同一短事务。进度包含资源定位、处理代次、阶段、方向、已确认 ID／锚点、下一位置和必要来源计数；不是将读取端 cursor 复用为上游游标。
5. **断点验证与热帖收敛**：恢复先核验锚点、locator 与重叠页，漂移时重定位必要区段，不盲跳页码。新观察只追加后续工作，不推翻已确认分片；旧执行不能吞掉较新 revision 或清除新领取。全量最新工作未完成仍为 pending／部分完成，不简单放宽版本比较。
6. **保留既有一致性规则**：正文、根、回复和媒体 checkpoint 独立；来源数与本地数不强制相等。入选代次、执行领取、归档 generation、媒体尝试的隔离继续有效，不删旧成功内容。普通停止规则不扩改；风控必须阻止已领取链上的下一次源请求。
7. **触发与覆盖**：仅真实上游 HTTP 412／429 触发保护，不扩大其他 HTTP 状态或业务错误码分类。覆盖业务接口、首页／空间预热、图片 CDN，以及管理操作和手动同步。响应层先报告触发再交给原业务错误处理，不能被预热忽略异常或不同客户端吞掉。
8. **跨进程持久化**：使用共享 SQLite 保存全局状态、状态代次、档位、截止时间、触发原因、探测结果及 owner 租约；API 与 collector 共用。发送前原子核验许可，迟到风控响应按代次合并；状态不可读写时禁止新源请求，不降级放行。网络、等待、解析及 OSS 上传不占写事务。
9. **状态机**：使用 `normal`、`cooldown`、`probing`、`observing`、`manual`。六档等待为 1、2、4、8、15、30 分钟，每档到期都探测；一轮失败只推进一档，第六档探测仍失败转人工。合法 `Retry-After` 不得被更短的本地等待覆盖。
10. **探测集合**：本轮触发类型与当前待执行任务所需类型取并集，按主机／路径模板分类，不按资源 ID 或页码扩增类型；受信 CDN 按图片域族区分。计数、根页、楼中楼、feed、detail、网页、资料、预热及实际需要的图片类型均不能互相替代。
11. **探测执行**：仅唯一 owner 串行发出每类最小有效 GET，使用正式凭据、代理及解析校验。任一类型未通过立即结束本轮，全部通过才恢复。探测不暗中触发未获准预热，不提交归档成功、推进通知基线或生成业务通知；无样本及非 412／429 的探测失败表示尚未确认恢复，仍不放行，但不扩大普通错误分类。
12. **恢复与重启**：全部通过后进入观察态，连续正常采集 10 分钟并有成功业务请求才清零。观察期再被拦截进入下一档，第六档后再触发转人工。重启保留期限、档位和人工态，停机不计正常运行，观察期重新累计；租约失效后方可接管探测，接管重新确认本轮类型。
13. **状态读取与人工入口**：新增只读 `GET /api/manage/risk` 和人工态登记探测的 `POST /api/manage/risk/probe`，沿用管理入口部署保护。后者 `202` 仅表示已登记，由 collector 领取；重复登记幂等，不允许冷却未到期提前探测、叠加多轮或直接清零。状态不适用返回 `409 RISK_PROBE_NOT_ALLOWED`；不引入异步 UP 校验状态机或风控页面。
14. **现有操作遇到保护**：仅在操作实际需要访问 B 站时返回 `503 SOURCE_RISK_PAUSED`、固定安全提示、当前状态和可空下次探测时间；有未来截止时间时附 `Retry-After`。新增身份和目标关联不留半成品，手动同步不伪装成正常零成功；未风控时保留原同步入口及统计口径。
15. **不依赖源站的工作**：纯本地读取、管理停止／删除、已得内容提交及 OSS 上传不受暂停影响。后台工作保留 pending 与断点，不每个节拍制造新失败，也不伪造检查／成功时间。
16. **结构化日志**：INFO 覆盖阶段及每页摘要，WARNING 覆盖风控与原失败；记录独立关联号、业务字符串 ID、接口类型、页码、方向、数量、耗时、等待与结果。每页所有已校验评论／回复 ID 批量输出，超长分块而不静默丢失；不为每条回复单独刷 INFO，也不在暂停期间高频打印相同警告。
17. **日志保密与通知隔离**：有意放行已校验业务 ID，不放行 Cookie、密钥、正文、完整 URL／query、任意上游消息或内部领取令牌。复用系统群告警与已有去重、节流、三态开关，不改变动态变化／新增评论的业务通知资格，不在通知关闭时偷偷发送。
18. **迁移与契约同步**：实施时确定迁移版本及内部表结构，不预占版本号。原子迁移、未来版本拒绝、归档保留和有效阅读 cursor 保持；新增管理错误及必要固定提示同步契约与测试，其他故障处理、鉴权和正常采集信号不扩改。

## 测试决策

### 主测试 seam

以**实际 API／采集运行装配的公开行为**为主测试 seam：启动真实应用和 collector，使用真实临时 SQLite，只在外部上游传输及受控时间位置替换依赖。HTTPX、Requests、图片及 OSS 的不同传输由 Adapter 接入同一受控场景，保留生产解析、调度、归档和提交路径。

优先复用 `create_app` 与 TestClient 的实际应用装配，以及 Collector 的 `check_once`、`execute_pending`、`run` 入口；不为每个分页函数新造公开测试 Interface。既有 `ControlledClock` 提供时间控制，图片仍复用媒体传输注入，OSS 上传明确不受源站闸门限制。跨进程场景沿用真实进程 spawn 与同一临时数据库，不将进程内共享字典或 FakeProcess 当跨进程保护。

新增的风控状态、owner 租约和页锚点进度是生产持久能力，不给它们另造 FakeStore；通过同一高层装配和关库重开验证。必要内部注入只控制时钟、随机等待、传输响应与进程交错，不将内部调用序列当产品契约。新增 100ms 页后等待应有可控时间入口，不能被现有仅覆盖 0.3—0.4 秒楼级等待的测试替身误吞或错误约束。

本轮按“直接综合、不再访谈”完成测试设计，不声称用户另外确认过具体 fixture 或测试函数。

### 好测试的标准

- 驱动真实初始化、发现、检查、分页及恢复调用链，观察公开响应、来源请求账本、重开后的持久状态、归档读取、日志和通知结果。
- 断言“没有发送不允许的上游请求”“没有遗漏可获取内容”“未假完成”和“进度持续推进”，而不是私有函数被调用几次或某张内部表恰有特定名称。
- 外部响应使用脱敏固定 fixture，不连接真实 B 站；长时间等待用受控时钟推进，避免实际等待半小时或依赖不稳定墙钟。
- 每个回归用例能在原缺陷模式下失败，避免只测一个隔离 pacer，而遗漏多个调用方、不同客户端及 API／collector 同时运行的放大路径。
- 正常错误与已有版本／生命周期回归一起验证，确保新增保护没有把所有失败都改判为风控。

### 场景与验收映射

以下落实正式设计 RC-01—RC-12，结果均须保留可重复执行方式、样本范围及未验证项。

1. **全量与公平调度（RC-01、02）**：至少 8 个目标、其中含万条楼中楼回复；检查持续到来时，各目标分页仍有进展，归档完整且重型工作不并发；API 手动入口不能旁路。
2. **100ms 等待（RC-03）**：覆盖首次、增量、失败重试、尾页复查、探测、最后一页及整楼跳过；通过请求发送／完成时间账本验证，多个任务与进程无法交错绕过。
3. **续采与持续变化（RC-04）**：在根页及回复页中断、重开、改变来源计数、移动分页、改变 locator；保留已提交内容并验证断点，没有无条件全目标重扫、盲跳或假完成。
4. **所有入口触发（RC-05）**：逐类注入 HTTP 412／429，同时运行 API 和 collector；预热吞异常、媒体独立 client、重定向及迟到响应不能漏报或继续发请求。对照普通错误及非零业务码不扩大触发范围。
5. **持久状态与阶梯（RC-06）**：验证六档到期均探测、失败一次只升一档、末档失败转人工、合法 Retry-After、截止时间边界、租约接管、重启及不可读写时禁止发送。
6. **按接口探测（RC-07）**：计数通过而楼中楼失败必须仍暂停；同一类型多 ID 不逐一探测，必需的不同类型均需通过。验证业务无效 200、样本缺失、串行失败短路以及没有隐式预热／业务提交。
7. **观察及人工恢复（RC-08）**：全部类型通过后恢复，连续成功运行 10 分钟再清零；空闲／停机不抵扣，期间再风控沿用下一档。重复人工登记幂等且不能提前解除冷却。
8. **可用性与契约（RC-09）**：新增 UP、目标校验、initial 和媒体重试在保护状态下明确暂不可用；纯本地读取、停用／删除、已下载数据提交和 OSS 上传保持可用；无半成品及伪成功统计。
9. **日志与脱敏（RC-10）**：仅靠 INFO／WARNING 能串联动态、楼层、页、断点和探测；批量 ID 无遗漏，长批次安全分块；秘密、正文、完整 URL 与内部令牌的负向泄漏断言通过。
10. **告警与既有通知（RC-11）**：复用系统群去重／节流与通知三态；关闭通知不发送，探测不产生动态变化或新增评论通知，正常归档提交仍遵守既有通知起点和资格。
11. **性能与请求预算（RC-12）**：固定数据、相同全量覆盖、网络延迟、来源变化、分页大小和随机种子，比较真实实现与隔离参考策略；分别报告耗时、各类请求数、显式等待及归档量。
12. **已有行为回归**：来源未知／受限、不可见回复口径、旧领取迟到完成、停止与重纳入、媒体失败／交错、SQLite 原子迁移、冻结阅读分页和只读 GET 不触发上游均保持。

性能门槛为 `T_new <= 1.2 * T_reference + 0.1s * P_replies`。页数只计无故障固定样本中实际必需的楼中楼请求，包含协议要求的确认页，不能用重复请求扩大预算。参考侧同样必须完成全量内容；独有工作需等量计入，无法等价时只能报告可比链路，不宣称整体初始化达标。

原始参考脚本保持静态参照，不执行、导入或强制纳入版本。隔离参考 Adapter 记录来源摘要和适配项；不能构造等价基线时，性能结果记为未验收，不用通知基线完成日志替代。

### 既有先例

- 管理、正文和评论初始化的真实应用装配已有 `management_support`、`archive_support`、`root_support`，保留生产解析及真实数据库。
- `test_source_pacing`、`test_collector_cadence` 与 `collector_clock` 已有分页节奏、固定节拍和受控时间先例；沿用观察时序的方式，不把本次验收降成只测试 sleep 次数。
- `test_reply_incremental`、`test_inflight_lifecycle`、`test_inflight_recovery` 已有漂移、旧执行隔离及重开场景；页锚点持久续采是新增能力，不能把既有内存分页验证当成已完成。
- `test_deployment_processes`、`test_three_process_delivery` 及采集进程锁／重启场景已有真实子进程装配；风控 owner 接管需新增真实共享数据库断言，不能只复用托管顺序的假进程测试。
- `test_collector`、`test_profile_diagnostics` 与系统告警测试已有秘密不出现的负向断言；本次同时补上业务 ID、完整分页流确实出现的正向断言。

测试覆盖范围以生产可观察行为为准，不复制测试专用业务解析；性能等价基线尚无现成证据，须新增而不能引用既有普通回归结果充数。

## 范围之外

- 只抓最近 N 条评论或回复、仅保存预览、回填未入选的 UP 全部历史动态。
- 新的凭据失效／验证挑战分类、业务风控码识别、通用网络退避或受限内容处理改造。
- 换 IP、代理轮换、验证码或权限绕过、Cookie 管理／续期、nav 登录探针。
- 新增风控页面、前端操作面板、人工采集按钮或异步 UP／目标校验工作流。
- 改变评论检测信号、每日校准策略、通知起点／资格、群路由、通知开关和归档读取协议。
- 引入外部消息队列、分布式数据库、多机共享 SQLite 或新的应用账号权限体系。
- 生产压测、自动触发真实限流、真实 B 站／OSS／飞书验证、提交、部署、回滚或重启。

## 补充说明

- 正式设计及其 RC 验收清单是后续拆票依据；具体实现位置、内部表名、迁移版本和测试函数名在实施时确定，不作为本规格的稳定约束。
- 风控后的六档等待替代了讨论早期的 30／60／120 分钟及失败三次方案；“每次到期均探测”和“全部通过才恢复”不得遗漏。
- 性能公式已经包含用户新增的楼中楼每页 0.1 秒保护成本；没有实测的 B 站安全 QPS，不承诺平台永不拦截。
- 日志沿用标准输出／错误输出与 systemd-journald 的现有持久落盘链路。本规格只扩展内容，不新增独立日志文件、轮转器或固定保留天数；当前历史可见范围受全机 journal 容量与磁盘空间约束，保留期调整需另行确认运维预算。
- 固定节拍与“不默认退避”的既有要求，仅按正式设计增加已确认的 HTTP 412／429 例外；其他运行规则不借机扩改。
- 现有设计文档和规格不是验收证据。后续命令、回放样本、跨进程结果及未验证事项保存在本工作目录的证据中，并在交付时同步正式运行契约。
