# 飞书通知接入实施规格

Status: ready-for-agent

用户已确认业务方案、SQLite 事务发件箱＋独立通知进程，以及本文的三个测试入口。此状态表示可供后续拆票实施，不表示代码完成、测试通过或已授权真实投递和部署。

依据：[飞书通知需求与设计](../../docs/design/feishu-notifications.md)、[领域词汇](../../GLOSSARY.md)、[SRS](../../docs/product/SRS.md) FR-21 / AC-35、[HLD](../../docs/design/HLD.md)。正式文档负责长期业务规则；本文将已确认决策收敛为实施范围及验证要求。发现冲突时先指出并回到已确认决策，不静默扩大或删减范围。

## 问题陈述

用户目前需要主动打开本站查看动态和评论，缺少及时、可恢复的飞书提醒。参考脚本的消息内容与路由不能直接满足本站需求：动态变化只应通知 UP 群，UP 本人新增评论应同时通知 UP 群和全员群，其他人的新增评论只通知全员群；点击评论消息还应直接看到那一条评论，而非只到动态或楼层顶部。

接入不能让飞书慢请求或故障拖住采集，不能在首次启用时推送大量历史评论，也不能因采集分页失败、重复扫描或进程重启丢失已符合资格的通知。现有正文、根评论、回复分段提交与目标生命周期需要保留，通知的生成、投递及其成功状态必须与归档成功状态分开。

## 解决方案

在真实正文或评论提交时，以同一 SQLite 事务保存通知事件或待判定候选。独立通知进程默认每一秒领取到期记录，按服务器路由配置发送飞书，并持久记录每个目标群的独立结果。失败退避重试；不引入 Kafka，也不通过全表扫描评论来猜测新增。

沿用现有动态编辑信号与评论计数驱动采集逻辑：动态新版本正文成功归档后通知，评论成功保存且可在本站展示定位后逐条通知，不等待整轮评论或媒体完成。持久保存通知起点、版本基线与去重记录，区分历史初始化、正常运行、停止后重纳入及普通进程重启。

新增本站精确评论入口，使一级评论和任意楼中楼回复都可通过消息链接直接加载、展开、定位并高亮。系统群继续独立接收脱敏告警与定时心跳。

## 用户故事

### 消息内容与群路由

1. 作为监控使用者，我希望动态变化消息只显示标题或动态 ID、变化提示和可点击链接，以便快速判断并打开本站详情。
2. 作为监控使用者，我希望标题缺失或仅有空白时回退动态 ID，以便仍能准确识别目标，而不是把正文摘要误当标题。
3. 作为群成员，我希望每条新增评论独立显示动态、评论人、发表时间、正文和链接，以便直接了解这条评论。
4. 作为群成员，我希望发表时间统一为北京时间并显示到秒，以便不受设备时区或投递延迟误导。
5. 作为群成员，我希望评论保留原始换行及“回复 @某人”等上下文，以便理解对话关系。
6. 作为群成员，我希望缺昵称时显示作者 UID、纯图片评论显示明确占位，以便不会看到不明身份或无意义空消息。
7. 作为群成员，我希望超长评论只截断消息正文并保留链接和截断提示，以便不刷屏且能查看归档全文。
8. 作为群成员，我希望消息中的昵称和正文安全展示、不执行内容或触发任意提及，以便来源文本不会变成意外操作。
9. 作为 UP 群成员，我希望只收到所属动态变化和该动态 UP 本人的新增评论，以便专注 UP 的活动。
10. 作为全员群成员，我希望收到所属动态所有作者的新增评论，包括 UP 本人，以便完整关注实际发现的新增讨论。
11. 作为多 UP 监控使用者，我希望按动态作者 UID 判断本人，以便同名用户或另一位受监控 UP 串门时不会发错群。
12. 作为运维者，我希望每个 UP 有默认双群路由且个别动态可覆盖，以便新动态不必逐一手工配群。
13. 作为运维者，我希望缺少或配错一个目标群时保留待发消息、其他群仍正常发送，以便修复后补发且不会串群。
14. 作为运维者，我希望修复路由不重置通知起点、不重发成功目标，以便不会补出启用前历史或重复轰炸已成功的群。
15. 作为运维者，我希望飞书凭据只保存在服务器配置中，以便不暴露给浏览器、仓库、日志或消息内容。

### 发送时机、基线与生命周期

16. 作为监控使用者，我希望动态变化沿用现有每 58～62 秒采样的可信编辑信号，以便不改变当前检测行为。
17. 作为群成员，我希望新版本正文成功归档后才收到变化通知，以便点击时本站已具备对应内容，而不是只知道观察值变了。
18. 作为群成员，我希望正文通知不等待评论或图片同步完成，以便独立失败的分项不会拖住可读正文的提醒。
19. 作为监控使用者，我希望首次正文只建立基线、不发送新动态发布消息，以便本期通知仅覆盖已确认的变化类型。
20. 作为监控使用者，我希望计数变化、定位资源变化、读取失败或正文受限不冒充动态内容变化，以便减少误报。
21. 作为群成员，我希望新评论一旦保存并可在本站展示定位就进入投递，以便无需等所有分页和媒体结束。
22. 作为群成员，我希望后续分页失败不阻止已成功保存的新评论通知，以便局部成功仍能及时提供价值。
23. 作为监控使用者，我希望计数下降但没有发现新评论时不发送占位或删除通知，以便通知只描述实际确认的内容。
24. 作为监控使用者，我希望重复采集、补字段和评论纯编辑不重复产生新增通知，以便同一评论只生成一个新增事件。
25. 作为首次接入者，我希望启用前已有的评论静默，以便接入时不会被历史内容刷屏。
26. 作为首次接入者，我希望初始化期间发表的新评论仍有通知资格，以便不会因首次采集耗时漏掉新讨论。
27. 作为监控使用者，我希望作者 UID 或发表时间缺失时暂缓判定、补齐后按原起点评估，以便不猜身份或用采集时间冒充发表时间。
28. 作为群成员，我希望根评论或定位条件未就绪的回复暂缓投递，以便收到链接时能找到具体回复。
29. 作为监控使用者，我希望停止监控或移出窗口后不再生成新通知，包括停止后才提交的在途工作，以便停止立即约束后续事件生成。
30. 作为监控使用者，我希望停止前已入队的通知继续投递，以便停止监控不丢掉已确认的提醒。
31. 作为监控使用者，我希望重新启用或重新入选时重新建立通知起点和当前版本基线，以便不追补暂停期间的评论和编辑。
32. 作为运维者，我希望普通进程重启保留原通知起点、基线和队列，以便重启不会被误当作重新启用或触发历史重发。
33. 作为归档阅读者，我希望通知阶段变化不删除旧正文、评论或图片，以便保留原有归档阅读能力。

### 持久投递与运行隔离

34. 作为运维者，我希望归档与事件或候选同时提交或回滚，以便进程中断不会留下已存内容却永久缺失通知的双写窗口。
35. 作为运维者，我希望通知进程只领取到期的待处理记录，以便不反复扫描所有评论和放大数据库负担。
36. 作为监控使用者，我希望飞书请求独立于采集和 API，并在数据库事务之外执行，以便飞书慢或失败不会拖住上游采集和正常阅读。
37. 作为运维者，我希望通知进程默认每秒检查待投递记录，以便在无积压和限流时尽快开始发送，而不是承诺固定送达时间。
38. 作为运维者，我希望每个目标群分别保存成功或失败结果，以便只重试失败目标。
39. 作为运维者，我希望网络异常、平台业务失败及限流保留消息并退避重试，以便不会因短暂故障直接丢失提醒。
40. 作为运维者，我希望进程中断后可恢复过期领取，并拒绝旧领取回写，以便任务可继续处理且不会被迟到结果污染。
41. 作为群成员，我希望重试保持事件生成时的消息内容，以便排队期间归档更新不会把原事件描述改掉。
42. 作为运维者，我希望迁移保留原归档和检查状态，以便增加通知能力不破坏已有数据。
43. 作为运维者，我希望明确飞书成功但响应丢失时可能重复，以便不会把本地去重误解为外部绝对一次送达保证。

### 本站精确链接

44. 作为群成员，我希望点击动态变化消息直接打开本站动态详情，以便查看已归档内容。
45. 作为群成员，我希望点击一级评论消息时，即使该评论不在首批也能自动加载、定位并高亮，以便不用手动翻找。
46. 作为群成员，我希望点击楼中楼消息时，即使回复在后续页也能定位到具体回复，以便不会只看到根评论或楼层顶部。
47. 作为手机使用者，我希望精确链接在窄屏、首次打开和刷新时都有效，以便不依赖旧会话或预先加载的数据。
48. 作为阅读者，我希望定位完成后正常阅读和返回恢复仍有效，以便页面不持续抢占我的滚动位置。
49. 作为群成员，我希望目标不存在时看到明确提示和返回动态入口、临时失败时能重试，以便不会把列表顶部误认为指定评论。
50. 作为运维者，我希望精确链接只读取归档且保留代理鉴权，以便打开消息不会触发来源采集或绕过既有访问保护。

### 告警、心跳与验收

51. 作为运维者，我希望凭据失效、采集异常、主循环异常、持续投递失败和路由问题只进入系统群，以便业务群不混入运维消息。
52. 作为运维者，我希望同对象同类故障首次提醒、之后每 30 分钟最多提醒一次且跨重启保持，以便持续故障不会刷屏。
53. 作为运维者，我希望正常并发评论增长不产生故障告警、系统群自身失败不递归告警，以便区分业务活动和系统故障。
54. 作为运维者，我希望北京时间每小时第 40 分钟收到一次心跳，以便了解通知进程能观察到的当前状态。
55. 作为运维者，我希望同小时重启不重复生成心跳、停机错过和过期心跳不补发，以便恢复后不会被旧心跳刷屏。
56. 作为运维者，我希望心跳不把通知进程存活说成全部采集正常，以便正确理解系统健康程度。
57. 作为维护者，我希望自动化使用真实业务模块和隔离数据库，按已确认入口仅替换外部传输、来源或时间，以便测试能够发现事务和生命周期问题。
58. 作为维护者，我希望真实飞书、手机、浏览器与三进程运行证据分别记录，以便不会用模拟通过代替真实交付验证。

## 实现决策

### 1. 模块职责与接入位置

- 保留现有监控管理、来源读取、采集同步、归档读取和阅读导航职责。新增通知模块，将基线判定、候选、事件去重、路由、消息格式、领取、退避、告警和心跳收敛在小接口之后。
- 正文、一级评论及回复的实际归档写事务是通知事实的接入位置。调用者只登记持久事实，不直接请求飞书或自行管理投递重试。
- 除正式采集链外，显式初始化等既有归档写入口也须遵守相同约束；只读 HTTP、浏览器访问及普通状态查询不生成通知、不启动采集。
- 新增一个独立通知进程，形成单 API、单采集、单通知的运行形态。API 不启动通知定时器，不增加 API worker 或通用消息中间件。

### 2. 事件资格与消息快照

- 动态事件以可信编辑信号确认的新版本为依据，在该版本正文实际成功归档时生成；不以检查聚合代次、评论计数、资源定位变化、受限终态或检查完成代替正文成功。
- 首次正文静默建立基线；已有归档首次启用通知时复用已有可信版本；恢复监控后第一份可信当前正文用于重建基线，不追补暂停期间编辑。
- 评论事件针对首次发现且符合当前通知起点的一级评论及回复。单条合法归档就绪即可通知，不以整轮成功或媒体成功为前置条件。部分成功不代表来源评论集合完整。
- 作者 UID、发表时间或可定位的根关系不全时，可靠保存可合法归档的候选；后续补齐再按原通知阶段评估。不得为通知而放宽来源解析、归档身份或数据校验，也不伪造缺失值。
- 消息快照在取得资格并生成事件时冻结。包含真实标题或动态 ID、作者展示值、评论发表时间和正文等；重试不读取最新正文替换快照。
- 保留正式设计的两种业务模板、纯图占位、北京时间、文本安全和超长截断规则。采用支持显式链接的机器人消息载荷，不上传图片；实现时根据官方协议核验实际限制与业务成功响应，不只判断 HTTP 状态。

### 3. 通知阶段、起点与去重

- 通知起点独立于全量归档完成时间，必须在开始该有效通知阶段时持久建立。起点之前的评论静默，起点及之后的评论在被发现且就绪后通知；已有归档记录在首次启用时静默作为基线。
- 时间比较使用可信来源发表时间，保留来源精度，不用采集时间补造资格。信息不全的候选保存其原阶段及起点，不在字段补齐时重新制造启用时间。
- 停用、移出窗口、删除目标或配置及切换模式导致不再入选时，结束相应通知阶段。已领取采集允许按原规则保存归档，但提交时必须核验通知阶段和目标代次，不能产生失效阶段新事件。
- 重新纳入建立新阶段，旧在途执行不能借新阶段生成通知。普通进程重启不是新阶段；持续入选且没有实际停止的目标也不能仅因重复配置保存重设起点。
- 已经入队的事件继续投递，不因停止、删除监控配置或重新纳入而被删除。尚未取得资格的候选不是已入队业务事件，结束的旧阶段不能再据它生成新通知。
- 正文事件按动态与已成功取得的可信版本去重；评论事件按动态、评论稳定身份及必要的所属根身份去重。不使用总数、轮次或每次投递的随机标识代替事件身份。
- 去重记录跨重启、重复扫描和重纳入有效；重复采集、补字段及纯评论编辑不得重复生成已经登记的新增事件。

### 4. 持久模型与原子性

- 在现有 SQLite 中增加可迁移的通知阶段/基线、待判定候选、通知事件、目标投递和系统消息节流状态。具体表名、列名及迁移编号遵循实施时的真实基线，不在本规格中预设。
- 满足资格时，内容、事件和目标投递记录在同一短事务内提交或回滚；暂不满足资格时，内容与候选可靠保存，后续判定和生成事件采用原子转换。
- 每个事件保存稳定身份、来源动态/评论身份、正文版本或评论事实、生成时间及消息快照。每目标记录保存角色/路由引用、状态、下次重试时间、领取凭证与有效期及脱敏错误。
- 至少能够区分等待信息或定位、等待配置、可投递、已领取及成功；具体内部枚举与表拆分属于实现设计，测试不以枚举拼写或表布局为通过条件。
- 对到期任务、候选和稳定事件身份建立适当索引与唯一约束；正常轮询不扫描整张评论表推断新增。
- 迁移保留已有归档、来源观察、分项成功 checkpoint 和目标生命周期状态。通知成功或失败不反向推进或回退归档成功状态。

### 5. 群路由与服务端配置

- 动态变化只发 UP 群；UP 本人评论同时发 UP 群和全员群；其他人的评论只发全员群；告警和心跳只发系统群。
- 本人身份由评论作者 UID 与该动态所属 UP 的 UID 相等确定，使用字符串身份，不按昵称或受监控 UP 集合判断。
- 每个 UP 配置默认 UP 群和全员群，动态可覆盖相应目标角色；缺少动态覆盖时继承所属 UP 默认值，系统群单独配置。
- 缺失或错误路由暂停该目标并保留消息，其他目标独立发送；不得转投其他角色补位。修复配置后补发，不重置起点、不重新扫描历史、不重发已成功目标。
- 使用服务端配置文件提供路由与可信本站基址；Webhook、签名等凭据只在仓库外服务端保存，队列保存路由引用而非复制密钥。日志、错误、业务 API、前端产物和消息快照均不得包含凭据。
- 配置加载、校验与修复后生效流程必须在实施交付中明确，并验证等待任务能够恢复；本规格不要求热更新机制或管理 UI。

### 6. 独立领取、投递与恢复

- 默认每一秒轮询到期记录，以有限批量和短事务领取。正式运行单通知实例，并通过领取凭证及有效期阻止迟到结果污染重新领取的任务。
- 飞书网络请求、等待、限流和退避在事务之外执行；外部发送变慢时，不得持有 SQLite 写锁等待网络。
- 各目标独立保存结果，成功状态保持；一个群失败不能让另一群已成功的消息重发。飞书业务失败和 HTTP 成功须区分。
- 网络异常、限流与可修复投递失败持久重试，保存下次尝试时间；缺少路由进入等待配置而不是每秒重复发无效 HTTP。退避仅作用于通知，不修改采集节拍。
- 进程崩溃或过期领取可恢复；已失效的领取凭证不能覆盖新领取结果。发送成功但响应丢失的情况可能在飞书形成重复，不能承诺外部绝对一次。
- 无积压、无异常和无限流时，目标是提交后约一个轮询周期开始投递，不是一秒送达保证；不承诺跨群同时送达或全局按发表时间排序。
- 队列持久不等于无限容量，不新增自动丢弃业务消息、备份或存储治理；消息快照及重试状态需要在真实资源测试中测量。

### 7. 本站精确读取与浏览器入口

- 复用现有动态详情和楼中楼阅读流程，新增携带动态、根评论及目标评论身份的精确入口；不要另建一套与现有阅读状态无关的完整评论阅读器。
- 归档读取接口须支持可靠取得目标及定位所需上下文，区分不存在、暂时失败与可读结果；只读取本地归档，不访问上游。
- 精确定位不能依赖目标已经在首批 DOM 中，也不能为一次定位渲染全部评论。协议须覆盖后续批一级评论、后续页回复与窄屏独立楼中楼。
- 点击、直开和刷新均自动加载、必要时展开、定位并高亮指定评论。主动定位完成后不持续抢占滚动，原返回与历史恢复行为保持。
- 目标不存在或归档已清理时明确提示并提供回到对应动态的入口；临时读取失败可重试，不把列表顶部当作定位成功。
- 本站基址来自可信服务器配置，链接无管理凭据；保留现有代理鉴权。具体路由参数、读取契约及兼容处理在实施切片中定义并测试，不借此扩大应用账号体系。

### 8. 系统告警与心跳

- 告警范围为可信凭据失效、采集异常、主循环异常、飞书投递持续失败和路由缺失/错误。普通网络异常不冒充登录失效，正常并发评论增长不视为故障。
- 同对象同类故障首次提醒，此后每 30 分钟最多提醒一次，节流状态跨重启保留，未投递同类提醒不得无限堆积。采用固定脱敏原因，不回显来源正文或异常原文。
- 系统群投递失败留本地脱敏日志并重试原任务，不递归产生新的发送失败告警；不新增恢复通知或飞书图片上传降级告警。
- 心跳按北京时间每小时第 40 分钟生成，同一小时去重，不受告警节流影响；错过不追赶，过期不投递，有效期不跨下一个心跳时段。
- 心跳只报告当前可观察事实，不能把通知进程存活等同于采集全部成功。进程被强杀或整机停机时，不承诺即时告警或心跳送达。

### 9. 实施收口约束

- 实施切片需落实具体消息载荷、官方限制及响应判定、配置生效流程、数据迁移、精确读取契约、租约/退避/限流参数和第三进程托管方式，并给出可复现验证。
- 上述实现细节不能改变已确认的事件资格、路由、静默历史、停止/重纳入或投递可靠性语义；若发现确需改变业务行为，应先显式回到用户决策。
- 业务实现以当前代码与正式采集契约为复用基线，不导入参考脚本主循环，不把旧阶段“排除飞书”改写成当时已接入。

## 测试决策

### 已确认的三个测试入口

| 入口 | 使用真实能力 | 可替换的外部依赖 | 核心观察结果 |
| --- | --- | --- | --- |
| 归档到飞书投递主链 | 归档、通知阶段、SQLite、候选/事件生成、路由、格式及投递调度 | B 站与飞书 HTTP 传输、媒体外部传输、可控时间 | 实际发出的目标与载荷、成功/失败后可观察行为、重试及重启后的结果 |
| 本站深链接到浏览器定位 | 生产前端装配、生产读取 Adapter、路由、分页和阅读恢复；补少量真实 API＋隔离 SQLite 场景 | 大部分浏览器场景的归档 HTTP 响应 | 后续批/页的目标是否可见、展开、高亮，刷新和返回是否正确，读取是否触发上游 |
| 少量真实进程与迁移 | 真正临时数据库、迁移、进程启动/终止、领取恢复及跨进程提交 | 本地受控外部服务与故障注入 | 数据保留、进程中断恢复、失效领取被拒绝、外部慢请求不占写事务 |

这三个入口已经用户确认，不要求将所有验证挤进一套超大端到端测试，也不把每个内部辅助函数变成外部测试接口。

### 测试原则与已有先例

- 从已有归档/采集入口驱动真实业务，从接收端、公开读取结果和重启后的持久行为验证；不模拟归档写入、事件生成、路由判定或 SQLite 来获得主链绿灯。
- 仅在证明原子性、查询索引、领取隔离等存储不变量时使用必要的数据库断言或故障注入；避免把内部函数调用顺序、私有表列拼写或实现层数当需求。
- 后端已有应用工厂传输注入、临时 SQLite、可控采集时钟、阻塞门闩、中断恢复、真进程终止和迁移回滚测试，可作为本期先例。复用这些接入能力，不新增只为某一函数通过测试的宽接口。
- 前端已有生产 Adapter＋HTTP 替身、mock/fault 场景、真实管理 API＋隔离 SQLite 及独立视觉项目。评论批次、回复页码、窄屏楼中楼和历史恢复均有先例；新增测试按现有项目声明与命令约定接入。
- 一秒轮询、退避、半小时节流和整点偏移心跳优先使用受控时间；并发与在途切换用门闩控制，不靠长时间真实睡眠或偶然调度结果。
- 跨进程测试不能把进程内 HTTP 替身直接冒充可跨进程服务；采用现有隔离进程夹具的受控来源/本地服务方式，不接真实 B 站或飞书。

### 完成条件与证据隔离

- 所有正式条件均须记录通过、失败或未验证及原因；引用对应自动化结果、运行环境和版本，不把规格发布或标记为可实施当作验收。
- 运行已有后端回归、前端类型/单测/所需浏览器项目及交付检查，确保原阅读、目标生命周期、归档与媒体分项行为不被改变；具体命令以项目当时的正式入口为准。
- 自动化、真实飞书群投递、飞书内置浏览器/手机、三进程运行与资源测量分别记录，彼此不能替代。真实发送与部署须获得授权后执行；未授权时完成可自动化部分并如实保留未验证项，不能宣布完整交付。
- 测试使用虚构身份、消息和凭据，不读取真实路由配置、不向真实群试发，不对现有运行数据库做故障注入。

## 范围之外

- Kafka、Redis、Celery、通用消息总线、多种通知渠道、多 API worker 或分布式投递集群。
- 直接在采集事务中请求飞书，或周期扫描全部评论表猜测新增。
- 新动态发布、评论删除、纯评论编辑、故障恢复通知，以及动态正文/图片比对检测。
- 改变现有采集节拍、采集退避、自适应频率、默认每日全量校准或全历史动态回填，以弥补既有检测限制。
- 飞书图片上传、额外飞书应用凭据、父评论全文附加、回复图片采集范围扩展。
- 前端通知配置、凭据编辑、投递管理 UI，新增应用账号或权限系统。
- 暂停期间的历史追补、飞书端绝对一次送达、跨群同时送达、一秒送达或捕获全部中间编辑版本的承诺。
- 首期备份、容量治理、消息自动淘汰、未验证的同机容量承诺。
- 本次规格阶段的业务代码、票据拆分、真实外部请求、生产配置修改、提交代码或部署。

## 补充说明

- 现有能力包括分段归档、SQLite、目标入选代次、可控采集测试、基本动态/楼中楼路由；目前没有飞书事件/投递设施，也没有任意评论精确深链接与高亮。新增能力必须取得新证据。
- 用户接受现有分钟精度编辑漏检、计数抵消/纯评论编辑漏检，以及飞书已接受但响应丢失时可能重复。动态链接打开当前归档详情，不保证固定到消息对应的历史版本。

- 原后端集成、前端迁移及部署验收保持原范围，不改写历史记录；新任务证据归属本功能工作目录，正式契约更新另按文档职责同步。
