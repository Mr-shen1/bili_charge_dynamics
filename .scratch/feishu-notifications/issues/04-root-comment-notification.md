# 04: 一级评论通知闭环

**What to build:** 一级评论保存并可精确定位后逐条发送飞书：动态所属 UP 本人同时发 UP 群和全员群，其他人只发全员群；历史静默，初始化期间的新评论不遗漏。

**Blocked by:** 01 动态变化通知首条闭环；02 一级评论精确链接。

**Status:** ready-for-agent

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 3–11、21–27、34、38、41、45；验收关联 FS-AC-01、02、04、05、07、11。

复用 01 的持久通知阶段、事务发件箱和独立投递，消息使用 02 的一级评论精确入口。单条归档就绪是发送时机；不等待评论集合完整或媒体就绪。本票实现合法双群发送与基本目标隔离，06 补齐配置与复杂恢复矩阵。

## 验收条件

- [ ] 开始有效通知阶段时持久保存起点，不等首次全量归档结束；已有归档静默作为基线。
- [ ] 10:00 启用、10:02 采集时，09:59 发表的旧评论静默，10:01 的新评论产生事件；覆盖无归档、有归档和同秒边界，不以采集时间替代发表时间。
- [ ] 新根评论与合格事件或待判定候选同事务保存；候选取得资格时原子转成事件，提交前失败/回滚及提交后重启不造成孤立事件或永久遗漏。
- [ ] 作者 UID 或有效发表时间缺失时，仅对可合法归档数据保留候选并暂缓；后续补齐按原阶段起点判断，不伪造字段或放宽来源身份校验。
- [ ] 评论保存且可通过 02 入口读取定位后即可投递；后续分页或图片失败不阻塞已就绪评论，不宣称来源集合完整。
- [ ] 来源计数增加并发现两条新评论时发送两条；计数下降且无新评论时不发占位或删除通知；重复扫描、补字段、纯编辑不重复生成已登记事件。
- [ ] 至少两个 UP，覆盖本人、同名异 UID、另一受监控 UP 串门和普通作者；按所属动态作者 UID 判断，双群/全员群路由正确，系统群不收业务评论。
- [ ] 规范模板包含动态标题或 ID、昵称或作者 UID、北京时间到秒、原正文和可点击的具体评论链接；保留换行与回复前缀，不附父评论全文或上传图片。
- [ ] 已知纯图评论使用规定占位；标题空白和昵称缺失正确回退；来源文本不执行 HTML 或触发任意提及，不修改归档原文。
- [ ] 超长正文在实际载荷限制内安全截断，保留其他字段、全文提示和链接；标题/昵称等也纳入序列化预算，核验协议依据，不拆多条刷屏。
- [ ] 事件快照冻结内容，逐群记录结果；一个目标失败不重新发送已成功目标。停止后提交的旧阶段候选不能新增事件，普通重启不重置基线。
- [ ] 从实际归档链驱动飞书替身，取其真实生成的链接进入生产浏览器读取并验证目标，证明不是手工拼出的另一套入口。

## 验证方式

真实归档、临时 SQLite 和通知模块构成主链，仅替换外部 HTTP 传输及时间。用受控分页失败和门闩证明“不等全轮”，用数据库重开与重复归档证明去重。浏览器部分沿用 02 的生产装配和隔离 API；无需真实群或真实来源。

## 完成与后续

交付一级评论从归档到双群受控投递、再到本站精确阅读的闭环及边界证据。楼中楼由 05 扩展，多群复杂故障和跨事件生命周期分别由 06、07 收口，但本票已须保证原子保存、基础去重与有效阶段约束。
