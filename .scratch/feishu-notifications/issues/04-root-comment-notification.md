# 04: 一级评论通知闭环

**What to build:** 一级评论保存并可精确定位后逐条发送飞书：动态所属 UP 本人同时发 UP 群和全员群，其他人只发全员群；历史静默，初始化期间的新评论不遗漏。

**Blocked by:** 01 动态变化通知首条闭环；02 一级评论精确链接。

**Status:** resolved

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 3–11、21–27、34、38、41、45；验收关联 FS-AC-01、02、04、05、07、11。

复用 01 的持久通知阶段、事务发件箱和独立投递，消息使用 02 的一级评论精确入口。单条归档就绪是发送时机；不等待评论集合完整或媒体就绪。本票实现合法双群发送与基本目标隔离，06 补齐配置与复杂恢复矩阵。

## 验收条件

- [x] 开始有效通知阶段时持久保存起点，不等首次全量归档结束；已有归档静默作为基线。
- [x] 10:00 启用、10:02 采集时，09:59 发表的旧评论静默，10:01 的新评论产生事件；覆盖无归档、有归档和同秒边界，不以采集时间替代发表时间。
- [x] 新根评论与合格事件或待判定候选同事务保存；候选取得资格时原子转成事件，提交前失败/回滚及提交后重启不造成孤立事件或永久遗漏。
- [x] 作者 UID 或有效发表时间缺失时，仅对可合法归档数据保留候选并暂缓；后续补齐按原阶段起点判断，不伪造字段或放宽来源身份校验。
- [x] 评论保存且可通过 02 入口读取定位后即可投递；后续分页或图片失败不阻塞已就绪评论，不宣称来源集合完整。
- [x] 来源计数增加并发现两条新评论时发送两条；计数下降且无新评论时不发占位或删除通知；重复扫描、补字段、纯编辑不重复生成已登记事件。
- [x] 至少两个 UP，覆盖本人、同名异 UID、另一受监控 UP 串门和普通作者；按所属动态作者 UID 判断，双群/全员群路由正确，系统群不收业务评论。
- [x] 规范模板包含动态标题或 ID、昵称或作者 UID、北京时间到秒、原正文和可点击的具体评论链接；保留换行与回复前缀，不附父评论全文或上传图片。
- [x] 已知纯图评论使用规定占位；标题空白和昵称缺失正确回退；来源文本不执行 HTML 或触发任意提及，不修改归档原文。
- [x] 超长正文在实际载荷限制内安全截断，保留其他字段、全文提示和链接；标题/昵称等也纳入序列化预算，核验协议依据，不拆多条刷屏。
- [x] 事件快照冻结内容，逐群记录结果；一个目标失败不重新发送已成功目标。停止后提交的旧阶段候选不能新增事件，普通重启不重置基线。
- [x] 从实际归档链驱动飞书替身，取其真实生成的链接进入生产浏览器读取并验证目标，证明不是手工拼出的另一套入口。

## 验证方式

真实归档、临时 SQLite 和通知模块构成主链，仅替换外部 HTTP 传输及时间。用受控分页失败和门闩证明“不等全轮”，用数据库重开与重复归档证明去重。浏览器部分沿用 02 的生产装配和隔离 API；无需真实群或真实来源。

## 完成与后续

交付一级评论从归档到双群受控投递、再到本站精确阅读的闭环及边界证据。楼中楼由 05 扩展，多群复杂故障和跨事件生命周期分别由 06、07 收口，但本票已须保证原子保存、基础去重与有效阶段约束。

## Answer

已交付一级评论从归档到双群投递、再到本站精确阅读的完整纵向切片：根评论写事务内同事务登记事件或候选，独立通知进程按角色投递，消息链接命中 02 的精确入口。

- 接入与原子性：`backend/bili_monitor/storage.py` 的 `_change_roots` 在每次分页提交里调用 `outbox.record_root`（传入 `discovered = previous is None`）；评论、事件（或候选）与逐群投递记录同事务提交或回滚（`backend/bili_monitor/notifications/outbox.py`）。单条就绪即投递，不等整轮分页与媒体。
- 起点与静默：新增 `notification_phases.comment_started_at`，与阶段建立同一时刻写入；升级已有库时以升级时刻回填（只补 NULL），因此 01 的旧起点不会把历史评论判成“起点之后”。比较用来源 `published_at` 解析后的时间戳，起点按秒取整。
- 候选：`notification_candidates` 记录**原阶段**，作者 UID 或发表时间缺失时暂缓；补齐后按原起点原子转事件，阶段封存后作废，不越阶段。
- 路由：作者 UID 与该动态所属 UP 的 UID 字符串相等 → `up`+`all`，否则仅 `all`；系统群（09 的顶层 `system`）不接收业务评论。
- 去重与快照：一级评论事件身份 `(kind, dynamic_id, root_id, comment_id)`（`root_id` 即自身，05 用所属根），部分唯一索引跨重启/重扫/重纳入有效；快照冻结标题、作者、发表时间、正文与是否已知有图，重试不读最新归档。
- 模板与预算：`message.root_comment` 输出北京时间到秒、保留换行与“回复 @某人”、纯图占位、昵称/标题回退；超限只裁正文并追加全文提示，标题与昵称也计入 20 KB 序列化预算，链接与时间不被截掉，不拆多条。
- 迁移：schema v18（09 占 v17），链为 `<17` 心跳 → `<18` 评论增量 → `PRAGMA 18`，两侧结构与既有断言都保留。
- 浏览器证据：`frontend/tests/e2e-notification/delivery-link.spec.ts`（`pnpm test:e2e:notification`）用真实归档链 + 真实 `Dispatcher` 打到进程内飞书替身，从投递产物里取链接，在生产装配里直开并定位第 26 条评论（第二批），窄屏刷新同样成立。
- 证据：[04 一级评论通知闭环](../evidence/04-root-comment-notification.md)（12 主链用例、协议与迁移用例、后端全量 909 passed、`pnpm check` 271 passed、`pnpm test:e2e` 198 passed / 10 skipped、`test:e2e:notification` 2 passed、`test:e2e:location` 4 passed、`test:e2e:manage` 7 passed、`pnpm check:dist` 通过）。
- 正式契约：[通知进程与事件投递](../../../docs/backend/api/notification-process.md)（§3.1 一级评论、§4 持久状态、§6 载荷、§7 迁移）。

## Comments

- **评论起点不能复用 01 的 `started_at`**：那是 01 阶段建立时刻，可能远早于评论通知上线。裁决是“升级时已有阶段以升级时刻建立评论起点”，代价是 01 之后、04 之前发表但未接入评论通知的评论静默（明确取舍，避免升级瞬间历史回填）。新阶段（启用/重新入选）两值同一时刻，行为与设计 §3.3 一致。
- **first insert 与候选补齐必须分开**：根评论首屏带置顶/热评 extras，且历史评论会在每次首扫“首次插入”。因此事件登记要求 `discovered`，补齐只走候选转换；两者都用评论起点做最终过滤。`pending` 阶段的候选不是“待投递目标”，单独成表，不进 `claim_due` 谓词。
- **事件键预留 05**：`root_id` 列让回复用所属根作身份；一级评论 `root_id` 即自身，全部非空，避免 SQLite 唯一索引里 NULL 各自独立的坑。
- **迁移号协调**：并行票据 09 先用 v17（心跳时段表、`expires_at`、`system` 角色）。本票重排为 v18，保留 09 的 `<17` 分支与原断言；两侧 schema 各自可重入（`IF NOT EXISTS` + 列存在性检查）。
- **被测试纠正的实现缺陷**：`_register_comment` 漏取 `comment_id` 时异常被采集侧折叠成 `internal_error`（表现为根同步失败而非通知失败），说明通知异常仍受归档事务保护；`_clip` 整段裁完时丢了截断标记，会让“长标题+长昵称+长正文”的全文提示消失，已改为“至少留标记”。
- **浏览器夹具**：`live_app` 里“刚发表”的虚构评论作者改为该动态所属 UP，才能同时进双群——改的是夹具事实，不是放宽路由；`tests/e2e-notification` 用独立端口（4179/4326）与独占 SQLite，便于与 03/09 并行跑（共享端口的 `pnpm test:e2e` 已另行回归 198 passed / 10 skipped）。
- **给 06/07 的稳定契约**：投递状态常量与失败分类在 `notifications/outbox.py` 与 `notifications/message.py`（`timeout`/`network_error`/`http_error`/`invalid_response`/`platform_rejected`/`rate_limited`/`route_missing`/`expired`/`unsupported_kind`）；`attempts` 含 `waiting_config` 复检，不能直接当“持续失败次数”，06/08 需按 `state`/`error` 分流；角色解析在 `NotificationConfig.reference`，阶段有效性在 `outbox._comment_phase`。
- **未覆盖**：真实飞书群、飞书内置浏览器/手机实机、三进程托管与目标环境（票据 10/11，需授权）；楼中楼（05）、复杂故障矩阵（06）、告警（08）。
