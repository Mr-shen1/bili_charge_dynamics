# 01: 动态变化通知首条闭环

**What to build:** 动态可信新版本正文归档后，由独立通知进程向 UP 群发送精简消息，点击可打开本站动态详情；首次归档静默，未成功归档不误发。

**Blocked by:** 无（可立即开始）。

**Status:** ready-for-agent

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 1–2、8–9、15–20、32、34–37、41–44；验收关联 FS-AC-01、03、07、08、14。

这是一个只覆盖动态变化的完整纵向切片，同时落地后续复用的最小事务发件箱与独立投递能力；不是先建一套无人使用的消息框架。复用现有归档事务和采集检测，不导入参考脚本主循环，不预建 Kafka 或多渠道接口。

从本票起遵守事务、稳定事件身份、有效通知阶段、凭据隔离与失败保留约束。06 扩充多群复杂故障，07 补齐跨事件生命周期矩阵，不能以它们尚未完成为由先实现丢消息或停用后误发的路径。

## 验收条件

- [ ] 现有默认 58～62 秒页面信号采样及评论计数检查节拍不变；只有可信编辑版本变化且对应正文实际成功归档才登记动态事件。
- [ ] 首次取得正文只建立基线；已有归档启用通知时复用已有可信版本，不补发旧版本；计数、资源定位、聚合检查代次、未知信号、失败或受限终态都不单独产生动态变化通知。
- [ ] 正文与合格事件及其 UP 群投递记录同事务提交或回滚；正文失败不发，后续成功可发；正文已提交后进程中断不永久遗漏消息。
- [ ] 按动态与已取得的可信版本去重，保存消息快照；重复同步和普通重启不重复生成事件，也不重置起点或基线。
- [ ] 归档提交时核验通知阶段及入选代次；停止后的旧在途工作可按原规则存内容，但不新增通知。首次恢复的基线语义符合规格，不能借旧任务激活新阶段。
- [ ] 正文成功就可投递，不等待评论或图片；通知结果不改变归档成功 checkpoint。
- [ ] 服务器配置提供有效 UP 群和可信本站基址；消息仅含规定的变化提示与显式可点击链接。标题缺失/空白回退动态 ID，安全展示来源文本，不用正文摘要伪造标题。
- [ ] 最小配置流程不暴露凭据；缺少目标时可靠保留待配置记录，不丢弃、不转投。动态覆盖与双群修复矩阵由 06 完整验证。
- [ ] 独立通知进程默认每秒按索引领取到期记录，有限批量，飞书网络请求不占数据库事务；API 不内嵌通知定时器，归档读取不产生事件。
- [ ] 验证飞书业务成功响应，不只看 HTTP 200；基础失败记录可恢复并退避重试，成功状态持久保持，不因读取归档更新而改写消息快照。
- [ ] 新迁移保留已有归档、观察与同步状态，可重复执行且失败可恢复；不写死过期迁移编号，不因引入通知改变原采集行为。
- [ ] 通过受控主链证明正文已可从本站读取、飞书替身收到正确目标和内容、详情链接有效；记录本票测试与当前未覆盖范围。

## 验证方式

从真实归档/采集入口驱动临时 SQLite 与实际通知模块，仅替换 B 站、飞书、媒体外部传输及时间。覆盖提交前异常、事务回滚、提交后重启、媒体阻塞和正常失败重试；必要的事务断言不替代外部可观察结果。核验飞书官方载荷及业务响应契约，使用虚构配置，不读取真实机器人配置或试发。

## 完成与后续

交付可复现的动态变化到受控接收端演示、最小进程启动与配置说明、安全迁移及回归证据。不能宣称双群恢复、完整告警/心跳或真实飞书验收完成；这些按后续票据独立取证。
