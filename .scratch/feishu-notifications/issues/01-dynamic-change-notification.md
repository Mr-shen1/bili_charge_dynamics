# 01: 动态变化通知首条闭环

**What to build:** 动态可信新版本正文归档后，由独立通知进程向 UP 群发送精简消息，点击可打开本站动态详情；首次归档静默，未成功归档不误发。

**Blocked by:** 无（可立即开始）。

**Status:** resolved

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 1–2、8–9、15–20、32、34–37、41–44；验收关联 FS-AC-01、03、07、08、14。

这是一个只覆盖动态变化的完整纵向切片，同时落地后续复用的最小事务发件箱与独立投递能力；不是先建一套无人使用的消息框架。复用现有归档事务和采集检测，不导入参考脚本主循环，不预建 Kafka 或多渠道接口。

从本票起遵守事务、稳定事件身份、有效通知阶段、凭据隔离与失败保留约束。06 扩充多群复杂故障，07 补齐跨事件生命周期矩阵，不能以它们尚未完成为由先实现丢消息或停用后误发的路径。

## 验收条件

- [x] 现有默认 58～62 秒页面信号采样及评论计数检查节拍不变；只有可信编辑版本变化且对应正文实际成功归档才登记动态事件。
- [x] 首次取得正文只建立基线；已有归档启用通知时复用已有可信版本，不补发旧版本；计数、资源定位、聚合检查代次、未知信号、失败或受限终态都不单独产生动态变化通知。
- [x] 正文与合格事件及其 UP 群投递记录同事务提交或回滚；正文失败不发，后续成功可发；正文已提交后进程中断不永久遗漏消息。
- [x] 按动态与已取得的可信版本去重，保存消息快照；重复同步和普通重启不重复生成事件，也不重置起点或基线。
- [x] 归档提交时核验通知阶段及入选代次；停止后的旧在途工作可按原规则存内容，但不新增通知。首次恢复的基线语义符合规格，不能借旧任务激活新阶段。
- [x] 正文成功就可投递，不等待评论或图片；通知结果不改变归档成功 checkpoint。
- [x] 服务器配置提供有效 UP 群和可信本站基址；消息仅含规定的变化提示与显式可点击链接。标题缺失/空白回退动态 ID，安全展示来源文本，不用正文摘要伪造标题。
- [x] 最小配置流程不暴露凭据；缺少目标时可靠保留待配置记录，不丢弃、不转投。动态覆盖与双群修复矩阵由 06 完整验证。
- [x] 独立通知进程默认每秒按索引领取到期记录，有限批量，飞书网络请求不占数据库事务；API 不内嵌通知定时器，归档读取不产生事件。
- [x] 验证飞书业务成功响应，不只看 HTTP 200；基础失败记录可恢复并退避重试，成功状态持久保持，不因读取归档更新而改写消息快照。
- [x] 新迁移保留已有归档、观察与同步状态，可重复执行且失败可恢复；不写死过期迁移编号，不因引入通知改变原采集行为。
- [x] 通过受控主链证明正文已可从本站读取、飞书替身收到正确目标和内容、详情链接有效；记录本票测试与当前未覆盖范围。

## 验证方式

从真实归档/采集入口驱动临时 SQLite 与实际通知模块，仅替换 B 站、飞书、媒体外部传输及时间。覆盖提交前异常、事务回滚、提交后重启、媒体阻塞和正常失败重试；必要的事务断言不替代外部可观察结果。核验飞书官方载荷及业务响应契约，使用虚构配置，不读取真实机器人配置或试发。

## 完成与后续

交付可复现的动态变化到受控接收端演示、最小进程启动与配置说明、安全迁移及回归证据。不能宣称双群恢复、完整告警/心跳或真实飞书验收完成；这些按后续票据独立取证。

## Answer

已交付动态变化通知的完整纵向切片：正文可信新版本成功归档时，在同一 SQLite 事务内登记事件与 UP 群投递记录；独立通知进程按索引领取并在事务外请求飞书，失败退避重试、成功状态持久保持。首次正文与已有归档只建立基线，不补发历史；停止后旧在途仍可保存内容但不产生事件；重新入选建立新阶段并按恢复后第一份可信正文重建基线。配置、凭据、消息快照与队列分离，标题缺失/空白回退动态 ID。

- 实现：`backend/bili_monitor/notifications/`（config/message/outbox/delivery/log）、`backend/bili_monitor/notifier.py`；接线点 `storage.claim_archive`/`finish_archive` 与 `selection.refresh_selections`。
- 迁移：schema v16（通知阶段/基线、正文写领取、版本去重、事件、目标投递），空库与旧库可重入，失败整体回滚并保留旧归档/观察。
- 契约文档：[通知进程与动态变化投递](../../../docs/backend/api/notification-process.md)；运行入口 [backend/README.md](../../../backend/README.md)。
- 测试与证据：[01-dynamic-change-notification.md](../evidence/01-dynamic-change-notification.md)（44 个本票用例；全量后端回归 869 passed；隔离演示可复现）。

## Comments

- 关键裁决 1：通知阶段用自有阶段令牌，`target_selections.token` 只表示“此刻仍入选”。原因是 `refresh_selections(reset=True)` 会为持续入选的目标轮换令牌，用令牌相等围栏会误杀合法续选并重设基线。用例 `test_configuration_reset_keeps_phase_and_never_resets_baseline` 直接驱动生产 `refresh_selections(reset=True)` 证明阶段与基线不变。
- 关键裁决 2：`archives.generation` 只作内容写围栏。正文领取时把 `generation` + 当时阶段写入 `notification_body_claims`，提交时同时校验写代次、阶段未封存与目标仍入选，因此不需把阶段参数一路扩展进 `sync_*` 签名。
- 飞书协议按官方自定义机器人文档核验：富文本 `post` 段落支持 `{"tag":"a","text","href"}`、`zh_cn.title` 可选、业务成功为 `code=0`（兼容 `StatusCode=0`）、请求体 20 KB、限流 100 次/分与 5 次/秒（HTTP 429 / 11232 / `x-ogw-ratelimit-reset`）。未做真实投递。
- 迁移编号以真实 `Store.migrate` 与测试基线为准：本票把 v15 推进到 v16，并同步两个既有断言；`backend/README.md` 此前的 v13 表述已按活文件更正。旧库降级重放（既有用例会把 `user_version` 回退）要求通知建表可重入，故使用 `IF NOT EXISTS`。
- 未覆盖（不属本票或未授权）：新增评论事件与双群路由（04–07）、告警与心跳（08、09）、三进程统一托管与真实飞书/设备验收（10、11）。`services` 进程仍只托管 API＋collector。
