# 09: 小时心跳闭环

**What to build:** 北京时间每小时第 40 分钟向系统群发送一次心跳，报告当前可观察运行状态；重启不重复生成，错过和过期的心跳不补发。

**Blocked by:** 01 动态变化通知首条闭环。

**Status:** resolved

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 54–56；验收关联 FS-AC-13、14。

复用 01 的独立通知进程与持久投递能力，补充系统群角色和心跳时段/有效期。心跳不是故障告警，因此不依赖 08 的告警实现；不得为独立推进而另建一个时钟进程或放进 API 定时器。

## 验收条件

- [x] 按 Asia/Shanghai 计算每小时第 40 分钟的心跳时段（生成窗口是 `:40:00`–`:40:59` 这一整分钟，给 1 秒轮询留窗口、不要求精确到秒），不随服务器本地时区变化；时段身份及生成结果持久保存。
- [x] 同一小时重复调度或进程重启不重复生成心跳事件；使用真实持久状态而非仅进程内标记去重。
- [x] 停机错过的时段不追赶，过期心跳不投递，有效期不跨下一个心跳时段；不会在恢复后积压发送旧心跳；进程在 `:41`–`:59` 首次启动也不为本小时补发；已生成待发的心跳仍可在有效期前重试。
- [x] 心跳只发系统群；系统群缺失或暂时故障保留本地诊断并遵守心跳有效期，不转投业务群、不无限补发过期内容。
- [x] 心跳报告当前能够观察的事实；采集失败、状态未知或进度滞后不能被描述为全部正常，通知进程存活不等于采集成功。
- [x] 心跳拥有独立时段去重，不共用故障的 30 分钟节流键；不需要等告警实现才具备正确独立性。
- [x] 动态变化和评论事件不应用心跳的过期丢弃规则；共用队列处理不会误删业务待发任务。
- [x] 飞书 HTTP 保持事务外，凭据和错误仍脱敏；不承诺整机离线时的可达性或将一秒轮询视为精准送达时刻。
- [x] 用受控时间覆盖第 40 分钟窗口两端（`:39:59` 不生成、`:40:00`/`:40:59` 生成且同小时一次）、`10:41`/`10:55` 首次启动不补、跨小时、不同服务器时区、同小时重启、长停顿和网络故障后过期，验证受控系统群收到的实际消息。

## 验证方式

真实持久存储、通知调度与飞书 HTTP 替身，注入时区明确的时间而非真实等待一小时。重开数据库证明小时去重；最终与 08 告警并存时的节流隔离由 10 再集成验证。

## 完成与后续

交付心跳生成到系统群受控投递的闭环及时间边界证据。09 可在 01 完成后独立推进；系统角色和公共投递改动需与 06/08 集成协调，但不新增业务阻塞边。

## Answer

已交付小时心跳的完整纵向切片：通知进程每轮轮询先按北京时间登记本小时心跳（仅第 40 分钟窗口 `:40:00`–`:40:59` 内），再投递到期记录。

- 时段身份是北京时间的 `YYYY-MM-DDTHH`，持久写入 `notification_heartbeats`（主键即时段）；同一小时的重复轮询、进程重启、重开数据库都不重复生成，不靠进程内标记。时段只在第 40 分钟这一分钟内成立（`:40:00`–`:40:59`），`:40` 之前不成立、`:41` 起关闭，因此停机错过与 `:41`–`:59` 冷启动都没有补发入口。
- 有效期 = 下一个 `:40`（1 小时），写到该投递记录的 `expires_at`；领取事务先丢弃过期心跳（状态 `expired`、错误 `expired`），发送前复查一次，业务记录 `expires_at` 永远为 `NULL`，共用队列不会误删业务消息。恢复后只处理当前时段，不会一次性补发旧心跳。
- 心跳只发系统群（配置顶层 `system` 单独角色，不参与 UP/动态覆盖解析）：系统群缺失留 `waiting_config` 与脱敏错误 `route_missing`、零 HTTP、不转投；系统群失败按原任务退避重试，过期即停。
- 文本只陈述本地已记录事实（纳管/已检查目标数、最近检查时间、最近一次失败数、正文待同步数），固定声明“进程存活不等于采集成功”，不出现“正常/全部正常”；生成心跳不写检查或归档。
- 复用 01 的 Dispatcher、事务发件箱与独立进程，不新增时钟进程，API/collector 仍无通知定时器；飞书 HTTP 仍在事务外，日志字段沿用安全白名单（心跳只记小时）。
- 迁移推进到 schema v17：v15（01 之前重放）与 v16（01 交付）走同一可重入入口，已入队业务事件/状态/快照全部保留。

实现：`backend/bili_monitor/notifications/{heartbeat,outbox,delivery,message,config}.py`、`backend/bili_monitor/storage.py`（v17）。契约：[通知进程与动态变化投递](../../../docs/backend/api/notification-process.md) §2/§3.1/§4/§5/§7。测试与证据：[09-hourly-heartbeat.md](../evidence/09-hourly-heartbeat.md)（本票 13 条用例；全量后端回归 884 passed）。

合并后复核曾发现一处实现偏差并由本票修正：`heartbeat.slot()` 原先以「分钟 `>= 40`」为条件，导致 `:41`–`:59` 冷启动为本小时补发一条 `:40` 心跳（例如 10:55 首次启动发出 10:40）。现已收紧为「仅在 `:40:00`–`:40:59` 生成」，`10:41`/`10:55` 首次启动都不补；已生成待发的心跳仍可在 `expires_at` 前重试，业务消息与告警不受影响。红绿过程、契约同步与修正后回归见证据 §7。

## Comments

- 关键裁决 1：**心跳不另起时钟，挂在通知进程轮询里**。`Dispatcher.tick()` = 登记本小时心跳 + 投递到期记录，`run()` 每轮调用；`--once` 仍只跑一轮投递（运维排查用），不写心跳。这样“第 40 分钟”只是一个时间窗判定，不需要第二个调度器，也不把定时器塞进 API。
- 关键裁决 2：**过期做成投递层的通用机制**（`notification_deliveries.expires_at`），当前只有心跳写它。`claim_due` 先 `expire_overdue` 再领取，`_deliver` 发送前再复查；因此“业务消息不会被过期规则误删”是结构性的，08 若要用同一机制也无需改心跳代码。
- 关键裁决 3：**系统群是顶层单独角色**（`"system": "system-room"`），`reference()` 对 `system` 角色直接返回，不走 UP/动态覆盖，缺失即等待配置。06 补全员群时沿用同一形状，不会出现两套凭据入口。
- 关键裁决 4：**生成窗口是整分钟，不是「>= 40 分」也不是精确秒**。窗口 `:40:00`–`:40:59` 既满足“每小时第 40 分钟生成”，又给 1 秒轮询 60 次机会；窗口外 `slot()` 返回 `None`，本小时不再有生成入口。窗口只约束生成：`claim_due`/`_deliver`/`expire_overdue` 对已生成记录照旧，待发心跳重试到 `expires_at` 为止。
- 被测试纠正的三处：日志把时段身份压成 `unknown`（改为只记小时）；状态用例的真实失败数比预期多 1（测试数据用错页面构造器，改用 `readable_html(id=...)`）；过期记录的 `attempts` 预期写错（过期发生在领取前，不产生 HTTP）。
- 迁移编号由 16 推进到 17，同步更新 `test_migrations.py`（当前版本与未来版本拒绝基线）、`test_inflight_recovery.py` 与 `test_notification_migration.py`；新增 v16→v17 原地升级用例，证明已入队业务消息不丢。
- 与 08 的接口注意项：系统群未配置/待修复时，60 秒复检会持续累加该记录的 `attempts`；08 的“飞书持续投递失败”阈值必须按 `state`/`error` 分流，不能直接用 `attempts`，否则等待配置的心跳会被刷成故障告警。心跳过期后记录转 `expired`，不再增长。
