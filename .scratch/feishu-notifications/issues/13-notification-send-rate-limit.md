# 13: 飞书发送主动限速

**What to build:** 在“领取之后、发送之前”加一层主动限速，让投递先遵守飞书的公开额度（单机器人 100 次/分钟、5 次/秒），而不是等 429 再退避。

**Blocked by:** 无（01–10 已 `resolved`，13 只改投递调度，不改路由、模板与采集）。

**Status:** resolved

**来源：** 票据 [11](11-real-feishu-device-acceptance.md) 真实验收暴露。10 条业务消息在约 1 秒内发出，同一群 5 条同时打给一个自定义机器人，正好压在“5 次/秒”线上；本次全部一次成功，但那是运气而非预算。

## 现状（已核对）

- 投递节拍与并发：1.0s 轮询、单轮领取 ≤8 条、`asyncio.gather` 全并发、单请求超时 10s —— `backend/bili_monitor/notifications/delivery.py:18-21,124-131`。
- 失败退避：`min(300, 2*2^attempts)` 秒 —— `delivery.py:22-23,37-38`。
- 限流只做**被动**处理：识别 HTTP 429 与业务码 `11232/11233/230020/99991400`，用 `x-ogw-ratelimit-reset`，解析失败兜底 60s、封顶 600s，且**只推后那一条** —— `message.py:35-38,292-300,303-323`、`delivery.py:194-199`。
- 官方额度出处：`message.py:9` 注释与 `docs/backend/api/notification-process.md:186,201`（单机器人 100 次/分、5 次/秒）。
- 参考脚本是**有主动节流**的：每条 `random.uniform(0.5, 1.5)`/`uniform(0.5, 1.0)` 秒，每 10 条评论再 `sleep(1)`；同一 webhook 本轮失败即阻断其后消息（组级串行）—— `script_demo/bili_charge_monitor.py:1829-1837,1690-1770`。当前实现没有沿用这套。
- 单实例约束已有：`flock` 只允许一个投递进程（`notifier.py:28-41`），租约 30s > 超时 10s（`delivery.py:20-21`）限制重复而非速率。

## 裁决结果（用户已定）

| # | 决定 |
| --- | --- |
| 1 | **限速键 = 目的地（webhook/群）**：同群受同一份额度约束，跨群并行、互不占用 |
| 2 | **额度 = 每目的地 5 次/秒 + 100 次/分钟**（飞书自定义机器人官方额度），不再额外加全局层 |
| 3 | **超预算 = 顺延 `due_at`**：记录留在 `pending`，下一轮轮询自然重领；不阻塞进程、不丢记录、不累加 `failures` |
| 4 | **心跳/告警 = 独立且优先的额度**：系统群角色（`outbox.SYSTEM_ROLE`）不计入业务目的地的额度，也不被业务积压挤掉——心跳有效期（下一个 `:40`）因此不会被同群业务消息耗尽额度而 `expired` |

契约文档（先行完成，实现以文档为准）：`docs/backend/api/notification-process.md` §5.2（限速键、额度、顺延、系统角色独立额度、与 429 的关系）、`docs/design/feishu-notifications.md` §4.5（为什么现在加限速与边界）。两处原标注“尚未实现”，实施完成后已同步为已交付（票据 14 的闸门仍为未实现）。

实现要点（据此细化，不再改动方向）：

- 限速器按 `(role == system ? 'system' : webhook)` 键控；业务与系统各持独立计数窗口。
- 顺延只改 `due_at`，不改 `state`；`attempts`/`failures` 不动（顺延不是失败）。
- 限速等待不得持有 SQLite 写事务（沿用 06/10 的不变量）：先算预算、再决定是否领取/发送。
- 单实例 `flock` 与租约语义不变（限制重复，不是速率）。

## 验收条件（按裁决细化后定稿）

- [x] 同一目的地在任意 1 秒窗口内不超过 5 次、任意 60 秒窗口内不超过 100 次；按目的地隔离，跨目的地不互相占用额度。
- [x] 超预算记录不改状态、不丢、不重复：仍留在 `pending`，`due_at` 顺延，下一轮被重新领取。
- [x] 限速等待**不持有 SQLite 写事务**，也不阻塞其他目标（沿用 06/10 的既有不变量）。
- [x] 429 被动退避继续保留：主动限速不能替代对 `x-ogw-ratelimit-reset` 的处理。
- [x] 心跳与告警的时效语义有明确结论（见上表风险点），并有对应用例锁住。
- [x] 退避与限速不会叠加成“永远轮不到”：单条记录的最坏等待时间可计算、有上界且有测试。
- [x] 日志只有固定分类（不出现 webhook、密钥或 URL），新增的限速事件沿用 `notifier_event` 的安全字段约定。
- [x] 隔离条件明确：是否可通过环境变量调小额度用于测试（默认值不得被意外放宽）。

## 验证方式

- 单元：限速器本身（窗口滑动、跨目的地隔离、超预算顺延）。
- 组合：`test_notification_delivery.py` / `test_notification_combinations.py` 扩展“同群 20 条 + 一个心跳”的时序，断言真实发送时刻间隔与心跳未被过期。
- 真实（可选，需单独授权）：向测试群发 ≤10 条，核对实际到达间隔与无 429。不得用真实业务群做压力测试。
