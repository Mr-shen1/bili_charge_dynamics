# 06: 双群独立投递与故障恢复

**What to build:** 一个群不可用或配置错误时，其他群照常收消息；修复后仅补发未成功目标，进程中断、限流或响应丢失时消息仍可恢复处理。

**Blocked by:** 04 一级评论通知闭环。

**Status:** ready-for-agent

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 12–15、34–43；验收关联 FS-AC-07、08、09、10、14。

以已有动态及一级评论消息验证通用投递行为，不等待 05 才能验证双群故障。补齐路由继承、配置修复、逐目标持久状态、领取恢复和限流策略；不另建采集调度器或投递管理 UI。相关故障状态要可供 08 读取/登记告警事实，但本票不提前承担告警消息策略。

## 验收条件

- [ ] 每 UP 默认双群及动态对相应角色的覆盖优先级正确；未覆盖角色继承 UP 默认，系统群不充当业务群后备。
- [ ] 逐目标保存角色/路由引用和投递结果，队列不复制 Webhook/签名密钥；消息快照在等待及重试期间保持不变。
- [ ] 缺失或错误路由只暂停受影响目标，其他群仍发送；暂停消息可持久保留，不每秒执行无效 HTTP、不丢弃、不转群。
- [ ] 明确并验证配置加载、校验与修复后生效流程；补配后只恢复对应待发目标，不重置起点、不重新推送历史、不重发已成功目标，不要求额外热更新或 UI。
- [ ] 一群成功另一群失败后仅后者重试；不同目标的故障或退避不造成所有目标全局阻塞。
- [ ] HTTP 成功但飞书业务失败不标成功；网络超时、限流及业务错误使用经协议核验的分类和有限退避，保存下次尝试时间，不修改采集节拍。
- [ ] 默认每秒通过到期索引进行有限批量领取；持久领取凭证和有效期支持中断/过期恢复，失效执行的迟到成功或失败不能覆盖新领取结果。
- [ ] 正式投递保持单实例约束，额外启动不得造成未经控制的重复消费；从真实进程终止后恢复，已成功目标保持成功。
- [ ] 外部已接受但成功响应丢失时允许不确定重试，并在证据中说明可能重复；不能以内部去重宣称飞书端绝对一次。
- [ ] 飞书慢请求或等待退避不持有 SQLite 写事务；阻塞发送期间另一路实际数据库提交可以完成，API 和采集不执行飞书网络请求。
- [ ] 稳定事件身份、候选转事件和逐群投递状态跨重开保持，不全表扫描评论来补偿队列问题；失败不改变归档 checkpoint。
- [ ] 配置、API、前端产物、错误、日志和消息快照无凭据泄漏；故障样本使用虚构内容，路由修复测试不操作真实机器人。

## 验证方式

复用真实归档到飞书 HTTP 替身主链，使用受控时间与门闩覆盖退避、租约和迟到结果。少量真实子进程使用临时数据库与本地受控接收端验证终止/恢复；进程内传输替身不冒充跨进程服务。以外部投递结果、重启后状态及必要存储不变量断言为主。

## 完成与后续

交付故障恢复闭环、参数及配置修复说明、隔离进程证据。三事件生命周期由 07 组合验证，系统群告警由 08 实现，三进程整体竞争与交付准备由 10 收口。
