# 06: 双群独立投递与故障恢复

**What to build:** 一个群不可用或配置错误时，其他群照常收消息；修复后仅补发未成功目标，进程中断、限流或响应丢失时消息仍可恢复处理。

**Blocked by:** 04 一级评论通知闭环。

**Status:** resolved

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 12–15、34–43；验收关联 FS-AC-07、08、09、10、14。

以已有动态及一级评论消息验证通用投递行为，不等待 05 才能验证双群故障。补齐路由继承、配置修复、逐目标持久状态、领取恢复和限流策略；不另建采集调度器或投递管理 UI。相关故障状态要可供 08 读取/登记告警事实，但本票不提前承担告警消息策略。

## 验收条件

- [x] 每 UP 默认双群及动态对相应角色的覆盖优先级正确；未覆盖角色继承 UP 默认，系统群不充当业务群后备。
- [x] 逐目标保存角色/路由引用和投递结果，队列不复制 Webhook/签名密钥；消息快照在等待及重试期间保持不变。
- [x] 缺失或错误路由只暂停受影响目标，其他群仍发送；暂停消息可持久保留，不每秒执行无效 HTTP、不丢弃、不转群。
- [x] 明确并验证配置加载、校验与修复后生效流程；补配后只恢复对应待发目标，不重置起点、不重新推送历史、不重发已成功目标，不要求额外热更新或 UI。
- [x] 一群成功另一群失败后仅后者重试；不同目标的故障或退避不造成所有目标全局阻塞。
- [x] HTTP 成功但飞书业务失败不标成功；网络超时、限流及业务错误使用经协议核验的分类和有限退避，保存下次尝试时间，不修改采集节拍。
- [x] 默认每秒通过到期索引进行有限批量领取；持久领取凭证和有效期支持中断/过期恢复，失效执行的迟到成功或失败不能覆盖新领取结果。
- [x] 正式投递保持单实例约束，额外启动不得造成未经控制的重复消费；从真实进程终止后恢复，已成功目标保持成功。
- [x] 外部已接受但成功响应丢失时允许不确定重试，并在证据中说明可能重复；不能以内部去重宣称飞书端绝对一次。
- [x] 飞书慢请求或等待退避不持有 SQLite 写事务；阻塞发送期间另一路实际数据库提交可以完成，API 和采集不执行飞书网络请求。
- [x] 稳定事件身份、候选转事件和逐群投递状态跨重开保持，不全表扫描评论来补偿队列问题；失败不改变归档 checkpoint。
- [x] 配置、API、前端产物、错误、日志和消息快照无凭据泄漏；故障样本使用虚构内容，路由修复测试不操作真实机器人。

## 验证方式

复用真实归档到飞书 HTTP 替身主链，使用受控时间与门闩覆盖退避、租约和迟到结果。少量真实子进程使用临时数据库与本地受控接收端验证终止/恢复；进程内传输替身不冒充跨进程服务。以外部投递结果、重启后状态及必要存储不变量断言为主。

## 完成与后续

交付故障恢复闭环、参数及配置修复说明、隔离进程证据。三事件生命周期由 07 组合验证，系统群告警由 08 实现，三进程整体竞争与交付准备由 10 收口。

## Answer

**已完成并取得自动化、隔离进程与迁移证据；真实飞书群与目标环境运行未验证。** 实施与逐条验收证据见 [evidence/06-delivery-routing-recovery.md](../evidence/06-delivery-routing-recovery.md)。

- 路由：业务角色按“动态覆盖 → 所属 UP 默认”解析；条目级容错——单个目的地写错（坏地址/坏密钥/非对象/未知引用）只让该目标进入 `waiting_config`（`route_invalid`），其他群照常投递；角色本身没配才是 `route_missing`；系统群不参与业务兜底。整份文件不可解析或结构非法仍拒绝启动（此时无告警通道，属 08/10 边界）。
- 修复：编辑服务端配置 → 重启通知进程。启动即复检等待记录，只补发未成功目标；阶段令牌与评论起点不变、不补历史、已成功目标不重发、不重写快照。无热更新、无新增 UI。
- 恢复：`EXPLAIN QUERY PLAN` 证明到期/租约两条索引各自命中，领取仍限批量；SIGKILL 后租约过期由重启进程恢复，已成功目标保持成功，失效凭证不能回写（既有 01 用例）。
- 协议：HTTP 200 但业务码非 0、`11232` 等限流码、`19021` 签名失败都不标成功；429/`11232` 优先用 `x-ogw-ratelimit-reset`，缺失退避 60 秒；超时/网络异常按 2 秒起指数退避（上限 300 秒）保存下次尝试时间；采集节拍未改。
- 不确定重试：外部已接受但响应丢失时按失败重试，接收端会实际收到两次——不承诺飞书端绝对一次。
- 跨进程：通知子进程阻塞在真实本机 HTTP 服务时，另一子进程的 `BEGIN IMMEDIATE` 提交 < 1 秒完成（不持有写锁）；API/采集进程不加载通知进程入口，归档只留待投递记录。
- 凭据：可选签名密钥只在发送时组装 `timestamp`/`sign`，队列、`repr`、日志与消息快照均无密钥或 webhook（虚构 secret 零命中）。
- 迁移：v18 → v19 只补 `notification_deliveries.failures/last_failed_at` 与两条索引，旧记录 `failures=0`（不倒推历史 `attempts`）。

**给 08 的故障事实契约**（本票只提供事实，不实现阈值/节流）：`notification_deliveries.state/error/failures/last_failed_at` 与只读接口 `outbox.delivery_failures(connection)` → `{role, kind, uid, dynamic_id, state, error, failures, last_failed_at}`。`attempts` 含等待配置复检，**不能**当失败次数；`failures` 只在真实外部失败时递增，成功不清零；心跳与业务消息同在投递表，需按 `kind` 过滤。
