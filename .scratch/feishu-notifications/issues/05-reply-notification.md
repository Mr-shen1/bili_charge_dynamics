# 05: 楼中楼回复通知闭环

**What to build:** 楼中楼回复归档后，按评论人身份发送 UP 群和/或全员群，消息可直达该条回复；根关系或定位条件暂未就绪时保留候选，补齐后发送。

**Blocked by:** 03 楼中楼回复精确链接；04 一级评论通知闭环。

**Status:** resolved

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 3–11、21–28、34、38、41、46–47；验收关联 FS-AC-01、02、04、05、07、11。

复用 04 的评论资格、模板、群路由和候选语义，接入回复实际保存事务，并使用 03 的精确回复入口。回复与根评论都属于新增评论，不建立另一个身份规则或独立通知时钟。

## 验收条件

- [x] 回复按当前通知起点过滤历史，初始化期间发表的新回复保留通知资格；发表时间不能由采集或根评论时间补造。
- [x] 回复及其合格事件或候选同事务保存；去重使用动态、所属根和稳定回复身份，不以回复计数或扫描轮次为键。
- [x] 根评论、身份、时间或定位条件不全时可靠暂缓；当前有效阶段内补齐后原子生成一次事件，跨重启不丢候选，不放宽合法归档校验。
- [x] 所属根与回复可在本站展示定位后即可发送，不等其他楼层、后页或媒体成功；根扫描局部失败不能虚报整轮完整，也不能自动取消已就绪条目的资格。
- [x] 本人回复双群、其他回复仅全员群；覆盖回复普通人、回复 UP、同名用户和另一受监控 UP 串门，始终以回复作者而非被回复者判定路由。
- [x] 消息使用统一评论模板、原始回复正文与上下文；不剥除来源回复前缀，不附加父评论全文，不扩大回复图片采集或飞书上传范围。
- [x] 链接携带完整定位身份，受控投递生成的链接能打开后续页具体回复，宽屏和窄屏都加载、展开并高亮目标。
- [x] 同回复反复分页、补字段、纯编辑及采集失败重试不重复生成已登记事件；暂停阶段的旧候选不能借重新入选生成通知。
- [x] 事件快照和逐群结果沿用既有不变量；根计数下降但没有新回复时不制造删除或占位通知。
- [x] 覆盖保存回滚、提交后中断、候选转事件中断和重开去重，回归一级评论通知及两类精确链接。

## 验证方式

通过实际回复采集/归档、临时 SQLite、受控来源和飞书 HTTP 接收端驱动；阻塞根上下文或后续分页证明待就绪与逐条发送。链接采用实际事件产物，不单测一个拼接函数就宣布闭环；不调用真实外部服务。

## 完成与后续

交付回复从保存到消息、再到具体回复阅读的完整链及持久候选证据。06 与本票可在各自依赖完成后并行；共享通知模型的改动需要集成协调，不能因此修改双方既定业务规则或增加伪依赖。

## Answer

已交付楼中楼回复从归档写事务到双群投递、再到本站后继页回复阅读的完整纵向切片：回复写事务内同事务登记事件或候选，独立通知进程按回复作者路由，消息链接命中 03 的回复精确入口。

- 接入与原子性：`backend/bili_monitor/storage.py` 的 `_change_replies` 在每次逐楼分页提交里调用 `outbox.record_reply`（传入 `root_id`、`discovered = previous is None`、`generation`）；回复、事件（或候选）与逐群投递记录同事务提交或回滚。单条就绪即投递，不等其他楼层、后续页或媒体；某楼后页失败不收回已提交页的资格。
- 复用 04 的小接口：同一通知阶段与评论起点、同一 `notification_candidates`、同一 `_comment_ready`/起点比较/候选原子转换、同一新增评论模板与角色表（`up`/`all`），没有为回复新建身份规则或通知时钟。
- 路由：作者 UID 与该动态所属 UP 的 UID 字符串相等 → `up` + `all`，否则仅 `all`；被回复者身份、昵称、其他受监控 UP 都不参与判定（用例覆盖“UP 回复普通人”“普通人回复 UP”“同名异 UID”“另一 UP 串门”）。
- 去重与持久：事件身份 `(kind='reply_comment', dynamic_id, root_id, comment_id)`（`root_id` 为所属根），跨重启、重复分页、补字段与纯编辑有效；候选主键改为 `(dynamic_id, root_id, comment_id)`，旧候选按一级评论回填。
- 消息：与一级评论共用模板，链接换成 `{base}/dynamics/{d}/comments/{root}/replies/{reply}/locate`；保留来源换行与“回复 @某人”前缀，不附父评论全文、不扩大回复图片采集。纯图占位按设计 §2.1 同等适用：空正文且来源已给出图片的回复显示 `【图片评论，点击链接查看】`（归档只多布尔 `has_pictures`，不存 URL、不下载上传、不新增上游请求），来源未给/未知时保持原空正文行为。
- 迁移：schema v20（06 的 v19 之后顺延），只重建 `notification_candidates` 主键，06 的投递列/索引/错误分类与配置形状不动。
- 浏览器证据：`frontend/tests/e2e-notification/reply-link.spec.ts`（`pnpm test:e2e:notification`，端口 4179/4326）用真实归档链 + 真实 `Dispatcher` 打到进程内飞书替身，从投递产物取链接，在生产装配里宽屏直开第 3 页（末页 5 条）定位高亮、窄屏刷新同样直达，且上游请求与归档内容不变。
- 证据：[05 楼中楼回复通知闭环](../evidence/05-reply-notification.md)（18 主链用例、迁移用例、上一轮全量 941 passed、`pnpm check` 275 passed、`pnpm test:e2e` 203 passed / 10 skipped、`test:e2e:notification` 4 passed、`test:e2e:location` 4 passed、`test:e2e:manage` 7 passed、`check:dist` 通过；合并核验修复轮只重跑 focused 回归：主链 18 passed、专项相邻 264 passed，全量与前端数字未在本轮重跑）。
- 正式契约：[通知进程与事件投递](../../../docs/backend/api/notification-process.md)（§3.2 楼中楼回复、§4 候选身份、§6 载荷、§7 迁移）。

## Comments

- **提前 Spec 审查的两项在本票修复**：
  - ①04 的 `record_root` 只用“当前未封存阶段 + 仍入选”推导阶段，**没有绑定领取时的阶段**。可复现的违规路径是“旧执行已领取写代次 → 停用 → 重启用（新起点）→ 旧执行迟到提交”：评论发表时间晚于新起点，起点比较会放行，于是迟到内容进了新阶段。改为根/回复/正文共用 `notification_body_claims`（generation → phase）绑定（`outbox._active_phase` 连带返回 `comment_started_at`，`_comment_phase` 删除），两条门闩用例先红后绿，并显式断言“起点早于该回复发表时间”，证明拦住它的只能是阶段绑定。
  - ②候选主键只有 `(dynamic_id, comment_id)`，无法表达“同一回复 ID 属于不同根”。v20 重建为 `(dynamic_id, root_id, comment_id)`，回复候选带所属根；临时关掉迁移重跑为红（候选写入失败导致整页 `storage_error` 回滚），证明没有靠“碰不到”回避，也没有放宽存储或来源校验。
- **“根或站点不可定位”的真实边界**：`replies` 有指向 `root_comments(dynamic_id, id)` 的外键，双方 ID 又都经过本站 `is_valid_id` 校验，因此“根缺失/身份不可定位”只会表现为**回复根本无法合法归档**（分页失败、`REPLIES_FAILED`、旧内容保留），不会出现“回复已归档但根不可定位”。本票按此如实记录，没有为此放宽外键或伪造字段；能合法归档但字段不全的只用候选暂缓。
- **候选补齐的触发时机**：不为候选轮询全表（规格禁止“扫描评论表推断新增”），补齐依赖来源触发重扫（rcount 变化、上次失败重试或 24 小时校准）。测试用“楼内新增一条旧回复”构造真实重扫，而不是直接改库。
- **“刚发表”的回复排序在最后**：按发表时间升序，测试里 fresh 回复落在末页，浏览器用例因此固定第 3 页（5 条），并用真实定位响应的 `page` 交叉核对，避免断样式巧合。
- **迁移号协调**：06 先用 v19（`failures`/`last_failed_at` + 索引），本票顺延 v20；同一 `migrate` 顺序执行，两侧各自可重入，06 的 v19 用例数字同步顺延但断言不变。
- **给 07/08/10 的稳定契约**：事件/候选身份与 `outbox.record_reply(...)` 签名见证据 §4；阶段有效性判定统一为 `outbox._active_phase(connection, dynamic_id, generation)`（正文/根/回复共用）；`live_app` 新增 `POST /api/test/replies {fresh}` 与 `POST /api/test/notify`（`notify-roots` 保留为别名）。
- **未覆盖**：真实飞书群、飞书内置浏览器/手机实机、三进程托管与目标环境（票据 10/11，需授权）；回复图片仍不在采集、归档阅读与上传范围（只记布尔存在性，不保证尚未归档的图片可见），真实来源采集、视觉基准（本票无样式改动）。
- **合并核验修复（本轮重开 claimed）**：上一轮把“纯图回复空正文”当结论交付是规格偏差——`replies.reply_document` 丢弃了来源已给出的 `content.pictures`，`has_media` 恒 False。修复只做既有规格内的事：归档回复文档新增 `has_pictures`（`None`/`True`/`False`，从既有响应推出并沿 `_merge_comment` 合并语义保留，不存 URL），`_register_comment` 的 `has_media` 追加该信号；快照在登记时冻结，补字段/重扫已登记不重发；`_reply_reading` 不发布该键，回复阅读接口与前端图片范围不变。测试先红后绿：空正文 + 已知有图 → 占位；有文字 + 图 → 原文字；无图/未知空正文 → 原行为；根评论不退化、同事务去重原状态保留。

- **合并核验修复的红绿与验证（本轮）**：先红——`test_image_only_reply_uses_the_placeholder_and_records_only_picture_presence` 在旧实现上得到 `内容：` 空行（来源回复 `content={"message": "", "pictures": [一张]}` 经真实归档写事务 → 真实 `Dispatcher` → 进程内飞书接收端），归档回复无任何图片字段；再绿——`reply_document` 落布尔 `has_pictures`、`_register_comment` 的 `has_media` 追加该信号后转绿，6 条新用例覆盖「空正文 + 已知有图 → 占位」「有文字 + 图 → 原文字」「无图/未知空正文 → 原行为」「重扫补出存在性但不重发」「候选补齐沿用合并语义」。命令与数字见[证据 §1/§2-12](../evidence/05-reply-notification.md)（主链 18 passed、专项相邻回归 264 passed；合并集成 tip `0f79ed7` 与提交前最新 tip `16fc18e` 后各重跑一次）。未跑全量后端与前端（本票无 UI 改动，按票据要求避免重复 30 分钟全回归；10 统一重跑）；未改 map/plan（由合并统一收口）。
