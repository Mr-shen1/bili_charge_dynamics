# 05: 楼中楼回复通知闭环

**What to build:** 楼中楼回复归档后，按评论人身份发送 UP 群和/或全员群，消息可直达该条回复；根关系或定位条件暂未就绪时保留候选，补齐后发送。

**Blocked by:** 03 楼中楼回复精确链接；04 一级评论通知闭环。

**Status:** ready-for-agent

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 3–11、21–28、34、38、41、46–47；验收关联 FS-AC-01、02、04、05、07、11。

复用 04 的评论资格、模板、群路由和候选语义，接入回复实际保存事务，并使用 03 的精确回复入口。回复与根评论都属于新增评论，不建立另一个身份规则或独立通知时钟。

## 验收条件

- [ ] 回复按当前通知起点过滤历史，初始化期间发表的新回复保留通知资格；发表时间不能由采集或根评论时间补造。
- [ ] 回复及其合格事件或候选同事务保存；去重使用动态、所属根和稳定回复身份，不以回复计数或扫描轮次为键。
- [ ] 根评论、身份、时间或定位条件不全时可靠暂缓；当前有效阶段内补齐后原子生成一次事件，跨重启不丢候选，不放宽合法归档校验。
- [ ] 所属根与回复可在本站展示定位后即可发送，不等其他楼层、后页或媒体成功；根扫描局部失败不能虚报整轮完整，也不能自动取消已就绪条目的资格。
- [ ] 本人回复双群、其他回复仅全员群；覆盖回复普通人、回复 UP、同名用户和另一受监控 UP 串门，始终以回复作者而非被回复者判定路由。
- [ ] 消息使用统一评论模板、原始回复正文与上下文；不剥除来源回复前缀，不附加父评论全文，不扩大回复图片采集或飞书上传范围。
- [ ] 链接携带完整定位身份，受控投递生成的链接能打开后续页具体回复，宽屏和窄屏都加载、展开并高亮目标。
- [ ] 同回复反复分页、补字段、纯编辑及采集失败重试不重复生成已登记事件；暂停阶段的旧候选不能借重新入选生成通知。
- [ ] 事件快照和逐群结果沿用既有不变量；根计数下降但没有新回复时不制造删除或占位通知。
- [ ] 覆盖保存回滚、提交后中断、候选转事件中断和重开去重，回归一级评论通知及两类精确链接。

## 验证方式

通过实际回复采集/归档、临时 SQLite、受控来源和飞书 HTTP 接收端驱动；阻塞根上下文或后续分页证明待就绪与逐条发送。链接采用实际事件产物，不单测一个拼接函数就宣布闭环；不调用真实外部服务。

## 完成与后续

交付回复从保存到消息、再到具体回复阅读的完整链及持久候选证据。06 与本票可在各自依赖完成后并行；共享通知模型的改动需要集成协调，不能因此修改双方既定业务规则或增加伪依赖。
