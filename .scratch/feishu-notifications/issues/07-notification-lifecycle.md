# 07: 停用、重纳入与在途通知

**What to build:** 用户停止或移出目标后不再产生新通知，已经入队的消息仍按原资格送达；恢复监控不追补暂停历史，普通进程重启不改变通知起点。

**Blocked by:** 05 楼中楼回复通知闭环；06 双群独立投递与故障恢复。

**Status:** ready-for-agent

## 上下文与范围

依据：[实施规格](../spec.md)、[正式需求与设计](../../../docs/design/feishu-notifications.md)、[领域词汇](../../../GLOSSARY.md)。对应用户故事 25–33、38–40；验收关联 FS-AC-05、06、07、10。

01、04、05 已实现各自基本阶段校验，本票覆盖动态、根评论、回复、待判定候选及失败队列的完整生命周期交错，补齐发现的实现缺口，不将基础安全推迟到这里才开始。依赖 06 是为了证明停用后等待配置/失败重试/已领取消息仍能正确恢复，而非只测成功路径。

## 验收条件

- [ ] 停用 UP、移出近期窗口、删除指定目标、删除监控配置、模式切换后不再入选，均结束相应通知阶段而不删除归档。
- [ ] 动态、根评论和回复分别覆盖“任务已领取、管理操作发生、归档随后提交”；内容按原 owner 规则可保留，但失效阶段不生成新通知。
- [ ] 通知阶段与入选代次在提交时核验，不只在任务开始检查；旧执行或旧候选不能因为当前已重新入选而冒充新阶段事件。
- [ ] 已入队消息在停止后仍投递，包括等待配置、失败退避及在途领取；不随监控配置删除级联丢失，已成功目标不重复发送。
- [ ] 尚未取得资格的候选与已入队事件区分：旧阶段结束后补齐信息，不据旧候选生成新事件；既有归档仍可读。
- [ ] 重新启用/重新入选创建新的持久起点，以恢复后第一份可信当前正文重建基线，不补暂停编辑；评论按新起点过滤，不补暂停期间发表的历史评论。
- [ ] 新阶段初始化期间的新评论仍有资格；同秒边界和字段补齐沿用原时间规则，不能以新扫描时间重新激活旧评论。
- [ ] 普通 API、采集或通知进程重启不等于停用，原起点、基线、候选和队列保持；适当恢复未完成领取，不重建启用时间。
- [ ] 仍持续入选的目标在重复保存等价配置或重复发布相同窗口时不重设起点；真实移出再入选才建立新阶段。
- [ ] 跨重启、重纳入、重复扫描的事件去重保持；停止后的投递结果不会推进新阶段的归档或通知基线。
- [ ] 完整记录各停止原因、各事件类型与候选/队列状态的组合结果，回归原目标代次、归档保留及分项 checkpoint 行为。

## 验证方式

使用实际管理与归档入口、临时 SQLite、可控来源/飞书接收端，通过门闩精确安排在途提交顺序。用数据库重开及少量真实进程重启区分“重新启用”和“进程恢复”。不能只直接修改测试数据库绕过真实管理生命周期。

## 完成与后续

交付可复核生命周期矩阵与必要实现修正。此票通过仍不代表真实飞书或所有目标环境验证完成；10 负责组合回归与台账，11 负责授权实测。
